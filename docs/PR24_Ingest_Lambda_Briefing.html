01 What This PR Does

This PR completes Milestone 12 of the refactor. It introduces the full VCF ingest pipeline — the code that takes a VCF file uploaded to cloud storage, validates it against a clinical manifest, and persists all variant and patient data to the database. It also adds the Lambda handler that wires the whole pipeline to an automated cloud trigger.

In practical terms: after this PR, uploading a .vcf.gz file to the right cloud storage location will automatically kick off the entire ingest process without any manual intervention.

Orientation

The code reviewed in this PR sits in the backend layer only. It is not part of the web API (no HTTP routes are added here). Instead, it is the background data ingestion path: files arrive asynchronously from a clinical pipeline, and this code processes them into the database so they appear in the web UI.

02 AWS Concepts for Python Developers

This section explains the three AWS services used in this PR. If you are already familiar with S3, Lambda, and boto3, skip ahead to Section 3.

Amazon S3
Simple Storage Service — cloud file storage

S3 is AWS's object storage service. Think of it as a very large file system in the cloud. A bucket is like a top-level folder; an object is any file stored inside it; an object key is the file path within the bucket (e.g. runs/2024/sample.vcf.gz). There is no concept of directories — the key is just a string that may contain slashes.

Storage
AWS Lambda
Serverless function — runs code on demand

Lambda lets you run Python functions in the cloud without managing any servers. You upload your code, and AWS runs it in response to events. Each invocation is independent — Lambda boots your function, runs it, and stops. You pay only for the time it runs. Critically, multiple Lambda invocations can run concurrently — this is why the TOCTOU race condition discussed in Section 7 is real.

Compute
S3 → Lambda Trigger
Automatic invocation on file upload

S3 can be configured to automatically invoke a Lambda function whenever a file is uploaded to a specific bucket or key prefix. This is called an event notification. The handler() function in this PR is that Lambda. AWS calls it with an event payload — a JSON object describing what was uploaded and where. No polling, no cron job; the trigger is instant.

Integration
boto3
AWS Python SDK — the AWS standard library for Python

boto3 is the official Python library for interacting with all AWS services. In this PR it is used to download files from S3. boto3.client("s3") creates a connection to the S3 API. The method download_file(bucket, key, local_path) downloads an S3 object to a local file path. It handles authentication, retries, and streaming automatically.

SDK

The S3 event payload structure

When a file is uploaded, Lambda receives a JSON payload that looks like this. The handler unpacks it to find the bucket name and file path:

{
  "Records": [
    {
      "s3": {
        "bucket": { "name": "variant-viewer-vcf-749929395031" },
        "object": { "key": "runs/2024/26041S0057.vcf.gz" }
      }
    }
  ]
}
AWS Gotcha

S3 delivers the object.key URL-encoded. A filename with a space like my sample.vcf.gz arrives as my+sample.vcf.gz. The code should call urllib.parse.unquote_plus(key) before using the key — this is a known gap flagged in the PR review.

What is jsonschema?

jsonschema is a pure-Python library that validates a Python dict against a JSON Schema — a standard way of describing the shape of a JSON document (required fields, types, allowed values). If the data does not match the schema, it raises jsonschema.ValidationError. Think of it as a form validator for JSON.

03 End-to-End Data Flow

The diagram below shows the complete journey of a VCF file from upload to database — all of it triggered automatically by a single file upload.

The two-file convention

Every VCF upload is expected to come with a paired manifest file. The manifest is a FHIR R4 Bundle — a structured JSON document that carries clinical metadata about the patient and specimen. The naming convention is:

File typeExample keyPurpose
VCF (variant calls)runs/2024/26041S0057.vcf.gzThe genomic data — one row per variant
Manifest (metadata)runs/2024/26041S0057.manifest.jsonPatient lab number, specimen ID, pipeline used, case type

The manifest key is derived automatically by replacing the .vcf or .vcf.gz extension with .manifest.json. This means both files must be uploaded to the same S3 prefix with the same base name.

04 The Lambda Handler

lambda_handler.py is a thin routing and error-handling shell. Its job is to unpack the S3 event, delegate to the ingest pipeline, and translate Python exceptions into HTTP-style status codes. It contains no business logic of its own.

What handler(event, context) does, step by step

1
Guard against multi-record events. The handler expects exactly one S3 record. If AWS delivers more (which can happen in batch scenarios), it raises RuntimeError. Lambda treats an unhandled exception as a failure and will retry the invocation — this is intentional behaviour for unexpected situations.
2
Unpack the event. Extracts the bucket name and VCF key from the nested JSON structure. Then derives the manifest key using a regular expression.
3
Create an S3 client. boto3.client("s3") creates a connection to the S3 API using credentials that Lambda automatically injects via its IAM execution role. No credentials are hardcoded.
4
Open a database transaction and call ingest_sample(). with_transaction() is a context manager that opens a database connection and wraps everything in a single transaction. If ingest_sample() raises, the transaction is rolled back automatically.
5
Return a structured response. The return value is a Python dict with a statusCode key. Lambda itself does not use HTTP status codes, but this convention lets monitoring tools read the outcome without parsing log messages.

Status code convention

CodeTriggerMeaning
200No exception raisedVCF successfully ingested; sample_id included in response
409DuplicateSubmissionErrorThis VCF file was already ingested — re-upload is rejected
400ValueError or jsonschema.ValidationErrorBad input — invalid VCF key format or invalid manifest
(no return)Any other exceptionUnexpected failure; Lambda retries and eventually routes to a Dead Letter Queue
Design note

The DuplicateSubmissionError is caught and returns 409 rather than letting it propagate, because a duplicate upload is an expected clinical scenario (e.g. a file re-sent by mistake) — not a system failure. Lambda should not retry it. Any other exception is treated as a genuine fault and is allowed to propagate so Lambda's retry and DLQ mechanisms kick in.

05 The ingest_sample() Pipeline

ingest_sample() in ingest.py is the heart of this PR. It is a nine-step sequential pipeline. Steps 1–8 run inside a TemporaryDirectory; step 9 runs outside it (after the temp files have been deleted) to keep database writes separate from file I/O.

Why use a TemporaryDirectory?

Lambda functions can be warm — after the first invocation, the runtime may be kept alive and reused for subsequent invocations. If files were written to /tmp without cleanup, each warm invocation would accumulate more files until the 512 MB /tmp limit is hit. tempfile.TemporaryDirectory is a context manager that creates a uniquely named directory and automatically deletes it when the with block exits — even if an exception is raised. This makes the Lambda safe for high-volume use.

Why run DB writes outside the TemporaryDirectory block?

By the time the database writes start, the VCF and manifest files are no longer needed — the data has been parsed into Python objects (VcfVariant instances and the manifest struct). Exiting the with tempfile.TemporaryDirectory() block at that point means the files are deleted before the database work begins, keeping the /tmp usage as short as possible.

The idempotency check

Before any database writes, the pipeline checks whether this exact VCF file has already been ingested by querying the samples table for the s3_key. This prevents duplicate rows. The check is deliberately simple: only an identical S3 key is rejected. Multiple VCFs for the same patient (e.g. from different gene panels) are allowed because the database has no unique constraint on (patient_id, sample_name).

06 Database Persistence

Step 9 of the pipeline performs all database writes inside a single psycopg2 cursor block. The writes are sequential and depend on each other — each returns a database-generated integer ID that feeds into the next.

The patient UPSERT

The patient is written using an upsert — a combined INSERT and UPDATE in one SQL statement. If the patient's lab_number already exists, the row is updated rather than rejected. The COALESCE function means: use the new value if it is not null, otherwise keep the existing value. This allows patient records to be enriched over time without overwriting existing data with nulls.

INSERT INTO patients (lab_number, name, dob)
VALUES (%s, %s, %s)
ON CONFLICT (lab_number) DO UPDATE
  SET name = COALESCE(EXCLUDED.name, patients.name),
      dob  = COALESCE(EXCLUDED.dob,  patients.dob)
RETURNING id

EXCLUDED is a PostgreSQL keyword that refers to the row that was proposed for insertion (i.e., the new values). RETURNING id means PostgreSQL sends back the row's primary key in the result set, so the code can retrieve it with cur.fetchone()[0].

The classification shell

For each variant, a variant_classification row is inserted as a pending shell. This row does not contain a final classification verdict — it is a placeholder that records which scoring framework applies (ACGS SNV vs SVIG-UK) and pre-populates criteria values computed from the variant data. A clinical scientist will later review and finalise the classification in the web UI.

07 Error Handling & the TOCTOU Race

DuplicateSubmissionError

This is a custom exception class defined at the top of ingest.py. It carries two structured attributes alongside the message string:

AttributeTypeMeaning
duplicate_typestrAlways "exact" — only re-uploading the identical file is rejected
existing_sample_idintThe database ID of the existing sample, or -1 if the ID is unavailable (TOCTOU race)

The TOCTOU race condition

TOCTOU stands for Time Of Check, Time Of Use. It is a classic concurrency bug. Because Lambda can run many invocations at the same time, two uploads of the same file can happen simultaneously:

The except psycopg2.errors.UniqueViolation block at the end of ingest_sample() handles this case. A UniqueViolation is a specific PostgreSQL error (a subclass of psycopg2.errors.IntegrityError) raised when an INSERT would violate a UNIQUE constraint. The code catches it and raises DuplicateSubmissionError with existing_sample_id=-1 (the ID is unknown because we can not easily recover it at this point).

Review note

The except UniqueViolation block currently catches violations from any INSERT in the write block, not just samples.s3_key. A bug in pre_compute_criteria() that emits duplicate criterion codes would be swallowed as a "duplicate VCF" error. The review comment on this PR recommends checking exc.diag.constraint_name to narrow the catch.

08 Test Design

The tests use Python's unittest.mock library to replace the two external systems — S3 and the database — with controllable fakes. This means the tests run without any network access, AWS credentials, or a running database.

Mocking S3 with _make_s3_mock()

Rather than actually uploading to S3, the mock intercepts download_file(bucket, key, dest) and writes files directly to the local destination path. The manifest content is the test fixture dict serialised to JSON; the VCF gets a minimal valid header.

def download_side_effect(bucket, key, dest):
    if key.endswith(".manifest.json"):
        Path(dest).write_text(manifest_content)  # write the test manifest locally
    else:
        Path(dest).write_text("##fileformat=VCFv4.2\n")  # minimal VCF header

Mocking the database with _make_db_mock()

The database mock returns pre-set values from fetchone() in sequence using side_effect. The sequence reflects the order the pipeline calls fetchone():

Call #ReturnsReason
1stNonecheck_idempotency: no existing row found for this s3_key
2nd(patient_id,)INSERT INTO patients RETURNING id
3rd(sample_id,)INSERT INTO samples RETURNING id

Mocking parse_vcf()

Because parse_vcf() calls cyvcf2 (which needs a real VCF file), the happy-path ingest tests patch it with @patch("app.lib.ingest.parse_vcf"). The mock returns a bare VcfMeta object directly, bypassing file parsing entirely.

Test Philosophy

The test suite deliberately avoids integration testing (no real database, no real S3). This makes tests fast and deterministic — they pass in any environment without AWS credentials. The trade-off is that the mock sequences must be kept in sync with the real call order. When the production code changes, the mocks may need updating.
