01 Vite vs webpack

Traditional bundlers like webpack read your entire source tree, compile everything into a dependency graph, and re-bundle whenever a file changes. On large projects this makes cold starts and hot reloads slow — sometimes tens of seconds.

Vite takes a different approach for development. It uses the browser's native ES module support to serve source files directly — no bundling at all during development. When you change a file, only that module is reloaded. Cold starts are near-instant regardless of project size.

For production builds, Vite hands off to Rollup (a mature, well-optimised bundler) to produce a small, tree-shaken output. This means the dev experience is fast, and the production bundle is compact — best of both worlds.

# Development (native ES modules, no bundling)
npm run dev   # starts vite dev server, instant HMR

# Production (TypeScript check + Rollup bundle)
npm run build  # = tsc && vite build
In this projectConfigured in vite.config.ts. The dev server proxies /api requests to localhost:3000 (the FastAPI backend), so the frontend can call backend endpoints without CORS issues during local development.

02 The vitest/config dual-use pattern

Vitest is the test runner used in this project. It is built on top of Vite and deliberately re-uses the same transformation pipeline — the same TypeScript compilation, JSX handling, and path aliases work in tests exactly as they do in the browser.

The key quirk is the import at the top of vite.config.ts:

// ✗ Wrong — loses Vitest's "test" configuration block type
import { defineConfig } from "vite"

// ✓ Correct — TypeScript knows about the "test" block
import { defineConfig } from "vitest/config"

When you import from "vitest/config" instead of "vite", the defineConfig function gains type awareness of the test: block, so TypeScript will catch typos in test configuration options.

In this projectvite.config.ts uses import { defineConfig } from "vitest/config" and contains both a server.proxy section (for dev) and a test section (for Vitest). One file serves both purposes — you do not need a separate vitest.config.ts.

03 TypeScript strict mode options

TypeScript has a large number of individual strictness flags. The "strict": true option in tsconfig.json enables a bundle of them all at once. Beyond that, this project uses several additional options that deserve explanation:

OptionWhat it meansWhy it matters here
noEmit: trueTypeScript compiles for type-checking only; it does not write any .js filesVite uses esbuild (not tsc) for the actual transpilation — it is faster. tsc is only used for finding type errors.
isolatedModules: trueEach file must be type-checkable in isolation without looking at other filesRequired for esbuild and Babel-style transpilers that process one file at a time. Prevents const enum and namespace merging.
allowImportingTsExtensions: trueAllows import Foo from "./Foo.tsx" with the .tsx extensionVitest imports use the real file extension. Only valid when noEmit: true.
moduleResolution: "bundler"Resolves modules the way a bundler (Vite/webpack) would, not the way Node.js wouldSupports .tsx imports, path aliases, and package exports correctly for bundled apps.
resolveJsonModule: trueAllows import data from "./config.json"Needed to import the criteria JSON files directly into TypeScript.
types: ["vite/client"]Adds type definitions for import.meta.envWithout this, TypeScript complains that import.meta.env does not exist.
Why tsc and esbuild together?

esbuild is 100× faster than tsc but performs no type-checking — it just strips types. tsc is slow but catches type errors. Running tsc --noEmit first catches type errors, then Vite runs esbuild to produce the actual output. You get both correctness and speed.

04 Tailwind CSS and @layer

Tailwind is a utility-first CSS framework. Instead of writing .button { padding: 8px 16px; ... }, you compose classes directly in your HTML: <button class="px-4 py-2 text-sm font-medium">. At build time, Tailwind scans all files matching the content glob and generates CSS containing only the classes actually used. Unused utility classes are tree-shaken away.

The three Tailwind directives at the top of src/index.css insert Tailwind's three layers:

@tailwind base;       /* CSS reset + browser default normalisation */
@tailwind components; /* @layer components goes here */
@tailwind utilities;  /* all utility classes (px-4, text-sm, etc.) */

The @layer components block defines reusable CSS classes using @apply. The @apply directive expands to the utility classes it references at build time. This lets you write <span class="badge badge-pending"> in JSX instead of a long string of utilities, without losing Tailwind's tree-shaking.

@layer components {
  .badge {
    @apply inline-flex items-center px-2 py-0.5 rounded text-xs font-medium;
  }
  .badge-pending {
    @apply bg-yellow-100 text-yellow-800;
  }
}
In this projectsrc/index.css defines 13 badge-* classes (workflow statuses + classification outcomes) and 4 btn-* classes (btn, btn-primary, btn-secondary, btn-danger). These classes are used throughout D1–D4 components and tested in WorkflowBadge.test.tsx and ClassificationBadge.test.tsx.

05 jsdom — simulated browser for tests

React components render HTML and respond to DOM events (clicks, input changes). To test them automatically you need a document object — but real browsers cannot run in a command-line test runner.

jsdom is a JavaScript implementation of the browser DOM and HTML standards. When Vitest uses the environment: "jsdom" setting, it loads jsdom before each test file, giving your code a realistic document, window, navigator, and event system — without ever opening a browser.

// In vite.config.ts
test: {
  environment: "jsdom",   // use jsdom (not "node")
  globals: true,           // makes describe/it/expect available without import
  setupFiles: ["./src/tests/setup.ts"]  // runs before every test file
}

The setupFiles entry points to src/tests/setup.ts, which contains a single line:

import "@testing-library/jest-dom";

This import extends jsdom's expect matchers with DOM-specific ones like toBeInTheDocument(), toHaveClass(), and toBeDisabled(). Without it, those matchers do not exist and tests that call them will throw.

Common mistake

The package name is jsdom, not @vitest/jsdom. The latter does not exist. Vitest discovers the installed jsdom package automatically when environment: "jsdom" is set — you never import it directly.

06 nginx try_files and SPA routing

A single-page application manages its own routing in JavaScript. When a user navigates to /patients/42, the React Router intercepts the URL change and renders the right component — the server is never involved after the initial page load.

This creates a problem when users directly access or refresh a deep URL. The browser asks the server for /patients/42. A naïve nginx configuration tries to find a file at that path, fails, and returns 404.

The fix is try_files:

location / {
    try_files $uri $uri/ /index.html;
    # 1. Try $uri — serve the file if it exists (e.g. /assets/index-abc.js)
    # 2. Try $uri/ — serve as a directory index
    # 3. Fall back to /index.html — let React Router handle it
}

The three arguments are tried in order. Static assets (.js, .css, images) match on the first attempt. All other paths fall through to /index.html, which loads the React app, which reads the URL and renders the correct page.

In this projectnginx.conf has two location blocks: location / with try_files for SPA routing, and location /api/ with proxy_pass http://backend:3000. The backend hostname backend resolves to the FastAPI container within the Docker network defined in docker-compose.yml.

07 Docker multi-stage builds

A single Dockerfile can contain multiple FROM stages. Each stage starts from a fresh base image. The final image only contains what the last stage copies from previous stages — everything else (the build tools, node_modules, intermediate files) is discarded.

# Stage 1: builder — installs node, npm, all dev dependencies, runs build
FROM node:20-slim AS build

WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci                # reproducible install (uses package-lock.json)
COPY . .
RUN npm run build         # tsc + vite build → produces dist/

# Stage 2: final — only nginx + the compiled static files
FROM nginx:alpine

COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

The final nginx image contains no Node.js, no npm, no node_modules, and no TypeScript source. It is small and has a minimal attack surface. The builder stage is discarded entirely after the build — it is not part of the image you push to a registry.

In this projectpackage-lock.json* (the asterisk makes it optional) is copied before COPY . . so that Docker's layer cache is preserved when only source files change. npm ci (not npm install) is used to install from the lock file exactly, giving reproducible builds.

08 The criteria JSON schema

Two JSON files bundle the classification framework definitions into the frontend: acgs-snv-criteria.json (ACGS SNV, 28 criteria) and svig-criteria.json (SVIG-UK, 18 criteria). They are direct copies of the backend config files in backend/config/, ensuring the frontend and backend scoring engines use identical data.

Each file has four top-level keys:

KeyTypePurpose
versionstringHuman-readable framework version (e.g. "ACGS 2024 Best Practice Guidelines")
frameworkstringMachine identifier: "acgs_snv" or "svig"
criteriaarray of criterion objectsOne object per classification criterion (PVS1, PM2, BA1…)
combination_rulesarray of rule objectsPairs of criteria that conflict or are mutually exclusive
thresholdsobject of score boundariesPoint thresholds for each classification outcome

Each criterion object has a consistent shape:

{
  "code": "PVS1",
  "label": "PVS1",
  "category": "functional",       // groups criteria in the UI panel
  "direction": "pathogenic",       // or "benign" / "oncogenic"
  "default_strength": "very_strong", // point weight when applied
  "permitted_strengths": ["very_strong", "strong", ...],
  "adjustable": true,               // show strength dropdown in UI
  "description": "Null variant...", // tooltip/label in UI
  "pre_computable": true,           // backend can auto-apply from VCF data
  "pre_compute_hint": "Frameshift..."  // shown when pre-computed
}
In this projectThe criteria JSON files are imported by src/lib/classification-engine.ts (introduced in C2) using import acgsCriteria from "../config/acgs-snv-criteria.json". The resolveJsonModule: true tsconfig option enables this import. Vitest test files also import the JSON directly to drive the classification engine golden-case tests.
