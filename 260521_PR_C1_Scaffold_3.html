01 package.json

package.json Infrastructure

Purpose: Declares all npm dependencies and the five scripts that drive the development workflow.

Scripts

ScriptCommandWhen used
devviteLocal development — starts dev server with HMR on port 5173
buildtsc && vite buildCI / Docker — type-checks first, then bundles
previewvite previewLocally preview the production build before deploying
testvitest run --passWithNoTestsCI — runs tests once, exits 0 even with no test files
test:watchvitestDeveloper watch mode — re-runs tests on file save
--passWithNoTests

Vitest exits with code 1 when there are no test files — which would break CI for PR C1 (scaffold only, no tests yet). The --passWithNoTests flag changes this to exit 0. This flag is removed later in the series once test files exist.

Dependency split: runtime vs devDependencies

react, react-dom, react-router-dom, and @tanstack/react-table are in dependencies because they are needed at runtime in the browser. Everything else (Vite, Vitest, TypeScript, Tailwind, testing libraries) is in devDependencies — it is only needed to build and test, not to run.

In practice, for a frontend that runs entirely in the browser, this distinction does not affect the final bundle — Vite tree-shakes everything. But it is good practice and makes the intent clear to future maintainers.

02 vite.config.ts

vite.config.ts Infrastructure

Purpose: Single configuration file for both the Vite build/dev server and the Vitest test runner.

Three sections

plugins — react() from @vitejs/plugin-react enables SWC-based JSX transforms and React Fast Refresh (hot reloads that preserve component state during development).

server.proxy — During npm run dev, any request to /api/* is forwarded to http://localhost:3000. changeOrigin: true rewrites the Host header to match the target, avoiding CORS issues. This proxy is only active in the dev server — in production, nginx handles the proxying.

test — Tells Vitest to use the jsdom environment and to run src/tests/setup.ts before every test file. globals: true makes describe, it, expect, vi available without explicit imports in test files.

Design decision: one file for build and test

Having a single config file means both the dev server and the test runner use the same path aliases, JSX plugin, and transform settings. This prevents subtle "works in tests but breaks in browser" discrepancies.

03 tsconfig.json

tsconfig.json Configuration

Purpose: TypeScript compiler options. Only affects type-checking — Vite uses esbuild for the actual JavaScript transpilation.

The unusual options (all explained in Part 2, §03)

Path alias

"paths": { "@/*": ["src/*"] } allows import Foo from "@/components/Foo" instead of "../../components/Foo". This must be declared in both tsconfig (for type resolution) and vite.config.ts (for runtime resolution) to work correctly. This project does not currently use the alias in practice but the pattern is established for future use.

04 tailwind.config.ts

tailwind.config.ts CSS

Purpose: Tells Tailwind which files to scan for class names, and extends the default theme with project-specific fonts.

content glob

content: ["./index.html", "./src/**/*.{ts,tsx}"] — Tailwind scans these files to find every CSS class name used. Any class not found here will be stripped from the production CSS. The glob intentionally includes TypeScript files because JSX class strings live in .tsx files.

Font extension

The theme.extend.fontFamily block adds two custom font stacks: font-sans uses Inter (falling back to system-ui), and font-mono uses JetBrains Mono. These fonts are not loaded externally — they use system fonts as fallbacks and rely on the user having Inter installed, or degrade gracefully. No Google Fonts or CDN dependency.

05 postcss.config.cjs

postcss.config.cjs CSS

Purpose: Configures PostCSS, the CSS transform runner that processes src/index.css.

Two plugins: tailwindcss (expands the @tailwind directives and @apply rules) and autoprefixer (adds vendor-prefixed CSS properties for browser compatibility).

Why .cjs not .ts?

The project uses "type": "module" in package.json, which makes all .js files treated as ES modules. PostCSS's config loader uses require() (CommonJS) to load the config file — it cannot load .ts files without ts-node. The .cjs extension opts this single file out of ES module mode, allowing PostCSS to load it with require() without needing ts-node.

06 Dockerfile

Dockerfile Infrastructure

Purpose: Multi-stage Docker build that produces a minimal nginx image containing only the compiled static files.

Stage 1 — builder (node:20-slim)

Installs all dependencies with npm ci (reproducible install from lock file), then runs npm run build (TypeScript check + Vite bundle). The output is in /app/dist.

Note: package-lock.json* with an asterisk makes the lock file optional — if it does not exist, Docker does not error. In practice it always exists in this repo.

Stage 2 — final (nginx:alpine)

Copies only /app/dist from the builder and the custom nginx.conf. The entire Node.js toolchain, source files, and node_modules (~200 MB) are discarded. The final image is ~50 MB (nginx:alpine base + dist files).

Layer caching

COPY package.json package-lock.json* ./ is done before COPY . .. Docker caches each layer by its inputs. If only source files change (not package.json), Docker reuses the npm ci cache layer and skips reinstalling 200+ packages — saving 30–60 seconds per build.

07 nginx.conf

nginx.conf Infrastructure

Purpose: nginx server block configuration — SPA routing via try_files and API proxying to the FastAPI backend.

location / — SPA routing

try_files $uri $uri/ /index.html serves real files (JS, CSS, images) directly, and falls back to index.html for any other path. This is what makes React Router's client-side routes work on direct access or page refresh (explained in detail in Part 2, §06).

location /api/ — backend proxy

proxy_pass http://backend:3000 forwards all requests starting with /api/ to the FastAPI backend container. The hostname backend resolves within the Docker Compose network. The two proxy_set_header lines preserve the original client IP and host for use in backend request logging.

Port 3000, not 8000

The FastAPI backend listens on port 3000 (set in its own Dockerfile: CMD ["uvicorn", ..., "--port", "3000"]). The proxy target must be backend:3000 — not port 8000, which is a common FastAPI tutorial default but not what this backend uses.

08 index.html

index.html Entry point

Purpose: The single HTML document that all routes of the SPA share. Contains only a root div and the module script tag.

Unlike traditional setups, Vite treats index.html as a first-class entry point rather than a template. The <script type="module" src="/src/main.tsx"> tag is processed directly — Vite resolves it as a TypeScript module, transforms it, and rewrites the path to the hashed bundle URL in the production build.

The <div id="root"></div> is where React mounts. The entire application UI is rendered inside this element.

09 src/index.css

src/index.css CSS

Purpose: Global stylesheet — loads Tailwind's three layers and defines the project's reusable CSS component classes.

@layer base

@layer components — btn-* classes

4 button variants: .btn (base), .btn-primary (blue fill), .btn-secondary (white/gray outline), .btn-danger (red fill). Components use these classes directly in JSX rather than repeating the full utility string every time.

Why @layer components instead of plain CSS?

Placing classes in @layer components ensures they have lower specificity than Tailwind utility classes. This means you can always override a .badge-pending style with a utility class like text-white in JSX without needing !important.

10 src/main.tsx

src/main.tsx Entry point

Purpose: React application mount point — the bridge between the static HTML and the React component tree.

import React from "react";
import ReactDOM from "react-dom/client";
import { BrowserRouter } from "react-router-dom";
import App from "./App";
import "./index.css";

ReactDOM.createRoot(document.getElementById("root")!).render(
  <React.StrictMode>
    <BrowserRouter>
      <App />
    </BrowserRouter>
  </React.StrictMode>
);

React.StrictMode runs extra checks in development only (double-invoking render functions, detecting deprecated lifecycle methods). It has zero runtime cost in production.

BrowserRouter provides the routing context that useParams, useNavigate, and <Route> components rely on. It must wrap the entire application so routing works at every level of the component tree.

The ! after getElementById("root") is a TypeScript non-null assertion — it tells TypeScript "I know this element exists". If it does not exist at runtime, React will throw immediately with a clear error.

11 src/App.tsx (placeholder)

src/App.tsx Placeholder

Purpose: Temporary placeholder — the real App.tsx (with routes and Navbar) is introduced in PR D4.

// Placeholder — routes wired in D4 once all components and pages exist
export default function App() {
  return null as unknown as JSX.Element;
}

The cast null as unknown as JSX.Element is needed because TypeScript's JSX types require a component to return JSX.Element | null. Returning null directly is valid at runtime but TypeScript's strict mode rejects it in components typed to return JSX.Element. The cast bypasses the type check without changing runtime behaviour.

Why a placeholder here?

The scaffold commit must pass tsc and vite build. main.tsx imports App, so App.tsx must exist and export a default function. If it imported real components (Navbar, PatientsPage, etc.) those components would also need to exist — forcing all 10 components to be introduced in the scaffold commit. The placeholder breaks that dependency, keeping the scaffold PR focused on infrastructure only.

12 src/tests/setup.ts

src/tests/setup.ts Test infrastructure

Purpose: Runs before every test file; extends Vitest's expect with DOM-specific matchers from @testing-library/jest-dom.

Contains exactly one line: import "@testing-library/jest-dom". This import has the side effect of calling expect.extend() with matchers like toBeInTheDocument(), toHaveClass(), and toHaveValue().

Referenced by the setupFiles array in vite.config.ts — Vitest loads and executes this file in the jsdom environment before any test file runs.

13 src/config/pipelines.json

src/config/pipelines.json Configuration data

Purpose: Default variant filter presets for each sequencing pipeline. Consumed by src/lib/pipeline-config.ts (PR C2) to pre-populate the variant table filter bar with sensible defaults.

Two pipelines are currently defined:

Pipeline keygnomAD AF maxPre-filtered consequencesClinVar excluded
dragen_germline0.01 (1%)stop_gained, frameshift, splice_acceptor/donor, missenseBenign, Likely_benign
dragen_somatic0.001 (0.1%)None (show all)None

The germline preset pre-filters to coding variants with population frequency below 1% — a reasonable starting point for diagnostic germline analysis. The somatic preset applies only a stricter AF filter (0.1%) reflecting that somatic variants are expected to be rare in the population.

Runtime vs build-time

These presets are bundled into the JS at build time (not fetched at runtime). Adding a new pipeline requires rebuilding and redeploying the frontend. If dynamic pipeline configuration is needed in future, this could be moved to a backend API endpoint.
