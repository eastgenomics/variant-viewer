16 get_upload_url — validation chain

Selected because the validation logic has a deliberate ordering that is not obvious from reading the code alone. Each guard protects a different thing, and their order matters.

get_upload_url upload.py · lines 37–82 · POST /api/upload-url 
@router.post("/upload-url", response_model=UploadUrlResponse)
async def get_upload_url(body: UploadUrlRequest) -> UploadUrlResponse:
    if not _VCF_RE.search(body.vcf_filename):           # ①
        raise HTTPException(status_code=400, ...)

    safe_filename = body.vcf_filename                    # ②
    if "/" in safe_filename or ".." in safe_filename:  # ③
        raise HTTPException(status_code=400, ...)

    if body.run_date is not None:                       # ④
        try:
            datetime.strptime(body.run_date, "%Y-%m-%d")
        except ValueError:
            raise HTTPException(status_code=400, ...)

    bucket = os.environ.get("VCF_BUCKET_NAME")         # ⑤
    if not bucket:
        raise HTTPException(status_code=500, ...)

    date_prefix = body.run_date or datetime.today().strftime("%Y-%m-%d")  # ⑥
    vcf_key = f"runs/{date_prefix}/{safe_filename}"      # ⑦
    manifest_key = _VCF_RE.sub(".manifest.json", vcf_key)  # ⑧

    region = os.environ.get("AWS_REGION", "eu-west-2")
    s3 = boto3.client("s3", region_name=region)         # ⑨

    vcf_url = s3.generate_presigned_url(                 # ⑩
        "put_object",
        Params={"Bucket": bucket, "Key": vcf_key},
        ExpiresIn=3600,
    )
    manifest_url = s3.generate_presigned_url(            # ⑪
        "put_object",
        Params={"Bucket": bucket, "Key": manifest_key},
        ExpiresIn=3600,
    )
    return UploadUrlResponse(                            # ⑫
        vcf_url=vcf_url, manifest_url=manifest_url,
        vcf_key=vcf_key, manifest_key=manifest_key,
        expires_in=3600,
    )
①
Extension guard (400). _VCF_RE = re.compile(r"\.vcf(\.gz)?$") was compiled once at module load time. Using .search() rather than .match() finds the pattern anywhere in the string, including after a path prefix — but at this point the filename should not have a path, which is enforced by check ③.
②
Alias before mutation. safe_filename is assigned as a local name for the validated filename. The alias makes the intent explicit: from this point, only safe_filename should be used in key construction. Using body.vcf_filename later would be a bug — the alias is a named contract.
③
Path traversal guard (400). Without this check, a client could send vcf_filename: "../secret.vcf.gz", which would produce S3 key runs/2024-11-05/../secret.vcf.gz. S3 resolves this to runs/secret.vcf.gz, escaping the runs/{date}/ namespace and potentially overwriting another object. Rejecting / and .. prevents this entirely.
④
Calendar-valid date check (400). datetime.strptime(run_date, "%Y-%m-%d") validates both format and calendar: it raises ValueError for "2024-13-45" (month 13 does not exist) where a regex like \d{4}-\d{2}-\d{2} would not. The date object returned is immediately discarded — we only call this to validate. This check runs before the bucket env-var check so a client with a bad date always gets 400, not 500.
⑤
Bucket guard (500). This is a server configuration error, not a client error — hence 500 not 400. It is checked after all input validation so a bad client request always gets a client error regardless of server state. If it were checked first, a misconfigured server would return 500 even for requests with invalid filenames, hiding the true client error.
⑥
Date prefix fallback. body.run_date or datetime.today().strftime("%Y-%m-%d") — if the client provided a date (and it passed check ④), use it; otherwise default to today. datetime.today() uses server local time — acceptable here since the date prefix is only organisational, not a precise timestamp.
⑦
Key construction uses safe_filename, not body.vcf_filename. This is the consequence of the alias at ②. Using body.vcf_filename here would be correct in practice (since a filename with / or .. would have been rejected at ③), but it would be semantically wrong — the convention is clear: after the alias is created, only the alias may be used.
⑧
Manifest key derivation. _VCF_RE.sub(".manifest.json", vcf_key) replaces the VCF extension in the full key string, not just the filename. So runs/2024-11-05/sample.vcf.gz becomes runs/2024-11-05/sample.manifest.json. Because vcf_key was constructed from safe_filename (already validated to end with .vcf or .vcf.gz), the substitution is guaranteed to match exactly once.
⑨
S3 client created per request. boto3.client("s3") is not cached globally — a new client is created on each call. This is intentional: in a Lambda context, boto3 clients are lightweight and may need refreshed credentials from the instance metadata service. For long-running ECS tasks, caching would be a minor optimisation, but correctness comes first.
⑩
Presigned PUT URL for VCF. "put_object" is the S3 API operation name. The URL will grant the bearer permission to PUT exactly the object at Key in Bucket. The bearer needs no AWS credentials. After ExpiresIn=3600 seconds, the URL becomes invalid and S3 will reject it with a 403.
⑪
Presigned PUT URL for manifest. A second signed URL is generated for the companion .manifest.json file. The Lambda ingest trigger and the manual ingest route both expect VCF and manifest to co-exist in S3 — providing both URLs in one response is essential so the client can upload both files before triggering ingest.
⑫
Return both keys alongside the URLs. The keys are returned even though the client could theoretically extract them from the URL. Returning them explicitly decouples the client from URL structure and makes the subsequent POST /api/ingest call straightforward: the client passes vcf_key directly as vcf_s3_key.

17 manual_ingest — _do closure & exception handling

Selected because the _do closure and exception chain are the two patterns a reviewer is most likely to question.

manual_ingest · _do closure ingest.py · lines 36–73 · POST /api/ingest 
@router.post("/ingest")
async def manual_ingest(body: IngestRequest) -> dict:
    if not _VCF_RE.search(body.vcf_s3_key):              # ①
        raise HTTPException(status_code=400, ...)

    bucket = os.environ.get("VCF_BUCKET_NAME")
    if not bucket:
        raise HTTPException(status_code=500, ...)      # ②

    s3 = boto3.client("s3", region_name=region)
    manifest_key = _manifest_key(body.vcf_s3_key)        # ③

    def _do(conn):                                        # ④
        sample_id = ingest_sample(                        # ⑤
            body.vcf_s3_key, manifest_key, bucket, s3, conn
        )
        with conn.cursor() as c:                         # ⑥
            c.execute(
                "INSERT INTO audit_log (...) VALUES (%s,'ingest','sample',%s,NULL,NULL)",
                (body.user_id, sample_id),
            )
        return sample_id                                  # ⑦

    try:
        sample_id = await asyncio.to_thread(             # ⑧
            db.run_in_transaction, _do
        )
        return {"sample_id": sample_id}
    except DuplicateSubmissionError as exc:              # ⑨
        raise HTTPException(409, ...) from exc
    except psycopg2.errors.UniqueViolation as exc:       # ⑩
        raise HTTPException(409, ...) from exc
    except ValueError as exc:                             # ⑪
        raise HTTPException(400, detail=str(exc)) from exc
①
Route-level key guard. Validates the S3 key before any network call. Without this, a key like runs/2024/sample.bam would pass to _manifest_key(), which would return the input unchanged (no regex match), producing a manifest key identical to the VCF key — a silent and confusing error deep in ingest_sample.
②
Bucket guard after key check. Input validation (①) runs first. A request with a non-VCF key always returns 400, not 500 — the server configuration problem is not visible to a client that also sent an invalid request.
③
_manifest_key called after guard ①. This is only safe because guard ① has already confirmed the key ends with .vcf or .vcf.gz. See Part 3 for why this ordering is important.
④
_do closure captures outer scope. _do is an inner function. It captures body, manifest_key, bucket, and s3 from the enclosing manual_ingest scope automatically. No arguments need to be passed explicitly — the closure mechanism handles it. The only argument _do receives is conn, supplied by run_in_transaction.
⑤
ingest_sample owns the heavy work. This function (from PR 5) downloads both S3 files to a temp directory, validates the manifest against the JSON schema, parses the FHIR bundle, checks idempotency, parses the VCF with cyvcf2, and writes all DB rows — all using the supplied conn. It does not commit; that happens in with_transaction after _do returns.
⑥
Audit INSERT in the same transaction. The cursor is opened on the same conn connection that ingest_sample used. All SQL statements on the same connection share the same transaction. If ingest_sample inserted 200 variant rows and then the audit INSERT failed, with_transaction would roll back all 201 writes atomically.
⑦
Return value propagated. run_in_transaction(fn) returns whatever fn(conn) returns. _do returns sample_id, which surfaces as the return value of await asyncio.to_thread(db.run_in_transaction, _do).
⑧
asyncio.to_thread offloads blocking I/O. db.run_in_transaction (and ingest_sample inside it) make synchronous network calls to S3 and synchronous DB calls via psycopg2. Running them on a thread prevents the event loop from stalling. The await keyword suspends manual_ingest until the thread finishes, then resumes with the return value.
⑨
DuplicateSubmissionError → 409. ingest_sample calls an idempotency check early in its flow. If the same VCF has been ingested before (exact or near-duplicate), it raises this custom exception. raise ... from exc sets exc.__cause__ on the new HTTPException, which means the original stack trace is preserved in logs even though a different exception is raised to FastAPI.
⑩
UniqueViolation → 409 (TOCTOU race). There is a time window between the idempotency check (SELECT) and the INSERT where a concurrent request could slip through and create the same row first. The second request then hits a PostgreSQL UNIQUE constraint violation. Mapping this to 409 (not 500) ensures the client sees a retryable conflict, not an internal error.
⑪
ValueError → 400. ingest_sample raises ValueError for bad manifest JSON, missing required fields, or unsupported VCF format. The detail message from the original exception is forwarded to the client — it is safe to expose because it comes from the validation layer, not from internal infrastructure.

18 update_workflow — optimistic locking in full

Selected because the two-phase read-then-conditional-update pattern is the subtlest piece of logic in the PR, and the sentinel exception pattern is worth examining closely.

update_workflow workflow.py · lines 41–85 · PUT /api/workflow/{sample_id} 
@router.put("/{sample_id}")
async def update_workflow(sample_id: int, body: WorkflowUpdateRequest) -> dict:
    rows = await asyncio.to_thread(                     # ①
        db.query,
        "SELECT status FROM workflow WHERE sample_id = %s",
        (sample_id,),
    )
    if not rows:                                          # ②
        raise HTTPException(status_code=404, ...)

    current: str = rows[0]["status"]                    # ③
    if body.status not in VALID_TRANSITIONS.get(current, []):  # ④
        raise HTTPException(status_code=422, detail=f"Invalid transition: {current} → {body.status}")

    def _do(conn) -> None:
        with conn.cursor() as c:
            c.execute(                                    # ⑤
                "UPDATE workflow SET status=%s, updated_at=NOW(), updated_by=%s "
                "WHERE sample_id=%s AND status=%s",
                (body.status, body.user_id, sample_id, current),
            )
            if c.rowcount == 0:                          # ⑥
                raise _ConcurrentModification()
            c.execute(                                    # ⑦
                "INSERT INTO audit_log (...) VALUES (%s,%s,%s,%s,%s,%s)",
                (body.user_id, "update_workflow", "workflow",
                 sample_id, json.dumps({"status": current}),
                 json.dumps({"status": body.status})),
            )

    try:
        await asyncio.to_thread(db.run_in_transaction, _do)  # ⑧
    except _ConcurrentModification:                       # ⑨
        raise HTTPException(status_code=409, detail="Concurrent modification...")
    return {"sample_id": sample_id, "status": body.status}
①
Read current status outside the transaction. db.query is a read-only SELECT that does not hold a row lock. This is intentional — holding a lock here would block concurrent readers for the duration of the entire request handling. The tradeoff is that a concurrent writer could change the status between this read and the UPDATE (which is why the optimistic lock at ⑤–⑥ exists).
②
404 for unknown sample. An empty result means the sample ID does not exist in the workflow table. This is a client error (wrong ID), not a server error — hence 404 not 500.
③
current is captured by closure. current is assigned here in the outer function scope. It is later referenced inside _do (lines ⑤ and ⑦) via Python's closure mechanism — _do captures the variable by reference at definition time. Since current is never reassigned after this line, the closure sees the value read at ①.
④
State machine check before opening a transaction. The transition validity check runs synchronously in the event loop, before any DB write is attempted. This avoids opening a transaction for a request that will definitely fail. VALID_TRANSITIONS.get(current, []) handles the edge case where current is an unrecognised status by returning an empty list (all transitions invalid) rather than raising KeyError.
⑤
Optimistic lock: AND status=%s in WHERE clause. The UPDATE will only affect a row if sample_id matches AND the current status still matches what was read at ①. If another request changed the status between ① and this UPDATE, the WHERE clause will not match any row, and the UPDATE will be a no-op. This is the "optimistic" part — we do not prevent the race; we detect it after the fact.
⑥
rowcount == 0 means the race was lost. psycopg2 sets cursor.rowcount to the number of rows affected by the most recent DML statement. Zero means the WHERE clause matched nothing. The only way this happens (given we already verified the row exists at ②) is that the status changed between ① and ⑤. _ConcurrentModification is raised to signal this — it is a private exception class, not HTTPException, to keep the DB callback layer-clean.
⑦
Audit INSERT only after successful UPDATE. The audit log INSERT runs only if the rowcount check at ⑥ passes. If the audit INSERT were placed before the rowcount check, it would be rolled back by the _ConcurrentModification exception anyway (since the whole transaction rolls back), but placing it after makes the intention explicit: we audit only confirmed changes.
⑧
_do is passed as a callable, not called. asyncio.to_thread(db.run_in_transaction, _do) — _do is not invoked here; it is passed as an argument. run_in_transaction calls _do(conn) on the background thread after opening a connection. A common mistake is accidentally writing asyncio.to_thread(db.run_in_transaction(_do)), which would call _do before the thread starts.
⑨
_ConcurrentModification is caught here, not inside _do. The exception propagates out of _do, through run_in_transaction (which rolls back the transaction and re-raises), through asyncio.to_thread (which re-raises on the event loop), and is caught here. At this point we are back in FastAPI's context and it is appropriate to raise HTTPException.

19 submit_classification — the _do transaction body

Selected because the _do closure performs four distinct SQL operations and the ordering and dependency between them is non-obvious.

submit_classification · _do classification.py · lines 100–175 · PUT /api/variants/{id}/classification 
# Before _do — runs in the event loop (async, non-blocking)
variant_rows = await asyncio.to_thread(db.query,         # ①
    "SELECT id, case_type, gene FROM variants WHERE id = %s", (variant_id,))
if not variant_rows:
    raise HTTPException(status_code=404, detail="Variant not found")

result = classify(                                         # ②
    _build_criteria(body.criteria),
    body.framework,
    _build_rules(body.combination_rules),
)
framework_version = get_framework_version(body.framework)  # ③

def _do(conn) -> int:
    with conn.cursor() as c:
        c.execute(                                         # ④
            "UPDATE variant_classification SET deleted_at=NOW() "
            "WHERE variant_id=%s AND deleted_at IS NULL",
            (variant_id,),
        )
        c.execute(                                         # ⑤
            "INSERT INTO variant_classification "
            "(variant_id, framework, framework_version, score, "
            " classification, locked_at, locked_by) "
            "VALUES (%s,%s,%s,%s,%s,NOW(),%s) RETURNING id",
            (variant_id, body.framework, framework_version,
             result.score, result.classification, body.locked_by),
        )
        classification_id: int = c.fetchone()[0]           # ⑥

        for crit in body.criteria:                         # ⑦
            c.execute(
                "INSERT INTO classification_criterion (...) VALUES (...)",
                (..., psycopg2.extras.Json(crit.evidence_links), ...),  # ⑧
            )

        c.execute(                                         # ⑨
            "INSERT INTO audit_log (...) VALUES (%s,'classify','classification',%s,NULL,%s)",
            (body.user_id, classification_id,
             json.dumps({"score": result.score,
                          "classification": result.classification,
                          "framework": body.framework})),
        )
    return classification_id                               # ⑩

classification_id = await asyncio.to_thread(db.run_in_transaction, _do)
①
Variant existence check before the transaction. The SELECT runs outside _do, before any transaction is opened. If the variant does not exist, we return 404 immediately without touching the DB write path. Checking inside _do would work but would acquire a connection from the pool unnecessarily for every 404 request.
②
classify() runs before the transaction. The classification engine is a pure function — no I/O, no side effects. It is called synchronously in the event loop before asyncio.to_thread. If the engine raises (e.g. unrecognised criterion code), the transaction never opens. Separating scoring from persistence also means the score-only endpoint (POST /classify) and this endpoint share the exact same engine call.
③
framework_version resolved before _do. get_framework_version() maps "acgs_snv" to "ACGS 2024 Best Practice Guidelines" etc. It is called here (outside _do) so the value is available as a closure variable. The framework_version column is NOT NULL in the schema — if this call returned None (it does not, but defensively), the INSERT at ⑤ would raise a constraint violation.
④
Soft-delete existing active classification. WHERE deleted_at IS NULL targets only the current active record. If there is no active classification (first submission for this variant), the UPDATE affects zero rows — which is fine, not an error. This must happen before ⑤ so there is never more than one active classification per variant at any point in the transaction.
⑤
INSERT with RETURNING id. PostgreSQL's RETURNING id clause returns the auto-generated primary key in the result set of the INSERT statement — as if it were a SELECT. Without RETURNING, you would need a separate SELECT lastval() or SELECT currval('seq') call, which is less reliable in concurrent environments.
⑥
fetchone()[0] extracts the returned ID. After an INSERT with RETURNING id, psycopg2 makes the result available via the cursor's standard fetch methods. fetchone() returns the single result row as a tuple; [0] extracts the first (and only) column value. This ID is then used in ⑦ and ⑨ to link criteria and the audit entry to the correct classification record.
⑦
One INSERT per criterion. Each criterion in body.criteria gets its own row in classification_criterion. The loop runs synchronously inside _do on the background thread — all N INSERTs share the same cursor and transaction. If any INSERT fails (e.g. a constraint violation), all previous criterion INSERTs and the classification INSERT at ⑤ are rolled back.
⑧
psycopg2.extras.Json() for the JSONB column. crit.evidence_links is a Python list[str]. Without the Json() wrapper, psycopg2 would attempt to bind it as a PostgreSQL ARRAY type, which is incompatible with a JSONB column. Json() serialises the list to a JSON string, which PostgreSQL accepts and stores as JSONB.
⑨
Audit log records the scoring outcome, not just the action. The new_value JSON includes score, classification, and framework — not just the fact that a classification was submitted. This makes the audit trail self-contained: a reader can reconstruct what was classified and how, without joining to the variant_classification table.
⑩
Return value propagated all the way to the HTTP response. _do returns classification_id → run_in_transaction returns it → asyncio.to_thread resolves to it → assigned to classification_id in the outer handler → included in the JSON response body. This chain is the mechanism by which a value created inside a background thread ends up in the HTTP response.
