07 Controlled components

The controlled component pattern

React fundamental · used throughout CriterionRow and ClassificationPanel

In React, a controlled component is one where the displayed value is always driven by state (or props), and every user interaction that changes the value goes through a state setter or callback before the display updates. The component never holds a "hidden copy" of its truth — what you see is always what the state says.

The opposite is an uncontrolled component, where the DOM element manages its own value (like a regular HTML <input> with no React wiring). Uncontrolled inputs are harder to validate, reset, or pre-populate from server data.

Minimal example

// Uncontrolled — React doesn't see the value until submit
function UncontrolledInput() {
  const ref = useRef(null);
  return <input ref={ref} />;  // DOM owns the value
}

// Controlled — React always knows the value
function ControlledInput() {
  const [value, setValue] = useState("");
  return (
    <input
      value={value}                        // driven by state
      onChange={(e) => setValue(e.target.value)}  // state updated on change
    />
  );
}
In CriterionRow: The checkbox (checked={crit.applied}), strength selector (value={crit.strength}), notes textarea (value={crit.notes}), and link input (value={pendingLink}) are all controlled. The checkbox and strength communicate changes up via onChange(); the link input is local state that only becomes a "real" change when the user clicks Add and addLink() validates and calls onChange().
In ClassificationPanel: The framework selector (value={framework}) is controlled by useState. Resetting the panel calls setCriteria(initCriteriaState(defs, [])) which wipes all criteria back to defaults — this works cleanly because every criterion's displayed state is driven by the criteria array, not hidden in each CriterionRow's local DOM.

08 useMemo and useCallback

useMemo — memoised derived values

React hook · used in ClassificationPanel for score, framework defs, combination rules

useMemo tells React: "only recompute this value when these specific dependencies change". Without it, every render would recompute the value from scratch, even if nothing relevant changed.

Minimal example

// Without useMemo: classify() runs on EVERY render
const result = classify(appliedCriteria, framework, rules);

// With useMemo: classify() only runs when deps change
const result = useMemo(
  () => classify(appliedCriteria, framework, rules),
  [appliedCriteria, framework, rules]   // dependency array
);
In ClassificationPanel: Three useMemo calls work together: (1) defs — the criteria definition array for the current framework (only recomputes when framework changes); (2) combinationRules — the rule list from the same JSON (same dep); (3) {score, classification, warnings} — the live classification result, which depends on appliedCriteria, framework, and combinationRules. Because classify() iterates up to 28 criteria per call, memoising it prevents unnecessary re-runs on unrelated state changes (e.g. a save error appearing).

useCallback — stable function identity

React hook · used in ClassificationPanel for updateCriterion

useCallback returns a stable function reference — the same function object across renders, unless its declared dependencies change. Without it, a new function object is created on every render, and any component that receives it as a prop would also re-render unnecessarily.

Minimal example

// Without useCallback: new fn object every render → all children re-render
const handleClick = (id: number) => doSomething(id);

// With useCallback: same fn object unless deps change
const handleClick = useCallback(
  (id: number) => doSomething(id),
  []   // empty array = created once, never recreated
);
In ClassificationPanel: updateCriterion is wrapped in useCallback([], []) (empty deps) because it only calls setCriteria and setFrameworkLocked — both of which are React state setters that are themselves stable references. The result is that all the CriterionRow components receive the same onChange prop reference across every render, preventing cascading re-renders when one criterion changes.

09 useEffect for side-effect cleanup

useEffect — responding to prop changes

React hook · used in CriterionRow to clear local state when applied goes false

useEffect runs a side-effect function after the component renders, whenever its dependency array changes. It is commonly used for timers, event listeners, and data fetching — but it is also useful for synchronising local state with incoming prop changes.

The challenge: CriterionRow owns three local state variables (showNotes, pendingLink, linkError) that are only meaningful when the criterion is applied. If the user unchecks the criterion, these should reset to their initial values. But because the checkbox triggers onChange({applied: false}), which updates the parent's state, which then passes the new crit.applied = false prop back down — this is a prop change, not a user action CriterionRow directly observes.

How it works in CriterionRow

useEffect(() => {
  if (!crit.applied) {
    setShowNotes(false);
    setPendingLink("");
    setLinkError(null);
  }
}, [crit.applied]);  // runs whenever applied changes
Why this matters: Without this effect, if an analyst applies a criterion, opens the notes panel, types a link, changes their mind and unchecks the criterion, then re-checks it — the notes panel would reappear in its previous state, including any partially typed invalid URL. The effect ensures the panel resets cleanly on every unapply, regardless of how the state change arrived (user action, reset from parent, or programmatic update from a test).
Test coverage

The test "clears linkError and pendingLink when notes panel is closed" verifies the toggle-close path (the button's onClick handler). The useEffect handles the prop-change path (crit.applied going false from outside). Both paths are tested: the button path by the test, the prop path implicitly by the "disables all inputs when locked" test which exercises a different applied=true but locked=true prop combination.

10 URL parsing for security

Using the URL constructor to validate protocols

Web security · Invariant 3 — isValidEvidenceLink

Evidence links are displayed in the browser as clickable <a href="..."> tags. If an attacker (or a compromised admin with API access) stores a javascript: URL in the database, clicking that link would execute JavaScript in the user's browser — a stored cross-site scripting (XSS) attack.

The defence is to validate the URL's protocol — only http: and https: are permitted. The browser's built-in URL constructor is the correct tool: it fully parses the URL according to the URL Living Standard, handling edge cases like percent-encoding, Unicode, and whitespace that a simple string prefix check would miss.

Why URL() is better than startsWith("https://")

// String prefix check — bypassable
"javascript:alert(1)".startsWith("https")   // false — but:
"https://x.com\njavascript:alert(1)".startsWith("https")  // true!

// URL constructor — parses correctly
new URL("javascript:alert(1)").protocol   // "javascript:"
new URL("https://x.com").protocol          // "https:"
new URL("not a url")                       // throws TypeError

The complete implementation

export function isValidEvidenceLink(url: string): boolean {
  try {
    const parsed = new URL(url.trim());        // parse — throws on invalid
    return parsed.protocol === "http:"         // whitelist: only these two
        || parsed.protocol === "https:";
  } catch {
    return false;                              // unparseable = rejected
  }
}
Two enforcement points: (1) CriterionRow.addLink() — called when user clicks Add or presses Enter; blocks user-entered javascript: links at input time. (2) ClassificationPanel.initCriteriaState() — filters server-loaded evidence_links through this function before they enter React state. This second enforcement point defends against a scenario where a valid API key holder writes malicious links directly to the database via the API, bypassing the frontend form entirely.
Backend enforcement too: backend/app/routes/classification.py applies a Pydantic field_validator on evidence_links that checks the same rule with a regex (r'^https?://'). This is defence-in-depth: even if the frontend validation were bypassed, the backend would reject the PUT /api/variants/{id}/classification request with a 422.

11 Draft saves vs confirmed saves

locked_by: null vs string — the backend contract

API contract · PUT /api/variants/{id}/classification

The classification PUT endpoint accepts a single request body shape regardless of whether the save is a draft or a confirmation. The distinguishing field is locked_by:

Save typelocked_by valuelocked_at in DBPanel effect
DraftnullNULLPanel stays unlocked; Save draft + Confirm still visible
ConfirmeduserId (non-empty string)NOW()Panel locks; only Reset visible

The panel's save(lock: boolean) function implements this contract directly:

async function save(lock: boolean) {
  const result = await putClassification(variantId, {
    framework,
    user_id: userId,
    locked_by: lock ? userId : null,   // THE key distinction
    criteria: /* ...all criteria... */,
  });
  setClassId(result.classification_id);
  if (lock) setLockedAt(new Date().toISOString()); // only on confirm
}
Backend note

The Python backend uses an f-string to embed the locked_at SQL expression directly: locked_at_sql = "NOW()" if body.locked_by is not None else "NULL". This is safe because the value is a hard-coded string literal chosen by server-side code, never derived from user input. The Pydantic field validator also rejects empty strings, so locked_by: "" returns a 422 — the only valid options are null or a non-empty user ID string.

In ClassificationPanel: The Save draft button calls save(false); Confirm calls save(true). After a draft save, classId is set (so subsequent saves update rather than create) but lockedAt remains null (so the panel stays unlocked). After confirm, lockedAt is set from the client clock (new Date().toISOString()), which immediately hides Save/Confirm and shows Reset. The actual server timestamp is in the database; the client-side timestamp is used only for the "Confirmed DD/MM/YYYY" display.

12 Optimistic UI and error recovery

Non-optimistic async: wait for server before updating state

UI pattern · save() and handleReset()

An optimistic update pattern immediately updates the UI as if the server call succeeded, then rolls back on failure. ClassificationPanel deliberately does not use this — for a clinical classification system, showing a confirmed result before the server has actually confirmed it would be misleading and potentially dangerous.

Instead, both save() and handleReset() follow a pessimistic pattern:

  1. Set saving: true (disables buttons, shows spinner)
  2. Await the API call
  3. Only on success: update the panel state (setClassId, setLockedAt, etc.)
  4. On failure: set saveError — panel stays in its previous state exactly
  5. finally: clear saving regardless
async function handleReset() {
  if (!classId) return;
  setSaving(true);
  setSaveError(null);
  try {
    await apiReset(variantId, classId, userId);
    // Only if the API call succeeded:
    setClassId(null);      setLockedAt(null);
    setFrameworkLocked(false);
    setCriteria(initCriteriaState(defs, []));
    setShowResetConfirm(false);
  } catch (err) {
    setSaveError(err instanceof Error ? err.message : "Reset failed");
    setShowResetConfirm(false); // close confirm; panel stays locked
  } finally {
    setSaving(false);
  }
}
Reset error design choice: On reset failure, setShowResetConfirm(false) is called in the catch block. This closes the "Yes / Cancel" confirmation row, but the panel remains in locked state (Reset button still visible). The error banner explains what happened. The analyst can try again. This avoids a stuck "Yes / Cancel" UI while ensuring the panel doesn't falsely show an unlocked state after a failed reset.

13 Vitest partial mock factory

vi.mock with async importOriginal — keeping real exports

Testing pattern · used in ClassificationPanel.test.tsx

The test file needs to mock putClassification and resetClassification (so the tests don't make real HTTP calls) but must keep the real ApiError class (so new ApiError(409, ...) in the test produces an object that err instanceof Error returns true for in the component).

A plain vi.mock("../lib/api") auto-mocks the entire module — including ApiError, which becomes a mock constructor that does not inherit from Error. The component's catch (err) { err instanceof Error ? err.message : "..." } would then always fall through to the fallback string, breaking the error-display tests.

The solution is a partial mock factory:

vi.mock("../lib/api", async (importOriginal) => {
  const actual = await importOriginal<typeof import("../lib/api")>();
  return {
    ...actual,              // spread real module (includes real ApiError)
    putClassification: vi.fn(),   // replace only these two
    resetClassification: vi.fn(),
  };
});

The factory is declared async and calls importOriginal(), which loads the real module. The result is spread first, then specific functions are overridden with vi.fn(). Everything not listed (ApiError, authHeaders, listPatients, etc.) remains the real implementation.

Why this matters for the error tests: The test "shows error banner when putClassification rejects" does vi.mocked(putClassification).mockRejectedValue(new ApiError(409, "Concurrent modification")). The component catches it and checks err instanceof Error. Because ApiError extends Error and ApiError is the real class (not a mock), the instanceof check succeeds and err.message ("Concurrent modification") reaches the error banner. If ApiError were mocked, the test would pass but for the wrong reason.

14 The criteria JSON structure

Both criteria files follow the same schema. Understanding the shape helps when reading getCriteriaDefs(), initCriteriaState(), and the CriterionRow render logic.

The 28 ACGS SNV criteria are grouped into six evidence categories (functional: 9, segregation: 5, case_evidence: 5, computational: 4, population: 3, other_databases: 2). ClassificationPanel renders them in this fixed order, defined by the EVIDENCE_CATEGORIES constant. The direction field ("pathogenic" / "benign") controls the colour of the criterion code in CriterionRow. The adjustable flag determines whether a strength selector appears; non-adjustable criteria show their fixed strength as italic text.

Pre-computed criteria

Some criteria (e.g. PVS1, BA1, PM2) are marked pre_computable: true. The backend's ingest pipeline runs pre_compute_criteria() to evaluate these automatically from VCF annotations and stores them as pre_computed: true rows in classification_criterion. When initCriteriaState() loads these, the CriterionRow renders a purple "pre-computed value" badge (e.g. "gnomAD AF < 0.001") and marks the state accordingly. The analyst can still override by checking or unchecking the criterion.
