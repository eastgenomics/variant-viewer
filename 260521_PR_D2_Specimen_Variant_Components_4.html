18 fetchVariants — full annotation

The core data-fetching function in VariantTable. Every line is load-bearing — the query string construction, the null guards, the response field names, and the state update sequence all matter.

fetchVariants VariantTable.tsx · lines 124–158 · useCallback-wrapped async fetch 
const fetchVariants = useCallback(async () => {   // ①
  setLoading(true);
  setError(null);                                   // ②
  try {
    const q = new URLSearchParams({                  // ③
      limit: String(PAGE_SIZE),
      offset: String(pageIndex * PAGE_SIZE),          // ④
      sort_by: sortBy,
      sort_dir: sortDir,
    });
    if (filters.gnomad_af_max != null)               // ⑤
      q.set("gnomad_af_max", String(filters.gnomad_af_max));
    if (filters.consequences) q.set("consequences", filters.consequences);
    if (filters.clinvar_exclude) q.set("clinvar_exclude", filters.clinvar_exclude);
    if (geneInput.trim()) q.set("gene", geneInput.trim());  // ⑥

    const resp = await fetch(                        // ⑦
      `/api/samples/${sampleId}/variants?${q}`,
      { headers: authHeaders() }                       // ⑧
    );
    if (!resp.ok) throw new Error(`HTTP ${resp.status}`);  // ⑨
    const json = await resp.json();
    setData(json.items);                               // ⑩
    setTotal(json.total);
  } catch (e) {
    setError(e instanceof Error ? e.message : "Failed to load variants");
  } finally {
    setLoading(false);                               // ⑪
  }
}, [sampleId, pageIndex, filters, geneInput, sortBy, sortDir]);  // ⑫
①
useCallback wrapper. This wraps the async function so its reference only changes when one of the listed dependencies changes. The outer useEffect lists fetchVariants as its sole dependency, so the effect re-runs on each new reference. This is equivalent to listing all six deps directly in the effect, but separates the fetch logic from the effect trigger.
②
Clear previous error. setError(null) runs at the start of every fetch attempt so a stale error message from a previous failed request does not remain visible when a new request is in flight.
③
URLSearchParams constructor. The constructor accepts an object of string key-value pairs. Mandatory params (limit, offset, sort_by, sort_dir) are always present. Optional filter params are conditionally appended below. String() is used to coerce numbers to strings — URLSearchParams does not accept numbers directly.
④
Offset calculation. The backend expects a byte offset into the result set, not a page number. pageIndex * PAGE_SIZE converts: page 0 → offset 0, page 1 → offset 50, page 2 → offset 100, etc. PAGE_SIZE is the module-level constant 50.
⑤
Null guard for gnomad_af_max. Uses != null (loose equality), which is true for both null and undefined. When the user clears the filter input, gnomad_af_max is set to null (see the NaN guard in section 20). Sending gnomad_af_max=null to the backend would fail validation; omitting the param entirely means "no filter", which is the user's intent.
⑥
Gene input trim. geneInput.trim() is evaluated twice — once for the truthiness check and once for the param value. This prevents sending a gene filter of just spaces, which the backend would interpret as a real gene name and return zero results. The backend uses ILIKE %s which would match any gene containing only spaces — an unhelpful result.
⑦
Direct fetch, not api.ts wrapper. VariantTable uses fetch() directly rather than the typed wrappers in api.ts. This is because the request is high-frequency (every filter change triggers it) and the response shape is already typed via the VariantRow[] state variable. The api.ts wrappers are used for mutation calls (workflow update, delete) where consistent error handling and type safety matter more.
⑧
authHeaders() at call time. authHeaders() reads import.meta.env.VITE_API_KEY inside the function body on every call. This ensures the key is read when the request is made, not when the module was first loaded. It is the single read-point for the API key in direct fetch calls (Invariant 2).
⑨
Explicit ok check. fetch() only rejects its promise on network errors (no connection, DNS failure). HTTP 4xx and 5xx responses resolve with resp.ok === false. Without this check, a 404 or 500 response would silently call resp.json() on an error body and potentially set data to an unexpected shape.
⑩
json.items not json.rows. The backend VariantListResponse Pydantic model uses the field name items. Using json.rows or json.data would silently set data to undefined, making TanStack render zero rows with no error — a subtle bug that would look like an empty result set rather than a contract mismatch.
⑪
finally block. setLoading(false) is in finally, not in the try block after the state updates. This guarantees loading is cleared even if the catch block throws an error, and even if setData or setTotal somehow fails. Without finally, a thrown exception in the catch handler would leave the table stuck in a perpetual loading state.
⑫
Dependency array completeness. All six variables from the surrounding component scope that are used inside the function are listed here. Omitting any one would create a stale closure — the function would close over the initial value of that variable and never see updates. ESLint's react-hooks/exhaustive-deps rule would flag any missing entry.

19 handleTransition and the prop-sync useEffect

These two pieces of code in WorkflowControl interact subtly. Understanding both is necessary to understand the full behaviour of the component.

handleTransition + prop-sync useEffect WorkflowControl.tsx · lines 19–36 
const [status, setStatus] = useState(currentStatus);  // ①
const [loading, setLoading] = useState(false);
const [error, setError] = useState<string | null>(null);

useEffect(() => { setStatus(currentStatus); }, [currentStatus]);  // ②

const transitions = TRANSITIONS[status] ?? [];                    // ③

async function handleTransition(newStatus: WorkflowStatus) {
  setLoading(true);
  setError(null);                                               // ④
  try {
    const userId = import.meta.env.VITE_USER_ID ?? "analyst";   // ⑤
    await updateWorkflow(sampleId, newStatus, userId);            // ⑥
    setStatus(newStatus);                                         // ⑦
  } catch (err) {
    setError(err instanceof Error ? err.message : "Update failed");  // ⑧
  } finally {
    setLoading(false);
  }
}
①
Local copy of status. status is local state initialised from the currentStatus prop. React's useState only uses its argument as the initial value — subsequent prop changes do not automatically update local state. This is intentional: local state allows the component to update the UI immediately on a successful transition without waiting for the parent to re-render.
②
Prop sync via useEffect. This effect runs after every render where currentStatus has changed. It bridges the gap between local state and external truth: if the parent page refreshes specimen data from the API and passes a new currentStatus, the local status will be updated to match. Without this, the component would show stale buttons after, for example, a page navigation or background refresh.
③
Deriving buttons from local status. TRANSITIONS[status] is evaluated against the local status variable, not the currentStatus prop. This means after a successful transition (line ⑦), the buttons update immediately — before the parent has re-rendered with the new status. The ?? [] fallback handles unexpected status values gracefully.
④
Clear previous error. Ensures the error from a previous failed attempt does not persist into a new attempt. If omitted, the user might see a stale error message briefly visible while the new request is in flight.
⑤
User ID source. import.meta.env.VITE_USER_ID is a Vite environment variable injected at build time. The ?? "analyst" fallback means the development setup requires no configuration — uploading and transitions just work locally. In production, VITE_USER_ID should be set to a meaningful user identifier. This value is recorded in the backend audit log.
⑥
API call via typed wrapper. updateWorkflow from api.ts calls PUT /api/workflow/{sampleId}. It throws ApiError (which extends Error) on non-2xx responses — including HTTP 422 if the transition is invalid according to the backend's VALID_TRANSITIONS. The TRANSITIONS map on the frontend should prevent 422s from ever being reached, but the error handler catches them if they occur.
⑦
Optimistic UI update. setStatus(newStatus) runs after the API call succeeds. This is not optimistic in the strict sense (it waits for server confirmation) but it does update the UI synchronously in the same event loop tick as the resolution — the user sees the button set change immediately after the request completes, without waiting for a parent re-render.
⑧
instanceof Error guard. JavaScript allows throwing any value, not just Error instances. Checking err instanceof Error before accessing err.message prevents a runtime TypeError if something other than an Error is thrown. ApiError extends Error, so err.message correctly returns the backend detail string (e.g. "Invalid transition: pending → reported").

20 NaN guard — gnomAD AF filter input

A small but important guard that prevents a malformed query string from reaching the backend. Without it, clearing the gnomAD AF input would send gnomad_af_max=NaN to the server, causing a 400 or 422 error that would appear to the user as a broken filter.

gnomAD AF onChange handler VariantTable.tsx · filter bar input · lines ~172–180 
<input
  type="number"
  step="0.001"
  min={0}
  max={1}
  value={filters.gnomad_af_max ?? ""}                   // ①
  onChange={(e) => {
    const val = parseFloat(e.target.value);             // ②
    setFilters((f) => ({
      ...f,
      gnomad_af_max: Number.isNaN(val) ? null : val,   // ③
    }));
    setPageIndex(0);                                    // ④
  }}
/>
①
Controlled value with null coercion. filters.gnomad_af_max ?? "" converts null to an empty string for the input's value attribute. React's controlled input requires a string (or number) — passing null would cause a warning and potentially switch the input to uncontrolled mode. The empty string displays as a blank input, which is the correct visual state when no filter is set.
②
parseFloat on the raw string. e.target.value is always a string from the DOM event, even for type="number" inputs. parseFloat("") returns NaN when the field is empty or cleared. parseFloat("0.01") returns the number 0.01. This is the standard DOM API behaviour.
③
The NaN guard itself. Number.isNaN(val) is used rather than the global isNaN(). The global function coerces its argument: isNaN("hello") is true, but so is isNaN(undefined). Number.isNaN only returns true for the actual IEEE 754 NaN value, making the guard precise. When the field is empty (val === NaN), gnomad_af_max is set to null. In fetchVariants, the null check at line ⑤ then omits the param from the query string entirely.
④
Reset page on filter change. Any filter change resets pageIndex to 0. Without this, the user might be on page 3, apply a tighter filter, and see "Page 3 of 1" — the filter would return fewer results but the page offset would point past the end, yielding an empty result set rather than the first matching page.
Why this matters for the backend

FastAPI's gnomad_af_max: float | None = Query(None, ge=0, le=1) parameter definition means: if the param is present, it must be a valid float between 0 and 1. The string "NaN" is not a valid float — FastAPI would return HTTP 422 Unprocessable Entity. The front end would then show an error message, which would confuse the user who simply cleared the filter field expecting to remove it.

21 DeleteSampleButton — confirming branch

The confirming branch of DeleteSampleButton is where most of the interesting logic lives. It handles two distinct UX paths (high-risk vs normal), inline error state, and the callback chain.

DeleteSampleButton — confirming branch DeleteSampleButton.tsx · lines 20–60 
const isHighRisk =
  workflowStatus === "reported" || workflowStatus === "archived";  // ①

if (confirming) {
  return (
    <span className="flex gap-1 items-center">
      {isHighRisk && (                                               // ②
        <span className="text-xs text-amber-600 mr-1">
          ⚠ This specimen has been {workflowStatus}.
        </span>
      )}
      {!isHighRisk && (                                             // ③
        <span className="text-xs text-gray-700 mr-1">
          Delete <strong>{name}</strong>?
        </span>
      )}
      <button
        className="btn btn-danger text-xs py-0.5 px-2"
        disabled={busy}
        onClick={async () => {
          setBusy(true);
          setDeleteError(null);                                   // ④
          try {
            await deleteSample(id);                               // ⑤
            onDelete?.(id);                                        // ⑥
            setConfirming(false);                                // ⑦
          } catch (e) {
            setDeleteError(e instanceof Error ? e.message : "Delete failed");
          } finally {
            setBusy(false);                                       // ⑧
          }
        }}
      >
        {busy ? "Deleting…" : "Yes, delete"}
      </button>
      <button
        onClick={() => { setConfirming(false); setDeleteError(null); }}  // ⑨
      >Cancel</button>
      {deleteError && (                                             // ⑩
        <span className="text-xs text-red-600 ml-1">{deleteError}</span>
      )}
    </span>
  );
}
①
High-risk classification. reported and archived are the statuses that indicate the specimen has been through clinical review or finalisation. Deleting at this point has audit implications — the deletion will be logged, but the clinical data and variant classifications will be permanently removed. The warning is a UX safeguard, not a server-side block. The backend returns 204 regardless of the sample's status.
②
High-risk: amber warning. When isHighRisk, the confirmation text is replaced by an amber status warning — no specimen name is shown. The amber colour (text-amber-600) and the ⚠ character (Unicode U+26A0) together form a visual signal that this action is more consequential than a normal delete.
③
Normal: specimen name in confirmation. For non-high-risk specimens, the name is shown in bold so the user can verify they are deleting the right specimen. Both ② and ③ use conditional rendering with the && pattern — only one is ever rendered at a time.
④
Clear previous error on re-attempt. The user may see an error (e.g. network timeout), wait, and click "Yes, delete" again. Clearing deleteError at the start of each attempt ensures the previous error message disappears while the new request is in flight.
⑤
API call. deleteSample(id) from api.ts calls DELETE /api/samples/{id}. The backend returns 204 No Content on success. The request() function in api.ts handles 204 correctly — it checks resp.status === 204 before calling resp.json(), so no JSON parse error occurs on an empty body.
⑥
Callback with optional chaining. onDelete?.(id) calls the callback only if it was provided. The ?. optional chaining operator short-circuits to undefined if onDelete is undefined or null. This is safe in all usage contexts: inside SpecimenCard (where onDelete is always provided as the prop relay) and in tests (where it may be omitted).
⑦
Close confirming bar after success. setConfirming(false) is only called on the success path, not in finally. This is deliberate: if the deletion fails, the confirming bar stays open with the error message, so the user can retry or cancel. Closing on failure would hide the error and leave the user wondering whether the deletion happened.
⑧
Re-enable button in finally. setBusy(false) is in finally so the button is always re-enabled after the request completes, whether success or failure. Without this, a failed request would leave the button permanently disabled.
⑨
Cancel clears error. The Cancel button calls both setConfirming(false) and setDeleteError(null). If the user saw an error, clicked Cancel, and then clicked Delete again, they would see a fresh confirming bar with no residual error message. Clearing only confirming would leave deleteError set, causing the error to flash on the next open.
⑩
Inline error display. The error span appears to the right of the Cancel button. It uses ml-1 for a small margin. The error is only rendered when non-null. This is the only place the user sees API errors from the delete operation — there is no toast, modal, or console log.
