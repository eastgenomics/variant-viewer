12 Navbar

components/Navbar.tsx18 lines · 1 export
Navbar lines 1–18 Stateless

Purpose: Renders the top navigation bar that appears on every page of the application.

Inputs

  • No props — renders identically on every page

Output

  • <nav> element with brand link and two navigation links

Key logic: Uses React Router's Link component rather than a plain HTML <a> tag. This is important: Link performs client-side navigation without reloading the page, preserving the SPA experience. A plain <a href="/"> would trigger a full browser navigation, discarding the React application state and causing a server round-trip.

Design decision

Navbar accepts no props and has no state. It is entirely self-contained — there is no "active link" highlighting, user name display, or authentication context. These can be added later without changing the component's interface.

13 WorkflowBadge

components/WorkflowBadge.tsx22 lines · 1 export
WorkflowBadge lines 1–22 Stateless

Purpose: Renders a small coloured pill badge displaying the human-readable label for a workflow status. Matches the backend VALID_TRANSITIONS status values.

Props

  • status: string — one of pending, reviewing, reported, archived (or unknown future value)

Output

  • <span> with CSS class from lookup, e.g. "badge badge-pending"
  • Falls back to the raw status string with neutral grey styling for unknown values

Key logic: Two Record<string, string> tables are defined inside the function body. The classes table maps status → CSS class string; the labels table maps status → display text. Both use ?? fallbacks: unknown statuses render with the raw status value as label and a neutral grey badge style. This makes the component safe against future status additions without requiring a code change.

Minor inconsistency

The lookup tables are declared inside the function body with const, meaning they are re-created on every render. ClassificationBadge uses module-level constants instead (more efficient). For these tiny 4-entry maps the difference is immeasurable, but the module-level pattern is preferred for new code.

14 ClassificationBadge

components/ClassificationBadge.tsx35 lines · 1 export
ClassificationBadge lines 1–35 Stateless

Purpose: Renders a coloured badge for a variant classification result, or an em-dash if the classification is null (no classification assigned yet). Covers both ACGS SNV (Pathogenic through Benign) and SVIG-UK (Oncogenic, Likely_Oncogenic) classifications.

Props

  • classification: string | null — classification string or null

Output

  • null → <span class="text-gray-400 text-xs">—</span>
  • Known value → badge span with matching class, e.g. "badge badge-pathogenic"
  • Unknown value → badge span with neutral grey fallback + raw string as text

Key logic: The null guard is a separate early return — if classification is null, the component immediately returns the em-dash span. This is intentional: it separates "no data" from "unknown data", and it avoids the BADGE_MAP[null] lookup which would return undefined.

Two module-level constants: BADGE_MAP maps the classification string to a CSS class; LABEL_MAP maps it to display text. The underscore in Likely_Pathogenic becomes a space in the label ("Likely Pathogenic") via this table, not via string manipulation — the mapping is explicit and easy to audit.

Design decision — no string manipulation

An alternative implementation would derive the display label by replacing underscores with spaces: classification.replace(/_/g, " "). This would be shorter. The explicit map is preferred because it: (1) allows different display labels for the same stored value if needed in future; (2) makes the set of expected values auditable without reading the backend code; (3) keeps the fallback behaviour visible — unknown values render their raw string, which is visible in tests.

15 PatientHeader

components/PatientHeader.tsx17 lines · 1 export
PatientHeader lines 1–17 Stateless

Purpose: Renders a card header at the top of the patient detail page, showing the patient's lab record number (MRN) as a prominent heading. Intentionally minimal.

Props

  • patient: Pick<PatientDetailResponse, "id" | "lab_number">
  • Narrow type — only id and lab_number accessible

Output

  • White card with <h1> containing patient.lab_number
  • No other patient data rendered

Key logic: The component renders exactly one thing: the lab_number. The Pick<> type constraint on the prop means that even if a developer modifies this component and tries to access patient.name, TypeScript will refuse to compile it. This is Invariant 1 enforced at the type system level.

What was here before (migration 004)

An earlier revision of PatientHeader included a formatYearOfBirth(patient.dob) line that displayed the year of birth below the MRN. After migration 004 dropped the dob column, this call was removed. The prop type was also narrowed to exclude dob from Pick<>. The formatYearOfBirth helper remains in display-utils.ts but is currently unused by any rendered component.

16 DeletePatientButton (inner function)

components/PatientListTable.tsxlines 8–57 (file-private inner function)
DeletePatientButton lines 8–57 · inner function, not exported Interactive (useState)

Purpose: A two-step confirmation button that guards the patient delete action. The first click shows a confirmation row; the second click triggers the API call. Errors are shown inline without closing the confirmation.

Props

  • id: number — patient ID to delete
  • label: string — the MRN, shown in "Delete LAB-001?" prompt
  • onDelete: (id: number) => void — callback called on success

State

  • confirming: boolean — whether confirm row is visible
  • busy: boolean — API call in flight
  • deleteError: string | null — last error message

Key logic: The component uses a conditional early return to switch between two UI states. When confirming is false, only the small "Delete" text button is rendered. When confirming is true, the entire confirmation row is rendered instead.

Inside the confirmation click handler, the sequence is: set busy=true, clear any previous error, call deletePatient(id) (from api.ts), then on success call onDelete(id) and close the confirmation. On error, set deleteError with the message — the confirmation stays open so the user sees what went wrong. The finally block always resets busy to false.

Why an inner function, not a separate file?

DeletePatientButton is defined inside PatientListTable.tsx rather than exported from its own file because it is only used in one place and its API (id, label, onDelete) is tightly coupled to the table's row structure. Exporting it would imply it is reusable — which it is not. The equivalent for samples (DeleteSampleButton) is in PR D2, where it is also used by SpecimenCard, so it warrants its own file.

17 PatientListTable

components/PatientListTable.tsxlines 59–107 (exported default)
PatientListTable lines 59–107 Stateless outer

Purpose: Renders a full HTML table of patients — the main content of the Cases (home) page. Each row shows the MRN, specimen count, latest specimen name, pipeline, workflow status badge, ingested date, a View link, and a Delete action.

Props

  • patients: PatientSummary[] — array of patient summary objects from the API
  • onDelete: (id: number) => void — called when a patient is successfully deleted; parent removes the row from state

Output

  • <div><table> with thead + tbody
  • One <tr> per patient, including WorkflowBadge and DeletePatientButton

Key logic: The outer function itself is stateless — it maps over patients and returns a row for each. All interactivity is delegated to child components: WorkflowBadge handles badge rendering, Link handles navigation, and DeletePatientButton handles the delete interaction.

Three columns deserving attention:

  • Pipeline column — p.pipeline_key?.replace(/_/g, " ") converts dragen_germline to dragen germline for display. The ?. optional chaining means replace is only called if pipeline_key is non-null. The ternary then shows "—" for null.
  • Workflow column — uses a ternary rather than ?? because the fallback (<span class="text-gray-400">—</span>) is JSX, not a string. The ?? operator cannot produce JSX on its right-hand side in this context.
  • Ingested column — new Date(p.latest_ingested_at).toLocaleDateString("en-GB") formats the ISO timestamp as a UK date (DD/MM/YYYY). The "en-GB" locale is explicit and correct for an NHS system.
Invariant 1 check

The <thead> has no NHS number column. The <tbody> renders only p.lab_number as the patient identifier — p.name is never accessed or rendered anywhere in this file. The test suite asserts both: no NHS column header, and the fixture name "Jane Smith" does not appear in the document.

18 Test files

All four test files follow the same structure: import the component, import Vitest utilities, define a test fixture, and assert rendering behaviour using Testing Library queries.

WorkflowBadge.test.tsx — parametric testing with it.each

The test uses it.each with a two-dimensional array to run the same assertion template against all four known statuses in one block. Each row in the array becomes one test case with substituted variables. This avoids four nearly-identical it() blocks. A fifth test checks the graceful fallback for an unknown status string.

ClassificationBadge.test.tsx — seven classifications + null

Same it.each pattern, now with seven rows covering both ACGS SNV and SVIG-UK classifications. The final test checks that classification={null} renders the em-dash character (—) rather than nothing.

PatientHeader.test.tsx — positive and negative assertions

Two tests, deliberately paired: one asserts the MRN is present (getByText("LAB-2026-001")); the other asserts the patient name is not present (queryByText("Jane Smith") returns null). The fixture object contains a real name so the second assertion would catch a regression. The comment // dob removed — migration 004 explains why the fixture lacks a dob field.

PatientListTable.test.tsx — vi.mock and MemoryRouter

This test file introduces two patterns not in the simpler badge tests:

  • vi.mock("../lib/api") — replaces the deletePatient function with a Vitest spy before any test runs. Without this, importing api.ts would trigger the import.meta.env read which may not be available in the test environment, and any test that clicks Delete would make a real HTTP call.
  • MemoryRouter — wraps the component in a router context. PatientListTable uses React Router's Link component, which requires a router ancestor. MemoryRouter is the in-memory version used in tests — no browser URL bar needed.
