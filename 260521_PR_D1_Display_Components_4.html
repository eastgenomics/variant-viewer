19 PatientListTable — the row template

The table body maps over the patients array and renders one <tr> per patient. Several cells use non-obvious patterns.

PatientListTable — tbody row PatientListTable.tsx lines 73–107 
{patients.map((p) => (
  <tr key={p.id} className="hover:bg-gray-50">                           // ①
    <td className="px-4 py-3 font-mono font-medium text-gray-900">
      {p.lab_number}                                                       // ②
    </td>
    <td className="px-4 py-3 text-gray-500">{p.sample_count}</td>
    <td className="px-4 py-3 text-gray-600">
      {p.latest_sample_name ?? "—"}                                         // ③
    </td>
    <td className="px-4 py-3 text-gray-500">
      {p.pipeline_key ? p.pipeline_key.replace(/_/g, " ") : "—"}          // ④
    </td>
    <td className="px-4 py-3">
      {p.latest_workflow_status ? (                                        // ⑤
        <WorkflowBadge status={p.latest_workflow_status} />
      ) : (
        <span className="text-gray-400">—</span>
      )}
    </td>
    <td className="px-4 py-3 text-gray-400 text-xs">
      {p.latest_ingested_at                                                // ⑥
        ? new Date(p.latest_ingested_at).toLocaleDateString("en-GB")
        : "—"}
    </td>
    <td className="px-4 py-3">
      <Link to={`/patients/${p.id}`}                                       // ⑦
            className="text-blue-600 hover:underline text-xs">
        View →
      </Link>
    </td>
    <td className="px-4 py-3">
      <DeletePatientButton                                                 // ⑧
        id={p.id}
        label={p.lab_number}
        onDelete={onDelete}
      />
    </td>
  </tr>
))}
①
key={p.id} — React requires a stable unique key on list items so it can reconcile the virtual DOM efficiently when the array changes (e.g. after a delete). Using p.id (the database primary key) is correct; using array index would cause React to re-render the wrong rows when an item is removed from the middle of the list.
②
Only p.lab_number is rendered as the patient identifier. p.name (the patient's full name) exists on the PatientSummary type but is deliberately never accessed here. This is Invariant 1. The font-mono class renders the MRN in monospace — this visually distinguishes it from prose text, which is conventional for identifiers and codes in clinical systems.
③
?? "—" — nullish coalescing. latest_sample_name is string | null: null when the patient has no ingested specimens yet. The em-dash is the standard display convention for "no data" in this codebase — it is more visible than an empty cell and unambiguous to a clinical reviewer.
④
p.pipeline_key.replace(/_/g, " ") — converts the database identifier dragen_germline to the human-readable label dragen germline for display. The ternary (rather than ??) is used here because the fallback is a string "—", and the transformation must only run when pipeline_key is non-null (calling .replace() on null would throw). Optional chaining p.pipeline_key?.replace(...) would be equally correct but returns undefined which renders as nothing in React, not "—".
⑤
Ternary for JSX fallback. ?? cannot be used here because the fallback is a JSX element, not a string. JSX elements are not null/undefined — they are objects — so ?? <span>—</span> would not work as intended. The ternary condition ? <A /> : <B /> is the correct pattern for JSX conditional rendering.
⑥
toLocaleDateString("en-GB") — formats the ISO datetime string (2026-04-01T12:00:00Z) as a UK date (01/04/2026). The "en-GB" locale is explicit. Without a locale argument, toLocaleDateString() uses the browser's locale — which could produce 4/1/2026 on a machine configured with en-US, ambiguous and potentially confusing in a clinical context.
⑦
React Router Link — not <a href>. Link to="/patients/1" performs client-side navigation: the React app stays mounted, only the URL and displayed components change. A plain <a href="/patients/1"> would trigger a full page reload, losing all React state and causing a round-trip to the server for the HTML shell.
⑧
label={p.lab_number} — MRN in confirmation prompt. DeletePatientButton renders "Delete LAB-2026-001?" in the confirmation row. Passing the MRN as the label (not the name) ensures the confirmation prompt itself does not expose PII. Passing p.name here would violate Invariant 1 even though it is inside the confirmation UI, not visible until the user clicks Delete.

20 DeletePatientButton — the confirmation state machine

The delete button's core logic is the async click handler and its surrounding state transitions. This is the only stateful code in the entire PR.

DeletePatientButton — confirming branch PatientListTable.tsx lines 20–57 
if (confirming) {                                                        // ①
  return (
    <span className="flex gap-1 items-center">
      <span className="text-xs text-gray-700 mr-1">
        Delete <strong>{label}</strong>?                                  // ②
      </span>
      <button
        className="btn btn-danger text-xs py-0.5 px-2"
        disabled={busy}                                                    // ③
        onClick={async () => {
          setBusy(true);                                                    // ④
          setDeleteError(null);
          try {
            await deletePatient(id);                                        // ⑤
            onDelete(id);                                                  // ⑥
            setConfirming(false);                                            // ⑦
          } catch (e) {
            setDeleteError(                                                // ⑧
              e instanceof Error ? e.message : "Delete failed"
            );
          } finally {
            setBusy(false);                                               // ⑨
          }
        }}
      >
        {busy ? "Deleting…" : "Yes, delete"}                            // ⑩
      </button>
      <button
        className="btn btn-secondary text-xs py-0.5 px-2"
        onClick={() => { setConfirming(false); setDeleteError(null); }}  // ⑪
      >
        Cancel
      </button>
      {deleteError && (                                                    // ⑫
        <span className="text-xs text-red-600 ml-1">{deleteError}</span>
      )}
    </span>
  );
}
①
Conditional early return splits the component into two render branches. The function returns early when confirming is true, rendering the confirmation row. The code after the closing } (a single "Delete" button) is only reached when confirming is false. This is idiomatic React: two mutually exclusive render paths via an early return, cleaner than a large inline ternary.
②
{label} is the MRN, not the patient name. The caller passes label={p.lab_number}. This is deliberate — showing "Delete LAB-2026-001?" rather than "Delete Jane Smith?" maintains Invariant 1 even inside the confirmation prompt, which is briefly visible on-screen while the user decides.
③
disabled={busy} prevents double-submission. While the API call is in flight (busy=true), the button is disabled. Without this, a user could click the button multiple times before the first response arrives, triggering duplicate DELETE requests. The browser also visually greys the button, communicating that an action is pending.
④
State updates are batched at the start of the handler. setBusy(true) and setDeleteError(null) are set before the await. React 18 batches these updates into a single re-render, so the button disables and any previous error clears simultaneously. Clearing the previous error on retry is important — if the first attempt failed, the second attempt should start clean.
⑤
await deletePatient(id) — deletePatient is imported from api.ts. It calls DELETE /api/patients/{id} and throws an ApiError on non-2xx responses. The await pauses the handler until the response arrives. If the server returns 404 (patient already deleted) or 500 (server error), the catch branch runs instead.
⑥
onDelete(id) is called only after a successful delete. This callback (provided by PatientsPage) removes the row from the parent's state. Calling it before the API response would cause the row to disappear optimistically — then if the API fails, the row is gone from the UI but still exists in the database. The current implementation only updates the UI after confirmed success.
⑦
setConfirming(false) — close confirmation on success. This is called in the try block (success path only). On failure, this line is never reached — the confirmation stays open so the error message is visible. If setConfirming(false) were in the finally block instead, the confirmation would close even on error, hiding the error message immediately.
⑧
Error normalisation: e instanceof Error ? e.message : "Delete failed". In JavaScript, anything can be thrown — not just Error objects. The instanceof Error guard ensures we only access .message when the thrown value is actually an Error (or subclass). ApiError from api.ts extends Error, so its .message property contains the server's detail string.
⑨
finally { setBusy(false) } — always re-enables the button. The finally block runs whether the try succeeded or the catch ran. This guarantees the button is never left disabled indefinitely, even if the error handling itself throws. Forgetting this is a common bug in async handlers — the button stays greyed out forever after an error.
⑩
Button label changes during the API call. {busy ? "Deleting…" : "Yes, delete"} updates the button text inline while the request is in flight. Combined with disabled={busy}, this gives the user clear feedback that their click was registered and the operation is in progress — no spinner component needed for a short-lived operation.
⑪
Cancel clears both confirming and deleteError. If a previous delete attempt failed and the error is displayed, clicking Cancel both dismisses the confirmation and resets the error. This ensures the next time the user opens the confirmation it starts clean — no stale error message from a previous failed attempt.
⑫
Short-circuit rendering: {deleteError && (...)}. In JSX, false && <span> renders nothing. "some error" && <span> renders the span. This is idiomatic React for conditional rendering of a single element — equivalent to {deleteError ? <span>{deleteError}</span> : null} but shorter. The error renders inline next to the buttons rather than below them, keeping the entire action visible without layout shift.

21 ClassificationBadge — the null guard chain

The four lines of the ClassificationBadge return logic contain two separate fallback paths that are easy to conflate.

ClassificationBadge — full function body ClassificationBadge.tsx lines 23–35 
export default function ClassificationBadge({
  classification,
}: {
  classification: string | null;
}) {
  if (!classification) return                                           // ①
    <span className="text-gray-400 text-xs">—</span>;

  return (
    <span className={BADGE_MAP[classification] ?? "badge bg-gray-100 text-gray-600"}>   // ②
      {LABEL_MAP[classification] ?? classification}                       // ③
    </span>
  );
}
①
Early return for null — separate from "unknown" fallback. if (!classification) return ... handles the case where no classification has been assigned yet (the variant is unclassified). This renders a muted em-dash rather than a badge. It is an early return, not an else branch, keeping the main path unindented. !classification is true for both null and undefined — the prop type says string | null but TypeScript allows passing undefined to optional-like props at call sites.
②
Two separate fallbacks in one expression. BADGE_MAP[classification] ?? "badge bg-gray-100 text-gray-600" resolves to:
— the lookup result if the classification is a known key (e.g. "badge badge-pathogenic")
— the fallback grey class string if the key is absent from BADGE_MAP.
This fallback handles future classification values (e.g. a new SVIG tier) gracefully — they render as a grey badge rather than causing an error.
③
LABEL_MAP[classification] ?? classification — raw value as last resort. If the classification is not in LABEL_MAP (an unknown future value), the raw stored string is displayed verbatim — e.g. "New_Classification". This is better than displaying nothing (which would happen if the fallback were an empty string) and better than crashing. The combination of ② and ③ means unknown classifications always render as a grey badge with the raw string as label.

22 Test fixture and vi.mock pattern

The PatientListTable test introduces two patterns that appear across all component tests in later PRs.

PatientListTable.test.tsx — mock and fixture PatientListTable.test.tsx lines 1–30 
import { render, screen } from "@testing-library/react";
import { describe, it, expect, vi } from "vitest";
import { MemoryRouter } from "react-router-dom";
import PatientListTable from "../components/PatientListTable";
import type { PatientSummary } from "../lib/api";

vi.mock("../lib/api", () => ({ deletePatient: vi.fn() }));           // ①

const patient: PatientSummary = {
  id: 1,
  lab_number: "LAB-2026-001",
  name: "Jane Smith",                                                   // ②
  // dob removed — migration 004                                         // ③
  sample_count: 2,
  latest_sample_id: 10,
  latest_sample_name: "SPECIMEN_A",
  latest_workflow_status: "pending",
  latest_ingested_at: "2026-04-01T12:00:00Z",
  pipeline_key: "dragen_germline",
};

function renderTable() {
  return render(
    <MemoryRouter>                                                         // ④
      <PatientListTable patients={[patient]} onDelete={vi.fn()} />
    </MemoryRouter>
  );
}
①
vi.mock("../lib/api", () => ({ deletePatient: vi.fn() })) — factory-form mock. Vitest replaces the entire api module with the returned object for this test file. The factory form (() => ({...})) is needed rather than the auto-mock form (vi.mock("../lib/api")) because we want precise control: only deletePatient needs to be a spy — the type exports (interfaces) don't need mocking. Without this mock, the test would import the real api.ts which reads import.meta.env.VITE_API_KEY — an environment variable not set in the Vitest jsdom environment.
②
The fixture includes name: "Jane Smith" deliberately. The test then asserts expect(screen.queryByText("Jane Smith")).not.toBeInTheDocument(). If name were absent from the fixture, this assertion would pass trivially even if the component had a bug that tried to render names — because there would be no name to find. By including a real name value in the fixture, the negative assertion is a genuine guard.
③
// dob removed — migration 004 — explains a non-obvious absence. The PatientSummary type no longer includes dob (the field was removed from the backend model when migration 004 dropped the database column). Someone reading the fixture later might wonder why there is no dob field — the comment provides the answer and links to the migration for investigation.
④
MemoryRouter — required because the component uses Link. React Router's Link component reads routing context from a React context provider. Without a router ancestor, rendering Link throws a runtime error: "useHref() may be used only in the context of a <Router> component." MemoryRouter provides that context using an in-memory history object — no browser URL bar, no navigation side effects, safe for unit tests. The same wrapper pattern is used in all component tests that involve navigation links.
