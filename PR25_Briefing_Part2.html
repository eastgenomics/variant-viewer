08 FastAPI Depends and Security

FastAPI's dependency injection system lets you declare reusable logic that must run (and succeed) before a route handler is called. You declare a dependency by passing it to Depends() either in the function signature or in the router's dependencies list.

Plain English

Think of Depends as a gatekeeper that FastAPI calls for you, automatically, before your route function. If the gatekeeper raises an HTTPException, FastAPI returns that response immediately — your route handler never runs. If the gatekeeper returns normally, its return value can be injected into your route handler as a parameter.

Minimal example

from fastapi import Depends, FastAPI, HTTPException

def verify_token(token: str) -> str:
    if token != "secret":
        raise HTTPException(status_code=401)
    return token              # injected into route as `tok`

app = FastAPI()

# Method 1: inject into the handler function
@app.get("/items")
async def list_items(tok: str = Depends(verify_token)):
    ...

# Method 2: attach to the router (protects ALL routes in the router)
from fastapi import APIRouter
router = APIRouter(dependencies=[Depends(verify_token)])

In this file

Where it appears

Every route module except health.py creates its router with dependencies=[Depends(require_api_key)]. This single declaration protects every @router.get() in that module without repeating the check on each function. Security() (a specialised variant of Depends) is used inside require_api_key itself to extract the X-API-Key header value — it behaves identically to Depends but also adds the key to FastAPI's OpenAPI security schema.

APIKeyHeader(name="X-API-Key", auto_error=False) is a pre-built FastAPI dependency that reads the named header and returns its value (or None if absent). auto_error=False means it returns None rather than raising a 403 when the header is missing — the custom require_api_key function then raises a 401 instead, which is the correct status code for missing authentication.

09 asyncio.to_thread

FastAPI is an async framework. Its route handlers are declared with async def, which means they run on Python's event loop. The event loop can only do one thing at a time on a single OS thread — but it can interleave coroutines (async functions) that yield control while waiting for I/O. The problem is that psycopg2 is synchronous: calling cursor.execute() blocks the OS thread until the database responds.

The problem without to_thread

# BAD — this blocks the event loop for ~5 ms per query
@app.get("/patients")
async def list_patients():
    rows = db.query("SELECT * FROM patients")  # synchronous call!
    # While this line runs, FastAPI cannot handle ANY other request.
    return rows

The fix with to_thread

# GOOD — the DB call runs in a thread-pool worker
import asyncio

@app.get("/patients")
async def list_patients():
    rows = await asyncio.to_thread(db.query, "SELECT * FROM patients")
    # `await` suspends this coroutine; the event loop is free to
    # handle other requests while the DB call runs in a worker thread.
    return rows

asyncio.to_thread(fn, *args) schedules fn(*args) on Python's default ThreadPoolExecutor, then returns a coroutine that resolves to the function's return value. The await suspends the current coroutine (releases the event loop) until the thread finishes.

In this file

Every db.query() call and every db.run_in_transaction() call in the route handlers is wrapped in await asyncio.to_thread(...). This is mandatory — calling psycopg2 directly from an async def handler would block the event loop and serialise all requests to the backend.

Thread safety note: db.query uses ThreadedConnectionPool, which uses a threading.Lock internally to protect getconn()/putconn(). Multiple to_thread workers can call db.query concurrently without data corruption.

10 psycopg2 connection pool

Opening a PostgreSQL connection is expensive — it involves a TCP handshake, TLS negotiation, and PostgreSQL's own authentication round-trips, adding ~20–100 ms per connection. A connection pool pre-opens a set of connections at startup and reuses them across requests.

How it works

import psycopg2.pool

# Created once at module load (lazily, on first query).
pool = psycopg2.pool.ThreadedConnectionPool(
    minconn=1,   # always keep 1 connection open
    maxconn=10,  # at most 10 concurrent connections
    dsn="postgresql://user:pass@host/db"
)

conn = pool.getconn()    # borrow a connection (blocks if all 10 are in use)
try:
    cursor = conn.cursor()
    cursor.execute("SELECT 1")
finally:
    pool.putconn(conn)   # return connection to the pool

Why ThreadedConnectionPool and not SimpleConnectionPool? Because asyncio.to_thread runs DB calls on real OS threads. Multiple threads will call getconn() concurrently. SimpleConnectionPool has no internal locking and would corrupt its internal state under concurrent access. ThreadedConnectionPool uses a threading.Lock to serialise pool operations.

In this file

The pool is created in _get_pool() (db.py) with minconn=1, maxconn=10. The _get_connection() context manager calls getconn() on enter and putconn() in finally, ensuring connections are always returned even if the query raises. The maxconn=10 value was chosen to give headroom above uvicorn's default ~6 worker threads while staying well within RDS db.t3.micro's ~80-connection limit.

11 @contextmanager

A context manager is the mechanism behind Python's with statement. It guarantees that setup and teardown code always run in pairs, even when exceptions occur. The @contextmanager decorator lets you write a context manager using a generator function rather than a class with __enter__/__exit__ methods.

How it works

from contextlib import contextmanager

@contextmanager
def managed_resource():
    resource = acquire()    # runs on `with` entry   (= __enter__)
    try:
        yield resource      # `with ... as resource:` body runs here
    finally:
        release(resource)   # always runs on exit    (= __exit__)

# Usage:
with managed_resource() as r:
    r.do_something()
# release() has already run here, even if do_something() raised

The generator pauses at yield. The value yielded becomes the as variable in the with block. When the with block finishes (normally or by exception), Python resumes the generator, which runs the finally clause.

In this file

_get_connection() uses @contextmanager to ensure pool.putconn(conn) always runs, even if the caller raises an exception. with_transaction() nests inside _get_connection() and adds commit/rollback logic: it yields the connection, and in its own finally block resets autocommit back to True. The nesting means the connection is always returned to the pool — the transaction cannot "leak" a connection even if it crashes mid-query.

12 Constant-time comparison

Python's == operator on strings is short-circuit: it compares characters left to right and returns False as soon as it finds a mismatch. This means "abc" == "axyz" takes slightly less time than "abc" == "abxyz", because the mismatch at position 1 is detected earlier than the mismatch at position 2.

Why this matters for secrets

An attacker sending thousands of requests with subtly different API keys can measure response times and use them to determine, character by character, what the correct key is — a timing attack. The attack is difficult to execute over the internet due to network jitter, but trivial to execute from within the same data centre or container network.

The fix: secrets.compare_digest

import secrets

# Constant time: always compares all bytes, regardless of where mismatch is.
# Returns True only if both strings are identical.
ok = secrets.compare_digest(provided_key, expected_key)

# Note: both arguments must be str (or both bytes). Mixed types raise TypeError.
# Guard against None before calling:
if not provided_key or not secrets.compare_digest(provided_key, expected_key):
    raise HTTPException(status_code=401, ...)
In this file

require_api_key uses secrets.compare_digest(api_key, expected). The not api_key guard before it short-circuits on None or empty string — this is safe because returning early on absence of a key leaks no information about the key's value. The timing vulnerability only arises when comparing a provided value against the correct one.

13 Pydantic BaseModel

Pydantic is a data validation library. A BaseModel subclass declares the expected fields and their types. When FastAPI sees a return type annotation of a BaseModel subclass on a route handler, it automatically serialises the returned value to JSON, validates field types, and excludes any extra keys.

Minimal example

from pydantic import BaseModel

class PatientSummary(BaseModel):
    id: int
    lab_number: str
    name: str | None      # Optional field — serialises as null in JSON

# Building from a dict (e.g. a DB row):
row = {"id": 1, "lab_number": "LAB-001", "name": "Jane"}
p = PatientSummary(**row)   # unpacks the dict as keyword arguments
print(p.model_dump())       # {'id': 1, 'lab_number': 'LAB-001', 'name': 'Jane'}

# Pydantic validates types at construction time:
PatientSummary(id="not-an-int", lab_number="LAB-001", name=None)
# raises ValidationError — "id must be an integer"
In this file

Every route module defines its own response models (PatientSummary, PatientListResponse, SampleDetailResponse, etc.) as BaseModel subclasses. The response_model= argument on each @router.get() tells FastAPI to use that model for serialisation. DB rows arrive as plain dicts (from db.query); the routes construct Pydantic models from them using ModelClass(**row) or ModelClass(**row, extra_field=value). Pydantic's type coercion handles the conversion — for example, a datetime column returned by psycopg2 as a Python datetime object is serialised to an ISO 8601 string in the JSON response.

Inheritance is used once: PatientDetailResponse extends PatientSummary, adding created_at and samples fields. This avoids duplicating the three shared fields. The same technique is available for any response type that is a superset of a summary type.

14 Lazy singleton pattern

A singleton is an object that is created at most once per process lifetime. The lazy variant delays creation until the first time the object is actually needed, rather than at module import time. This is useful when creating the object has a significant side effect (like a network call to Secrets Manager or opening a database connection pool).

The pattern

# Module-level variable, initially None
_resolved_key: str | None = None

def _get_value() -> str:
    global _resolved_key
    if _resolved_key:              # ① already resolved — return immediately
        return _resolved_key

    _resolved_key = expensive_call()   # ② first call only
    return _resolved_key

The global statement tells Python that the assignment inside the function should write to the module-level variable, not create a new local one. Without global, the assignment _resolved_key = ... would create a local variable that disappears when the function returns.

Thread safety caveat

This pattern has a theoretical race condition: two threads could both see _resolved_key is None and both call expensive_call() concurrently. In practice this is harmless for the API key case — both calls would return the same key and one write would clobber the other with the same value. The pool initialisation in db._get_pool() has the same exposure. For the expected concurrency level (small number of threads, cold start happens once) this is acceptable.

In this file

Both auth._resolved_key and db._pool use this pattern. The test helpers _reset_resolved_key() and _reset_pool() exist precisely because the singleton is module-level: without an explicit reset, one test that resolves the key would contaminate all subsequent tests in the same pytest process.

15 SQL patterns used in the routes

Three SQL patterns recur across the route queries. Understanding them makes the queries in Parts 3 and 4 immediately readable.

Pattern A — Parameterised queries

All queries use psycopg2 parameterised form: %s placeholders with a tuple of values as the second argument to cursor.execute(). The psycopg2 driver escapes the values before substituting them, preventing SQL injection.

# Safe — psycopg2 escapes patient_id before inserting it
cur.execute("SELECT * FROM patients WHERE id = %s", (patient_id,))

# Dynamic WHERE: build the clause as a string, keep values in the tuple
where = " WHERE lab_number ILIKE %s OR name ILIKE %s"
params = (f"%{search}%", f"%{search}%")
cur.execute("SELECT id, lab_number FROM patients" + where, params)

Pattern B — LEFT JOIN with soft-delete filter

The variant_classification table uses soft deletes: records are never physically removed; instead a deleted_at timestamp is set when a classification is superseded or reset. The active classification is the one where deleted_at IS NULL.

-- Variant list: join classification only if it is active (not soft-deleted)
SELECT v.id, v.gene, vc.classification, vc.score
FROM variants v
LEFT JOIN variant_classification vc
       ON vc.variant_id = v.id AND vc.deleted_at IS NULL
WHERE v.sample_id = %s

A LEFT JOIN means variants without any classification are still returned — they appear with NULL values for vc.* columns. An INNER JOIN would silently drop unclassified variants from the list, which is incorrect behaviour for a clinical review tool.

Pattern C — CASE expression for chromosomal order

Chromosomes stored as text strings sort lexicographically (1, 10, 11, ..., 2, 20, ...), not in the clinical order (1, 2, ..., 22, X, Y, MT). A SQL CASE expression maps chromosome names to sort integers without requiring a schema change.

ORDER BY
    CASE v.chrom
        WHEN 'X'  THEN 23
        WHEN 'Y'  THEN 24
        WHEN 'MT' THEN 25
        WHEN 'M'  THEN 25
        ELSE v.chrom::integer  -- cast '1'–'22' to integers
    END,
    v.pos
Known assumption

The ELSE v.chrom::integer cast assumes chromosomes are stored as bare numbers ('1'–'22'), not with the chr prefix ('chr1'–'chr22'). DRAGEN pipelines produce the chr prefix by default. The VCF ingest pipeline strips it during parsing, but this needs confirming against a real lab VCF before the endpoint is used in production.
