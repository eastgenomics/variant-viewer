07 TanStack Table

TanStack Table (formerly React Table)

Headless table state manager — brings structure, not HTML

Most UI frameworks give you a pre-built <Table> component that renders HTML and manages its own state. TanStack Table does the opposite: it is headless. You give it your data and column definitions; it gives you back a model (a plain JavaScript object) that describes what to render. You write the HTML yourself.

The key concept is the split between column definitions (declared once, outside the component) and the table instance (created inside the component with useReactTable). Column definitions tell the library what data to show and how to render each cell. The instance ties those definitions to the actual data array and exposes methods like getHeaderGroups() and getRowModel() to drive the render.

// 1. Declare columns once, outside the component (no re-creation on render)
const col = createColumnHelper<VariantRow>();
const COLUMNS = [
  col.accessor("gene", {
    header: "Gene",
    cell: (i) => <span>{i.getValue() ?? "—"}</span>,
  }),
  // ...more columns
];

// 2. Create the table instance inside the component
const table = useReactTable({
  data,          // VariantRow[] — changes when fetch completes
  columns: COLUMNS,
  getCoreRowModel: getCoreRowModel(),
  manualPagination: true,   // we manage page state ourselves
  pageCount,              // total pages, computed from server total
});

// 3. Render using the instance's iterators
table.getHeaderGroups().map(hg =>
  hg.headers.map(header =>
    <th>{flexRender(header.column.columnDef.header, header.getContext())}</th>
  )
);
table.getRowModel().rows.map(row =>
  row.getVisibleCells().map(cell =>
    <td>{flexRender(cell.column.columnDef.cell, cell.getContext())}</td>
  )
);

flexRender is a helper that can accept either a React component or a plain string as the cell renderer — it handles both cases transparently. getContext() provides the cell's value, row data, and column metadata to the renderer function.

The manualPagination: true flag is critical: it tells TanStack not to slice the data array itself. The component manages page state (pageIndex) and fetches the correct page from the server. pageCount (the total number of pages) is computed from the server-returned total count and the page size constant.

In VariantTable.tsx COLUMNS is declared at module level (lines 19–98) so it is created once when the file is imported, not on every component render. The table instance is created at line 161 inside the component, where it can react to the data state variable changing after each fetch.

08 The useCallback + useEffect fetch pattern

useCallback + useEffect for data fetching

Making a fetch re-run when its dependencies change — correctly

React's useEffect runs a function after a render, and re-runs it when items in its dependency array change. The naive pattern is to put the fetch directly inside useEffect:

// Naive — the async function is re-created on every render
useEffect(() => {
  async function doFetch() { /* ... */ }
  doFetch();
}, [sampleId, pageIndex, filters]);

This works, but there is a subtlety: the inline async function is a new object on every render, which is fine here because it is only used inside the effect. The pattern used in VariantTable is slightly different — it separates the fetch logic into a useCallback-wrapped function and then depends on that function reference in the effect:

// Pattern used in VariantTable
const fetchVariants = useCallback(async () => {
  // fetch logic here
}, [sampleId, pageIndex, filters, geneInput, sortBy, sortDir]);
// fetchVariants is a stable reference — only changes when a dep changes

useEffect(() => { fetchVariants(); }, [fetchVariants]);
// effect re-runs only when fetchVariants reference changes
// which only happens when one of its deps changes — same net result

The result is identical in behaviour but offers a benefit: fetchVariants can be called explicitly (e.g. for a manual refresh button) without needing to duplicate the dependency list. It also makes the effect's intent clearer — "run fetchVariants whenever it becomes a new function."

Stale closure risk

If a variable used inside fetchVariants is not listed in the useCallback dependency array, the function will close over its initial value and never see updates — a "stale closure". Every variable used in fetchVariants that comes from component state or props (sampleId, pageIndex, filters, geneInput, sortBy, sortDir) must be in the array.

In VariantTable.tsx fetchVariants is defined at lines 124–158 with a dependency array of all six inputs. The useEffect at line 160 has a single dependency: fetchVariants. Whenever any of the six inputs changes, useCallback produces a new function reference, which causes the effect to re-run the fetch.

09 useMemo and referential stability

useMemo — stable object references across renders

Why object identity matters in React dependency arrays

In JavaScript, two objects with the same content are not equal: {"{}"} === {"{}"} is false. React's useEffect and useCallback dependency arrays use reference equality (===) to decide whether a dependency has changed. This has a surprising consequence:

// Parent component — re-renders when its own state changes
function SpecimenCard({ specimen }) {
  // WITHOUT useMemo: new object on every render
  const defaultFilters = getPipelineDefaults(specimen.pipeline_key);
  // { gnomad_af_max: 0.01, consequences: "...", clinvar_exclude: "..." }
  // This is a NEW object reference every time SpecimenCard renders

  return <VariantTable defaultFilters={defaultFilters} />;
  // VariantTable's useEffect sees defaultFilters change on every parent render
  // → triggers a network fetch even when nothing actually changed
}
// WITH useMemo: same reference unless pipeline_key actually changes
const defaultFilters = useMemo(
  () => getPipelineDefaults(specimen.pipeline_key),
  [specimen.pipeline_key]  // only recompute when this changes
);
// Now VariantTable only refetches when the pipeline actually changes

useMemo caches the return value of the function and only calls the function again when one of the listed dependencies changes. The cached value keeps the same object reference between renders — so React's equality check sees no change and does not re-run downstream effects.

In SpecimenCard.tsx (lines 18–21) defaultFilters is memoized on specimen.pipeline_key. A string primitive is compared by value, so this is stable as long as the pipeline key does not change. VariantTable lists defaultFilters as a dependency of the filter-reset effect (line 121 of VariantTable.tsx), so without the memo, any re-render of SpecimenCard — triggered by, say, a workflow status update — would reset VariantTable's filters and fire a new fetch unnecessarily.

10 The workflow state machine

Finite state machine for workflow status

Why the frontend TRANSITIONS map must match the backend VALID_TRANSITIONS exactly

A finite state machine is a system that can be in exactly one of a fixed set of states, and where the rules for moving between states are explicit. The variant-viewer workflow is such a machine: a sample is always in exactly one of pending, reviewing, reported, or archived.

The backend enforces these transitions in routes/workflow.py with a VALID_TRANSITIONS dict. If the frontend sends a transition not in that dict, the backend returns HTTP 422. The frontend TRANSITIONS map in WorkflowControl.tsx is a copy of this dict — its purpose is purely UX: only render the buttons for transitions that will actually succeed. The backend remains the authoritative guard.

// backend/app/routes/workflow.py
VALID_TRANSITIONS: dict[str, list[str]] = {
    "pending":   ["reviewing", "archived"],
    "reviewing": ["reported",  "archived"],
    "reported":  ["archived"],
    "archived":  [],
}

// frontend/src/components/WorkflowControl.tsx
const TRANSITIONS: Record<string, WorkflowStatus[]> = {
  pending:   ["reviewing", "archived"],
  reviewing: ["reported",  "archived"],
  reported:  ["archived"],
  archived:  [],  // empty → no buttons rendered → terminal state
};

The archived: [] entry is important: TRANSITIONS["archived"] ?? [] produces an empty array, so the transitions.map() call renders zero buttons, giving the user a clear visual indication that the sample is in a terminal state.

In WorkflowControl.tsx (lines 5–10) The TRANSITIONS constant is declared at module level. It is used in the component body: const transitions = TRANSITIONS[status] ?? [];. The ?? [] fallback handles any unexpected status strings from the database gracefully (shows no buttons rather than crashing).

11 Vitest partial mock pattern

vi.mock with importOriginal — keeping real exports, replacing specific ones

Why full auto-mocking breaks class instances like ApiError

When you call vi.mock("../lib/api") with no factory, Vitest replaces every export with an auto-generated mock function. This is convenient for most functions, but breaks any export that is a class: the constructor becomes a no-op jest spy, so new api.ApiError(409, "message") produces an empty object that is not an instance of Error. When WorkflowControl then does err instanceof Error ? err.message : "Update failed", it falls through to the fallback string, and the test asserting for the specific error message fails.

// WRONG: full auto-mock breaks ApiError class
vi.mock("../lib/api");
// api.ApiError is now a mock spy, not a real class
// new api.ApiError(409, "msg") does NOT extend Error

// CORRECT: partial mock — keep real exports, replace only what we need
vi.mock("../lib/api", async (importOriginal) => {
  const actual = await importOriginal<typeof import("../lib/api")>();
  return { ...actual, updateWorkflow: vi.fn() };
  // ApiError is the real class — instanceof Error works
  // updateWorkflow is a spy — vi.mocked() + mockResolvedValue works
});

// Now this works as expected in the test:
vi.mocked(updateWorkflow).mockRejectedValue(
  new ApiError(409, "Concurrent modification")
  // Real ApiError extends Error → err.message === "Concurrent modification"
);

The factory function receives importOriginal — a helper that asynchronously imports the real module. Spreading its result (...actual) then selectively overriding only the functions being tested gives you the best of both worlds: real class behaviour for types you are not testing, and controllable spy behaviour for functions you are.

In WorkflowControl.test.tsx (lines 4–11) The partial mock factory keeps ApiError real and replaces only updateWorkflow. The import { updateWorkflow } from "../lib/api" statement below the mock block imports the spy (Vitest hoisting makes this work even though the import appears after the mock call). Tests then use vi.mocked(updateWorkflow).mockResolvedValue() to control the return value.
Note on SpecimenCard test

The SpecimenCard.test.tsx uses a different strategy: it full-auto-mocks api and stubs global fetch before each test. The fetch stub satisfies VariantTable's useEffect fetch immediately, preventing the React "state update after unmount" warnings (act() warnings) that appeared without it.
