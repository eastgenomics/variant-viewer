16 Authentication layer — middleware/auth.py

app/middleware/auth.py 3 functions · 66 lines · new file
_get_api_key() lines 19–47 Auth

Resolves the expected API key using a lazy singleton. The first call pays the cost of a Secrets Manager round-trip (if configured); every subsequent call returns the cached string immediately.

Inputs

  • None (reads from module globals and environment)

Returns / raises

  • str — the expected API key
  • RuntimeError — if API_KEY_SECRET_ARN secret is missing the api_key field
  • RuntimeError — if neither API_KEY_SECRET_ARN nor API_KEY is set

Resolution order: (1) return cached value if already resolved; (2) if API_KEY_SECRET_ARN is set, call Secrets Manager, parse the JSON, validate the api_key field exists, and cache it; (3) otherwise read API_KEY directly from the environment; (4) raise if neither produced a value.

Design decision

The field-presence check (if "api_key" not in secret) before assignment was added after code review. Without it, a secret created with the wrong field name (e.g. API_KEY instead of api_key) would raise a bare KeyError surfacing as HTTP 500, with a traceback that does not mention the misconfiguration. The explicit RuntimeError names both the ARN and the expected field.

require_api_key() lines 50–60 Auth

FastAPI dependency that validates the X-API-Key header on every protected request. Declared async def so FastAPI can call it as a coroutine, but it does no async work — the actual key resolution is synchronous (and fast after the first call).

Inputs

  • api_key: str | None — injected by APIKeyHeader; None if the header is absent

Returns / raises

  • str — the validated key (injected into the route handler if declared as a parameter)
  • HTTPException(401) — if key is absent or wrong

Uses secrets.compare_digest(api_key, expected) for constant-time comparison (see §12). The not api_key guard before it short-circuits on None or empty string without leaking timing information about the expected key.

_reset_resolved_key() lines 63–66 Test helper

Sets the module-level _resolved_key back to None. Required in tests because the singleton persists across test functions in the same pytest process. Used via monkeypatch.setattr(auth_module, "_resolved_key", None) in fixtures.

17 Database layer additions — lib/db.py

app/lib/db.py 2 additions · run_in_transaction + TypeVar · pre-existing functions unchanged

The five pre-existing functions (_resolve_secrets, _get_pool, _get_connection, query, with_transaction) are documented briefly below for completeness; run_in_transaction is the new addition and receives more detail.

_resolve_secrets() lines 21–42 DB setup

Idempotent (guarded by _secrets_resolved flag): on first call, reads DB credentials from Secrets Manager and writes a PostgreSQL DSN into os.environ["DATABASE_URL"]. On all subsequent calls returns immediately. Called by _get_pool().

Validates that all four required fields (username, password, host, dbname) are present in the secret; raises RuntimeError with the missing field names if any are absent.

_get_pool() lines 45–55 DB setup

Lazy-initialises the ThreadedConnectionPool. Calls _resolve_secrets() first (idempotent), then creates the pool if _pool is None. Adds sslmode="require" when APP_ENV == "production", satisfying the DSPT v8 / UK GDPR requirement for encryption in transit to the RDS instance.

_get_connection() lines 58–64 DB

Context manager: borrows a connection from the pool on entry, returns it in finally. The finally guarantee is important — it ensures connections are always returned even if the caller raises, preventing pool exhaustion.

query() lines 67–78 DB

Executes a SELECT and returns all rows as list[dict]. Constructs the dict by zipping column names (from cur.description) with row tuples. The conn.rollback() in finally closes the implicit transaction that psycopg2 opens automatically when you call execute() — without it, connections returned to the pool would carry an open idle transaction.

with_transaction() lines 81–92 DB

Context manager that wraps a sequence of database operations in an explicit transaction: sets autocommit=False, yields the connection for the caller to use, then calls commit() on success or rollback() on exception, and finally resets autocommit=True.

Gotcha

The autocommit toggle in finally is necessary because the pool reuses connections. A connection returned with autocommit=False would cause the next caller's query() to silently open a new implicit transaction — which would then be left open when the query completes.

run_in_transaction() lines 96–106 DB

Synchronous wrapper that opens a transaction, calls fn(conn), and returns the result. Designed to be passed as the first argument to asyncio.to_thread() so that an entire write transaction — including audit log inserts — runs as a single thread call on one connection.

Inputs

  • fn: Callable[[connection], T] — any callable that accepts a psycopg2 connection and returns a value

Returns

  • T — whatever fn(conn) returns; type preserved via TypeVar("T")
Design decision

The alternative to run_in_transaction would be to call db.with_transaction() directly inside the thread — but context managers cannot be yielded across asyncio.to_thread boundaries cleanly. By wrapping the whole transaction in a synchronous function and passing it to to_thread, the async route handler dispatches one unit of work that completes atomically on a single OS thread.

18 Patient & sample routes

app/routes/patients.py list_patients · get_patient · 4 Pydantic response models
list_patients() lines 45–72 Route — GET /api/patients

Returns a paginated list of patients. Optionally filters by a case-insensitive substring match on lab_number or name.

Query parameters

  • limit: int, 1–200, default 50
  • offset: int, ≥0, default 0
  • search: str | None

Returns

  • PatientListResponse — items, total, limit, offset
  • HTTP 401 — no/wrong key
  • HTTP 422 — limit out of range

Runs two queries: one COUNT(*) for the total (needed for frontend pagination controls), one SELECT with LIMIT/OFFSET for the page. The WHERE clause is constructed conditionally: if search is absent, no WHERE is added; if present, both ILIKE conditions share the same params tuple. The limit ≤ 200 ceiling is enforced by FastAPI's Query(le=200) — any client sending ?limit=999 gets HTTP 422 without the handler running.

get_patient() lines 75–101 Route — GET /api/patients/{patient_id}

Returns patient detail plus the list of all their samples with current workflow status.

Path parameter

  • patient_id: int

Returns

  • PatientDetailResponse (extends PatientSummary)
  • HTTP 404 — patient not found

Two sequential to_thread calls: first fetches the patient row (404 if empty), then fetches all samples via a LEFT JOIN workflow so each sample carries its current workflow status. COALESCE(w.status, 'pending') handles samples that have no workflow row yet — the workflow table row is created lazily on first status transition.

app/routes/samples.py get_sample · list_sample_variants · 3 Pydantic response models
get_sample() lines 56–92 Route — GET /api/samples/{sample_id}

Returns sample detail including patient summary, workflow status, and variant count — all in a single database query using multi-table JOINs.

Path parameter

  • sample_id: int

Returns

  • SampleDetailResponse with nested PatientSummary
  • HTTP 404 — sample not found

The JOIN pattern: samples JOIN patients (inner — every sample has a patient), LEFT JOIN workflow (optional — workflow row may not exist), LEFT JOIN variants COUNT (optional — may have zero variants). The GROUP BY s.id, p.id, w.status is required because COUNT(v.id) is an aggregate function; all non-aggregated columns in the SELECT must appear in the GROUP BY. The flat query result is then manually decomposed: the patient columns (patient_id, lab_number, patient_name) are extracted to build a PatientSummary object, and the rest populate the SampleDetailResponse.

list_sample_variants() lines 95–148 Route — GET /api/samples/{sample_id}/variants

Returns a paginated list of variants for a sample, including a classification summary column from the active (non-deleted) classification record. Variants are sorted in clinical chromosomal order.

Parameters

  • sample_id: int (path)
  • limit: 1–200, default 50
  • offset: ≥0, default 0

Returns

  • VariantListResponse
  • HTTP 404 — sample not found

Three sequential queries: (1) existence check (SELECT 1 FROM samples WHERE id = %s) to 404 on unknown samples rather than silently returning an empty list; (2) COUNT(*) for pagination total; (3) the paginated variant list with LEFT JOIN variant_classification ON deleted_at IS NULL. The chromosomal sort uses a CASE expression (see §15 Pattern C).

19 Variant & config routes

app/routes/variants.py get_variant · 3 Pydantic response models including nested ClassificationDetail
get_variant() lines 53–102 Route — GET /api/variants/{variant_id}

Returns full variant detail with the optional active classification and all its criteria. This is the most structurally complex route: it issues three sequential database queries and assembles a deeply nested response object.

Path parameter

  • variant_id: int

Returns

  • VariantDetailResponse with optional ClassificationDetail (itself containing list[CriterionDetail])
  • HTTP 404 — variant not found

Query 1 — variant + case_type: joins variants to samples to retrieve case_type, which is needed by the classification engine (PR 7 write routes will use it to select the correct framework). Query 2 — active classification: selects from variant_classification WHERE deleted_at IS NULL; returns at most one row per variant (the partial unique index on the table enforces this). Query 3 — criteria: fetched only if query 2 found a classification; otherwise skipped. The conditional dispatch avoids an unnecessary round-trip to the database for unclassified variants.

Design decision — 3 queries vs 1 JOIN

A single SQL query with two LEFT JOINs (on variant_classification and classification_criterion) would produce a row per criterion, requiring application-side aggregation to reconstruct the nested structure. The 3-query approach is simpler to read and maintain, and for the expected data sizes (1–30 criteria per classification) the extra round-trips are negligible.

app/routes/config.py get_criteria · reads JSON files from disk at request time
get_criteria() lines 20–27 Route — GET /api/config/criteria/{framework}

Serves a classification criteria JSON file from disk. No database call — the criteria definitions are static configuration files committed to the repository.

Path parameter

  • framework: str — one of "acgs_snv", "svig"

Returns

  • Parsed JSON dict (FastAPI serialises to response)
  • HTTP 400 — unknown framework name

The _FRAMEWORK_FILES dict maps framework names to Path objects resolved at module import time using Path(__file__).parent.parent.parent / "config". Lookup is a dictionary get — any framework name not in the dict returns 400. The JSON files are read on every request (path.read_text()); file-level caching is not implemented because the files change rarely and the read cost is negligible. The endpoint is consumed by the frontend ClassificationPanel (PR 10) to dynamically build the criteria checkbox list.

app/routes/health.py health · liveness probe · no auth
health() lines 11–13 Route — GET /api/health

Liveness probe for ALB health checks and monitoring. Returns {"status": "ok", "version": "0.2.0"}. No authentication required — the health router is created without dependencies=[Depends(require_api_key)], and it is registered separately from the protected routers in main.py. The version constant _VERSION = "0.2.0" is hardcoded in health.py rather than imported from main.py to avoid a circular import (main.py imports health.py; health.py importing main.py would create a cycle).
