05 Stateless functional components

React stateless functional component

In React, a functional component is simply a JavaScript function that accepts an object of props and returns JSX — a tree of UI elements. When the component is stateless, it means the function has no internal memory: given the same props, it will always return exactly the same output. This makes stateless components trivially testable, composable, and predictable.

// Minimal stateless component — props in, JSX out, nothing else
function Greeting({ name }: { name: string }) {
  return <p>Hello, {name}</p>;
}

// Every call with the same name produces identical HTML
Greeting({ name: "Alice" }) // → <p>Hello, Alice</p>
Greeting({ name: "Alice" }) // → identical, always

The props object is TypeScript-typed inline using an object destructuring pattern: ({ status }: { status: string }). The part after the colon is the type — this is only a compile-time annotation, not runtime overhead.

In this PR: Navbar, WorkflowBadge, ClassificationBadge, and PatientHeader are all purely stateless. PatientListTable is stateless in its outer function — the internal DeletePatientButton is the only place useState is used, and it is an inner component, not a hook on the outer function.

06 Record<string, string> lookup maps

TypeScript Record<string, string>

A Record<K, V> is TypeScript's way of typing a plain JavaScript object used as a key-value map. Record<string, string> means: "an object whose keys are strings and whose values are also strings." It is equivalent to { [key: string]: string } but more readable.

// A Record is just a typed object literal
const colourMap: Record<string, string> = {
  red:   "bg-red-100 text-red-800",
  green: "bg-green-100 text-green-800",
};

// Lookup — returns undefined if key is absent
colourMap["red"]      // → "bg-red-100 text-red-800"
colourMap["purple"]   // → undefined

// ?? fallback handles the missing-key case
colourMap["purple"] ?? "bg-gray-100 text-gray-600"
// → "bg-gray-100 text-gray-600"

The key performance point: the const lookup tables (BADGE_MAP, LABEL_MAP, classes, labels) are defined outside the function body. This means they are allocated once when the module is first imported and reused on every render. If they were defined inside the function, they would be reallocated on every render call — wasteful for tables that never change.

In this PR: WorkflowBadge uses inline const declarations inside the function body — a minor inconsistency with ClassificationBadge which uses module-level BADGE_MAP / LABEL_MAP. Both are functionally correct; the module-level pattern in ClassificationBadge is marginally more efficient because the objects are only created once. For these tiny maps (4–7 entries) the difference is negligible in practice.

07 Tailwind CSS and the badge-* component layer

Tailwind utility classes vs @layer components

Tailwind CSS is a utility-first CSS framework: instead of writing custom CSS rules, you compose class names directly in your HTML/JSX. Each class applies exactly one CSS rule: text-sm sets font-size: 0.875rem, border sets border-width: 1px, and so on.

<!-- Pure Tailwind utilities — readable but verbose -->
<span class="inline-flex items-center px-2 py-0.5 rounded text-xs
             font-medium bg-yellow-100 text-yellow-800">
  Pending
</span>

When the same combination of utility classes is reused many times, Tailwind lets you extract them into a component class using @layer components in your CSS file. The variant-viewer project defines this in frontend/src/index.css:

/* index.css — @layer components */
.badge {
  @apply inline-flex items-center px-2 py-0.5 rounded text-xs font-medium;
}
.badge-pending   { @apply bg-yellow-100 text-yellow-800; }
.badge-reviewing { @apply bg-blue-100 text-blue-800; }
.badge-reported  { @apply bg-green-100 text-green-800; }
.badge-archived  { @apply bg-gray-100 text-gray-600; }

Now instead of repeating all those utility classes in JSX, we just write "badge badge-pending". The badge class provides the shared layout, and badge-pending provides the status-specific colour. This is why WorkflowBadge strings look like two class names — not one.

In this PR: WorkflowBadge maps each status to a "badge badge-{status}" string. ClassificationBadge maps each classification to "badge badge-{hyphenated-classification}". The fallback "badge bg-gray-100 text-gray-600" applies the badge base class plus ad-hoc colour utilities — used when the lookup key is absent (unknown or future status values).

08 TypeScript Pick<T, K>

TypeScript utility type: Pick<T, K>

Pick<T, K> creates a new type that includes only the properties named in K from type T. It is one of TypeScript's built-in utility types — transforms on existing types that are evaluated at compile time with zero runtime cost.

interface PatientDetailResponse {
  id: number;
  lab_number: string;
  name: string | null;    // patient's full name — PII
  created_at: string | null;
  samples: SampleSummary[];
}

// Pick narrows to only the two safe fields
type SafeProps = Pick<PatientDetailResponse, "id" | "lab_number">;
// SafeProps = { id: number; lab_number: string }

// A component accepting SafeProps cannot access patient.name
function Header({ patient }: { patient: SafeProps }) {
  patient.name // ❌ TypeScript error: Property 'name' does not exist
  patient.lab_number // ✓ fine
}

The practical effect: if a developer accidentally writes {patient.name} inside PatientHeader, the TypeScript compiler refuses to compile it. The PII exclusion is enforced before the code ever runs.

In this PR: PatientHeader declares its prop type as Pick<PatientDetailResponse, "id" | "lab_number">. Callers must pass an object with at least id and lab_number — they may also pass a full PatientDetailResponse (TypeScript structural typing allows this), but inside the component only id and lab_number are accessible.

09 Nullish coalescing ??

The ?? operator — fallback for null and undefined

The ?? operator returns the right-hand side if and only if the left-hand side is null or undefined. Unlike the || operator, it does not treat 0, "", or false as falsy — it only triggers for the two "absent value" types in JavaScript.

// ?? vs || — they behave differently for empty strings and zero
null ?? "fallback"       // → "fallback"
undefined ?? "fallback"  // → "fallback"
""    ?? "fallback"       // → ""  (empty string IS a value)
0     ?? "fallback"       // → 0   (zero IS a value)

""    || "fallback"       // → "fallback" (|| treats "" as falsy)

// Used in JSX for optional display fields
{patient.latest_sample_name ?? "—"}  // → "—" only when null/undefined

In JSX, rendering null or undefined produces no output, but the intent is unclear to a reader. Rendering "—" is explicit: the field is absent, and that is intentional. This is why every nullable display field in PatientListTable uses ?? "—".

In this PR: PatientListTable uses ?? "—" for latest_sample_name and pipeline_key, and conditional rendering for latest_workflow_status (which can be null when no workflow row exists) and latest_ingested_at (which is null before any specimen is ingested).

10 Invariant 1 — PII exclusion

The variant-viewer project has five documented invariants — properties that must always hold, regardless of what changes. Invariant 1 states that no React component may render patient.name, nhs_number, or date of birth. Only the MRN (lab_number) is an acceptable patient identifier in the UI.

Why this matters clinically

Diagnostic variant review software is used in NHS laboratories. Patient names and NHS numbers are personally identifiable information (PII) subject to UK GDPR. Displaying them on-screen in a clinical context widens the surface area for accidental disclosure — shoulder-surfing, screenshots, screen recordings, or browser history. The MRN is sufficient to identify the relevant patient record within the laboratory's own systems and carries lower inherent risk if briefly visible.

11 React useState — the two-step confirmation pattern

React useState hook

useState is the standard React hook for adding local mutable state to a functional component. It returns a pair: the current value, and a setter function. When the setter is called, React re-renders the component with the new value. Until the setter is called, the value is frozen — the component does not re-render on its own.

import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0); // initial value = 0

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

The two-step confirmation pattern uses three boolean/string states to guard a destructive action from accidental clicks:

// Three pieces of state for a safe delete button
const [confirming, setConfirming] = useState(false);  // show confirm UI?
const [busy, setBusy]             = useState(false);  // API call in flight?
const [deleteError, setDeleteError] = useState<string | null>(null); // error msg

// State machine: idle → confirming → (busy → success | error)
//  idle:       confirming=false, busy=false, error=null  → shows "Delete" button
//  confirming: confirming=true,  busy=false, error=null  → shows confirm + cancel
//  busy:       confirming=true,  busy=true,  error=null  → shows "Deleting…" disabled
//  error:      confirming=true,  busy=false, error="msg" → shows error inline
//  success:    component unmounted (parent removes row)

The confirming flag controls which UI branch is rendered. If confirming is false, only a "Delete" button appears. Once the user clicks it, confirming becomes true and the UI switches to a confirmation row with the label, a danger button, and a cancel button. This prevents accidental deletion from a single misclick.

The error state (deleteError) renders inline as a small red span next to the buttons, without dismissing the confirmation. This is intentional — the user may wish to retry or cancel after seeing the error, and closing the confirmation automatically would hide the fact that the delete failed.

In this PR: DeletePatientButton inside PatientListTable.tsx implements this exact pattern. The onDelete(id) callback is called only after a successful API response — if the API throws, the catch branch sets deleteError and leaves confirming=true so the user sees the error in context.
