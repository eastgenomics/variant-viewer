06 FastAPI routing & dependency injection

APIRouter + @router.post/put/delete Declaring HTTP endpoints as Python functions

In FastAPI you declare an HTTP endpoint by decorating an async def function. The decorator specifies the HTTP method and the URL path. Path parameters (like {sample_id}) become function arguments automatically. FastAPI reads the type annotations to know what to extract from the URL, the request body, and the headers.

from fastapi import APIRouter
router = APIRouter(prefix="/api/workflow")

# Handles PUT /api/workflow/42
@router.put("/{sample_id}")
async def update_workflow(sample_id: int, body: WorkflowUpdateRequest) -> dict:
    ...  # sample_id comes from the URL; body comes from the JSON request body

An APIRouter is a mini-application that groups related routes. It is registered with the main FastAPI app in main.py via app.include_router(workflow.router). The prefix argument is prepended to every route path — so prefix="/api/workflow" with "/{sample_id}" produces /api/workflow/{sample_id}.

In this fileEach of the four modules declares its own router with a different prefix: /api for upload and ingest, /api/workflow for workflow, and /api/variants for classification. All four routers are registered in app/main.py.
Depends(require_api_key) Dependency injection for authentication

FastAPI's dependency injection system lets you declare "this route needs X before it can run" using Depends(fn). If fn raises an HTTPException, FastAPI returns that response instead of calling the route handler. If it returns a value, that value is available as a function argument.

# Declared at router level — applies to every route in the module
router = APIRouter(
    prefix="/api/workflow",
    dependencies=[Depends(require_api_key)]  # runs before EVERY handler
)

# require_api_key checks X-API-Key header; raises 401 if absent or wrong
async def require_api_key(api_key: str | None = Security(_api_key_header)) -> str:
    expected = _get_api_key()
    if not api_key or not secrets.compare_digest(api_key, expected):
        raise HTTPException(status_code=401, detail="Invalid or missing API key")
    return api_key
In this fileAll four routers declare dependencies=[Depends(require_api_key)] at the router level, not per-route. This guarantees every endpoint in every module requires authentication — it is impossible to forget it on a new route added to these modules.

07 Pydantic request models

class XRequest(BaseModel) Automatic JSON parsing, type coercion, and validation

A Pydantic BaseModel subclass is a schema. When FastAPI receives a JSON body, it passes the parsed JSON to the model's constructor. Pydantic checks that required fields are present, that types are correct (coercing where safe — e.g. "42" to int), and that any constraints are met. If anything fails, FastAPI returns a 422 Unprocessable Entity with a machine-readable error list — no handler code runs.

from pydantic import BaseModel
from typing import Literal

class ClassifyRequest(BaseModel):
    criteria: list[CriterionIn]               # required; must be a JSON array
    framework: Literal["acgs_snv", "svig"]    # only these two values allowed
    combination_rules: list[CombinationRuleIn] = []  # optional; defaults to []

# Sending {"framework": "unknown"} → automatic HTTP 422, no handler code runs
# Sending {"criteria": [...], "framework": "acgs_snv"} → body: ClassifyRequest instance

The Literal[...] type annotation is a built-in Python typing construct that restricts a field to a specific set of values. At runtime, Pydantic enforces this and rejects anything outside the set with a clear error message.

In this fileClassifyRequest and ClassificationSubmitRequest use Literal["acgs_snv", "svig"] for the framework field. This prevents an unknown framework string from silently reaching the classification engine and producing an undefined result.
Nested models (CriterionIn inside ClassifyRequest) Composing complex request schemas

Pydantic models can contain other Pydantic models as field types. The outer model validates the outer structure; each inner model validates its own fields. This is how ClassifyRequest.criteria is declared as list[CriterionIn] — each element of the JSON array must satisfy the CriterionIn schema.

class CriterionIn(BaseModel):
    criterion_code: str           # e.g. "PVS1"
    applied: bool                 # whether the analyst applied this criterion
    strength: str                 # e.g. "very_strong", "supporting"
    notes: str | None = None     # optional free text
    evidence_links: list[str] = [] # URLs; defaults to empty list
    pre_computed: bool = False
    pre_computed_value: str | None = None

# Only criterion_code, applied, strength are passed to the engine's
# AppliedCriterion dataclass — the extra fields go to the DB only.
In this fileThe _build_criteria helper explicitly maps only the three engine-relevant fields (criterion_code, applied, strength) from the Pydantic model to the engine's AppliedCriterion dataclass. The remaining fields (notes, evidence_links, etc.) are written to the DB but do not affect scoring.

08 async/await and asyncio.to_thread

async def + await Why route handlers are declared async

FastAPI runs on an async event loop (via Starlette / uvicorn). When a route handler is declared async def, it can yield control to the event loop while waiting for I/O — the server can then handle another incoming request in the meantime. A regular (synchronous) route handler would block the entire server thread for the duration of every DB query or network call.

# Synchronous — blocks the event loop during the DB call
def bad_route():
    result = db.query("SELECT ...")  # blocks for 50ms → no other requests handled
    return result

# Async — yields during the wait; event loop handles other requests
async def good_route():
    result = await asyncio.to_thread(db.query, "SELECT ...")
    return result
In this fileAll four route handlers are async def. They use await asyncio.to_thread(db.query, ...)) and await asyncio.to_thread(db.run_in_transaction, _do) for every database operation.
asyncio.to_thread(fn, *args) Running synchronous (blocking) code without freezing the event loop

psycopg2 and boto3 are synchronous libraries — their functions block the calling thread until the operation completes. You cannot call them directly inside an async def function without freezing the event loop. asyncio.to_thread(fn, arg1, arg2) is the solution: it runs fn(arg1, arg2) on a background thread from the default executor thread pool, and returns an awaitable that resolves to the function's return value.

# Pattern used throughout this PR:
sample_id = await asyncio.to_thread(db.run_in_transaction, _do)
#                  ^^^^^^^^^^^^^^^^^^^
# Runs db.run_in_transaction(_do) on a background thread.
# The event loop is free to handle other requests while this blocks.
# When the thread finishes, execution resumes here with the return value.
Important caveat

Code inside the _do(conn) function runs on the background thread, not on the event loop. This means you must not use await inside _do, and you must not share mutable state between _do and the event loop without locks. In practice, _do only calls synchronous psycopg2 methods and reads from the request body (via closure) — both are safe.

09 psycopg2 transactions & the _do closure

db.run_in_transaction(_do) Atomicity: all SQL succeeds together or none of it does

A database transaction groups multiple SQL statements into one atomic unit. If any statement raises an exception, all changes are rolled back — the database is left as if none of the statements ran. db.run_in_transaction is a wrapper that opens a connection, calls _do(conn), commits if no exception is raised, or rolls back if one is.

# In app/lib/db.py (PR 2, unchanged):
@contextmanager
def with_transaction():
    with _get_connection() as conn:
        try:
            conn.autocommit = False
            yield conn
            conn.commit()      # ← reached only if no exception
        except Exception:
            conn.rollback()    # ← undo everything on any error
            raise            # ← re-raise so the caller knows what happened

def run_in_transaction(fn):
    with with_transaction() as conn:
        return fn(conn)    # fn is the _do closure from the route handler

In the write routes, the _do(conn) function typically performs two or more SQL statements: an INSERT or UPDATE to the main table, and an INSERT to the audit_log table. Wrapping them in a transaction guarantees the audit record always exists when the main record exists, and vice versa.

In this filemanual_ingest wraps ingest_sample + an audit INSERT. update_workflow wraps a conditional UPDATE + an audit INSERT. submit_classification wraps a soft-delete UPDATE + a classification INSERT + N criterion INSERTs + an audit INSERT. All four must succeed together or none do.
conn.cursor() as a context manager Executing SQL and reading results

A psycopg2 cursor is the object that executes SQL statements. cursor.execute(sql, params) runs a parameterised query — %s placeholders are replaced with the values in the params tuple, with automatic escaping to prevent SQL injection. Always use parameterised queries; never format values directly into the SQL string.

with conn.cursor() as c:
    c.execute(
        "UPDATE workflow SET status=%s WHERE sample_id=%s AND status=%s",
        (body.status, sample_id, current),   # ← params tuple; never f-string
    )
    if c.rowcount == 0:   # ← how many rows the UPDATE touched
        raise _ConcurrentModification()

    c.execute(
        "INSERT INTO audit_log (...) VALUES (%s, %s, %s, %s, %s, %s)",
        (...),
    )
# cursor is closed automatically when the `with` block exits

After an INSERT with RETURNING id, the generated ID is retrieved with c.fetchone()[0]. After an UPDATE, c.rowcount tells you how many rows were changed — used here for optimistic locking.

In this fileAll SQL in the _do closures uses with conn.cursor() as c:. The RETURNING id pattern appears in submit_classification and reset_classification to get the auto-generated primary key of the newly inserted classification row.
psycopg2.extras.Json(value) Serialising Python objects to PostgreSQL JSONB columns

PostgreSQL's JSONB column type stores structured JSON data. psycopg2 does not automatically serialise Python lists or dicts to JSONB — if you pass a Python list as a parameter, psycopg2 will try to bind it as a PostgreSQL ARRAY (different type). psycopg2.extras.Json(value) wraps the value in an adapter that tells psycopg2 to serialise it as JSON, which PostgreSQL will then store as JSONB.

import psycopg2.extras

# Wrong: passes ["http://..."] as a PostgreSQL ARRAY
c.execute("INSERT INTO t (links) VALUES (%s)", (["http://..."],))

# Correct: serialises to JSON string, accepted by JSONB column
c.execute("INSERT INTO t (links) VALUES (%s)",
          (psycopg2.extras.Json(["http://..."]),))
In this filesubmit_classification stores each criterion's evidence_links field (a list[str]) using psycopg2.extras.Json(crit.evidence_links) to correctly target the evidence_links JSONB column in the classification_criterion table.

10 Presigned S3 URLs

s3.generate_presigned_url("put_object", ...) Letting the client upload directly to S3 without routing through the API server

Normally, if a client wants to upload a file to S3 it must route the file data through the API server (the server receives the file and then forwards it to S3). This is wasteful — large VCF files would saturate the API server's bandwidth and memory. Presigned URLs solve this: the API server generates a time-limited signed URL that grants the bearer permission to PUT a specific object to a specific S3 key, and gives that URL to the client. The client then uploads the file directly to S3 using a standard HTTP PUT — the file never touches the API server.

The signed URL embeds the bucket name, the object key, an expiry time, and an AWS Signature V4 HMAC. S3 validates the signature when the PUT arrives. The signature can only be generated by someone with valid AWS credentials (the API server), but using the URL requires no credentials.

In this fileget_upload_url generates two presigned URLs per request — one for the VCF file (.vcf.gz) and one for its companion FHIR manifest (.manifest.json). Both are PUT URLs. The manifest key is derived from the VCF key by replacing the file extension. The expiry is 3600 seconds (1 hour).

11 Domain patterns

Optimistic locking (workflow.py) Detecting concurrent modifications without a database lock

A race condition can occur when two requests both read the same workflow status and both decide they are allowed to change it. Without any protection, both would succeed, leaving the DB in an inconsistent state. Optimistic locking avoids this without holding a database row lock for the duration of the request. The trick: include the value you read as a condition in the UPDATE — if it has changed since you read it, the UPDATE will touch zero rows.

# Step 1 — READ the current status (no lock held)
rows = await asyncio.to_thread(db.query,
    "SELECT status FROM workflow WHERE sample_id = %s", (sample_id,))
current = rows[0]["status"]  # e.g. "pending"

# Step 2 — UPDATE only if status is still what we read
c.execute(
    "UPDATE workflow SET status=%s ... WHERE sample_id=%s AND status=%s",
    (new_status, sample_id, current),  # ← current is the guard condition
)

# Step 3 — If another request changed it first, rowcount == 0
if c.rowcount == 0:
    raise _ConcurrentModification()   # → HTTP 409
In this fileupdate_workflow uses this pattern. The _ConcurrentModification sentinel exception is private to the module — it exists purely to carry the signal out of the _do closure (which cannot raise HTTPException directly without coupling the DB layer to HTTP).
Soft deletes + append-only history (classification.py) Never destroying clinical records; always leaving an audit trail

A soft delete marks a record as deleted without removing it from the database. Here, deleted_at is set to NOW() instead of issuing a DELETE statement. Active records have deleted_at IS NULL; deleted records have a timestamp. This design guarantees the full classification history is always preserved — essential in a clinical context where audit trails are a regulatory requirement.

# Soft-delete the existing active classification
c.execute(
    "UPDATE variant_classification SET deleted_at=NOW() "
    "WHERE variant_id=%s AND deleted_at IS NULL",
    (variant_id,),
)

# Insert the new one — the old one is still in the table, just invisible to
# queries that filter WHERE deleted_at IS NULL
c.execute(
    "INSERT INTO variant_classification (variant_id, framework, ...) "
    "VALUES (%s, %s, ...) RETURNING id", ...)
classification_id = c.fetchone()[0]
In this fileBoth submit_classification (PUT) and reset_classification (DELETE) soft-delete before inserting. The ownership check in reset_classification queries WHERE id = %s AND variant_id = %s AND deleted_at IS NULL — all three conditions must match, preventing cross-variant resets.
Audit log An immutable record of every state-changing action

Every write operation in this PR appends a row to the audit_log table inside the same transaction as the main change. The row records who did it (user_id), what action was taken (action), what entity type and ID was affected, and the before/after values as JSON strings. Because the INSERT is in the same transaction, the audit record can only exist if the main change also succeeded — there can never be an orphaned audit entry.

c.execute(
    "INSERT INTO audit_log "
    "(user_id, action, entity_type, entity_id, old_value, new_value) "
    "VALUES (%s, %s, %s, %s, %s, %s)",
    (
        body.user_id,
        "update_workflow",   # human-readable action name
        "workflow",          # entity type
        sample_id,            # entity ID
        json.dumps({"status": current}),   # before
        json.dumps({"status": body.status}),  # after
    ),
)
In this fileAll four write handlers insert an audit entry. The ingest route logs the triggering user and resulting sample ID. The workflow route logs the status transition. The classification routes log the scoring result or the reset action.
