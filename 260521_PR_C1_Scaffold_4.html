01 vite.config.ts — annotated

The four non-obvious choices: why vitest/config instead of vite, what changeOrigin actually does, why globals: true is set, and why setupFiles is an array.

vite.config.ts Unified build + test configuration 
import { defineConfig } from "vitest/config"; // ①
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],                          // ②
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:3000",          // ③
        changeOrigin: true,                      // ④
      },
    },
  },
  test: {
    environment: "jsdom",                       // ⑤
    globals: true,                              // ⑥
    setupFiles: ["./src/tests/setup.ts"],        // ⑦
  },
});
①
Why vitest/config not vite? Importing from "vitest/config" gives defineConfig awareness of the test: block. Without it, TypeScript would complain that test is not a valid key — and you would lose autocomplete and type-checking for Vitest options like environment, globals, and setupFiles. At runtime they are identical; the difference is purely type-level.
②
What does react() add? The @vitejs/plugin-react plugin does two things: (a) transforms JSX using SWC (a Rust-based transpiler — much faster than Babel), and (b) enables React Fast Refresh, which hot-reloads components during development while preserving their state. Without this plugin, Vite would not know how to process .tsx files containing JSX syntax.
③
Why port 3000? The FastAPI backend's Dockerfile sets CMD ["uvicorn", ..., "--port", "3000"]. This proxy is only active when running npm run dev — it forwards /api/* requests from the Vite dev server (port 5173) to the backend (port 3000), avoiding browser CORS errors during local development. In production, nginx handles this proxying instead.
④
What does changeOrigin: true do? By default the proxy forwards requests with the original Host header (e.g. localhost:5173). Many servers — including FastAPI with some middleware — reject requests whose Host header does not match the server's address. changeOrigin: true rewrites the Host header to match the target (localhost:3000), preventing these rejections.
⑤
Why "jsdom"? The default Vitest environment is "node", which has no document object. React components need a DOM to render into. Setting environment: "jsdom" tells Vitest to load the jsdom library (a JavaScript implementation of the browser DOM) before running each test file, providing a simulated window, document, and event system.
⑥
What does globals: true do? Normally you would need to write import { describe, it, expect, vi } from "vitest" at the top of every test file. With globals: true, Vitest injects these into the global scope automatically — test files can use them directly without importing. This matches the Jest convention that most testing documentation assumes.
⑦
Why an array for a single file? setupFiles accepts an array because you may have multiple setup files — for example, one for jest-dom matchers, another for MSW (mock service worker), another for global test utilities. The pattern is established as an array from the start so adding a second setup file later requires no structural change.

02 tsconfig.json — annotated

The six options that are non-standard or whose interactions are surprising.

tsconfig.json TypeScript compiler options 
{
  "compilerOptions": {
    "target": "ES2020",                        // ①
    "useDefineForClassFields": true,           // ②
    "lib": ["ES2020", "DOM", "DOM.Iterable"],
    "types": ["vite/client"],                  // ③
    "module": "ESNext",
    "skipLibCheck": true,                      // ④
    "moduleResolution": "bundler",             // ⑤
    "allowImportingTsExtensions": true,        // ⑥
    "resolveJsonModule": true,
    "isolatedModules": true,                   // ⑦
    "noEmit": true,                             // ⑧
    "jsx": "react-jsx",                        // ⑨
    "strict": true,
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }             // ⑩
  },
  "include": ["src"]
}
①
target: "ES2020" — Sets the JavaScript version TypeScript targets when emitting code. Since noEmit: true, tsc never actually emits anything — but this option still controls which syntax tsc considers valid for the environment. ES2020 supports Promise.allSettled, optional chaining, nullish coalescing, and other modern features the codebase uses.
②
useDefineForClassFields: true — Controls how class fields are emitted. The ECMAScript standard uses Object.defineProperty; the old TypeScript behaviour used simple assignment. Setting this to true matches the ECMAScript spec. Required for compatibility with modern bundlers and the React component model.
③
types: ["vite/client"] — Restricts global type inclusions to only vite/client. This adds type definitions for Vite-specific globals: import.meta.env (for VITE_API_KEY, VITE_USER_ID, DEV), import.meta.hot (HMR), and import.meta.glob. Without this, TypeScript reports Property 'env' does not exist on type 'ImportMeta'.
④
skipLibCheck: true — Skips type-checking of all .d.ts files in node_modules. Some npm packages ship type declarations with internal inconsistencies that would fail strict type-checking. skipLibCheck ignores these, focusing tsc on your own code only. The trade-off is you might miss genuine type errors in library interfaces, but in practice those are very rare.
⑤
moduleResolution: "bundler" — A newer resolution strategy (TypeScript 5+) that mirrors how bundlers like Vite resolve imports. The older "node" strategy requires imports to omit file extensions; "bundler" allows .tsx extensions in imports and supports package.json exports maps correctly. Required when allowImportingTsExtensions: true is set.
⑥
allowImportingTsExtensions: true — Allows writing import Foo from "./Foo.tsx" with the explicit .tsx extension. Vite and Vitest work with the real file system and need the extension for module resolution. This option is only valid when combined with noEmit: true — TypeScript refuses to emit JS when extensions are present since the emitted files would have broken paths.
⑦
isolatedModules: true — Forces each file to be type-checkable in isolation, without needing information from other files. This is required for esbuild compatibility: esbuild transpiles one file at a time and cannot see the full program. The practical restriction: no const enum (they require cross-file lookup), and no namespaces that merge across files.
⑧
noEmit: true — The most important option to understand. tsc does not write any JavaScript output. Its sole job is type-checking. Vite uses esbuild for the actual transpilation — esbuild is 10–100× faster than tsc but does zero type checking. This split is why the build script is tsc && vite build: tsc finds type errors first, then esbuild produces the bundle.
⑨
jsx: "react-jsx" — Selects the JSX transform introduced in React 17. With "react-jsx", the compiler automatically imports the JSX runtime from react/jsx-runtime — you no longer need import React from "react" at the top of every file. Files that do not use JSX at all can omit the React import entirely.
⑩
paths: { "@/*": ["src/*"] } — Defines the @/ path alias so import Foo from "@/components/Foo" resolves to src/components/Foo. baseUrl: "." is required for paths to work. Note: this only tells tsc how to resolve it — Vite also needs an alias entry in vite.config.ts for runtime resolution. Currently the alias is declared but not used in practice.

03 nginx.conf — annotated

Every directive in the 14-line nginx config — what each line does and what would break if it were missing.

nginx.conf SPA routing + API proxy 
server {
    listen 80;                                    // ①
    root /usr/share/nginx/html;                   // ②
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;         // ③
    }

    location /api/ {                              // ④
        proxy_pass http://backend:3000;           // ⑤
        proxy_set_header Host $host;              // ⑥
        proxy_set_header X-Real-IP $remote_addr; // ⑦
    }
}
①
listen 80 — nginx listens on port 80 inside the container. The Dockerfile exposes port 80, and docker-compose.yml maps it to host port 5173. External HTTPS termination (TLS) would happen at a load balancer or reverse proxy upstream — the container itself only handles HTTP.
②
root /usr/share/nginx/html — The filesystem path nginx looks in when resolving $uri. The Dockerfile copies /app/dist here: COPY --from=build /app/dist /usr/share/nginx/html. So $uri = "/assets/index-abc.js" maps to /usr/share/nginx/html/assets/index-abc.js.
③
try_files $uri $uri/ /index.html — The SPA routing directive. nginx tries each argument in order: (1) look for a file at $uri — serves real static assets like /assets/index-abc.js; (2) look for a directory at $uri/ — rarely used but correct to include; (3) fall back to /index.html — this is the catch-all that makes React Router work. Without this line, GET /patients/42 would return 404 because there is no file at that path.
④
location /api/ — Matches requests starting with /api/. This location block is evaluated before location / because it is more specific. Note the trailing slash — it ensures /api (without slash) does not match; only /api/patients, /api/variants, etc. do. This prevents accidental proxying of any path that starts with the letters "api" in a future route.
⑤
proxy_pass http://backend:3000 — Forwards the request to the FastAPI container. backend is the Docker Compose service name — Docker's internal DNS resolves it to the container's IP. Port 3000 matches the uvicorn command in the backend's Dockerfile. The backend port is not exposed to the host in docker-compose.yml; it is only reachable within the Docker network, ensuring all traffic must go through nginx.
⑥
proxy_set_header Host $host — Passes the original Host header to the backend. By default, nginx would replace Host with the proxy target host (backend:3000). Forwarding the original host lets the FastAPI app log the correct virtual hostname and helps any middleware that uses the Host header for URL generation.
⑦
proxy_set_header X-Real-IP $remote_addr — Passes the original client IP to the backend. Without this, FastAPI would see the nginx container's IP as the client address for all requests — making IP-based logging useless. The FastAPI app can read request.headers.get("X-Real-IP") to get the real client IP for audit logging.

04 src/index.css — annotated

The Tailwind directive sequence and the @layer components block — why the order of the three directives matters and how @apply expands at build time.

src/index.css Tailwind directives + component layer 
@tailwind base;          // ①
@tailwind components;    // ②
@tailwind utilities;     // ③

@layer base {
  body {
    @apply bg-gray-50 text-gray-900 antialiased; // ④
  }
}

@layer components {       // ⑤
  .badge {
    @apply inline-flex items-center px-2 py-0.5 rounded text-xs font-medium; // ⑥
  }
  .badge-pending {
    @apply bg-yellow-100 text-yellow-800; // ⑦
  }
  .btn {
    @apply inline-flex items-center justify-center // ⑧
           px-3 py-1.5 text-sm font-medium rounded border transition-colors;
  }
  .btn-primary {
    @apply bg-blue-600 text-white border-blue-600 hover:bg-blue-700; // ⑨
  }
}
①
@tailwind base — Injects Preflight, Tailwind's CSS reset. Preflight removes default browser styles (margins on headings, list bullets, etc.) to give a consistent cross-browser starting point. This must come first so later layers can build on a clean foundation.
②
@tailwind components — This is the injection point where Tailwind inserts all classes defined in @layer components blocks — including the .badge and .btn classes defined later in this same file. The @layer components block below does not have to appear before this directive; Tailwind collects all component layer declarations and inserts them here regardless of order.
③
@tailwind utilities — Injects all utility classes: px-4, text-sm, bg-blue-600, etc. This must come last because utilities should override components when both are applied to the same element. The CSS cascade order (later = higher priority for equal specificity) enforces this: a utility class added after a component class wins.
④
@apply bg-gray-50 text-gray-900 antialiased — @apply is a PostCSS directive that expands to the CSS properties of the named utility classes. At build time this becomes: background-color: #f9fafb; color: #111827; -webkit-font-smoothing: antialiased; .... It is equivalent to using the classes in HTML but works inside a CSS rule for elements you cannot annotate (like body).
⑤
@layer components — Declares this block as belonging to the components layer. This has a critical specificity consequence: component classes have lower specificity than utility classes. So <span class="badge badge-pending text-white"> — the text-white utility overrides the text-yellow-800 from badge-pending, even though both rules have the same selector form. Without @layer, specificity would be determined by source order and overrides would require !important.
⑥
.badge base class — inline-flex makes the badge lay out its children as flex items while itself flowing inline with text. items-center vertically centres any icon alongside the label text. px-2 py-0.5 gives tight horizontal and very small vertical padding — appropriate for a status chip. This class is combined with a modifier class (.badge-pending, etc.) on the same element.
⑦
.badge-pending colour classes — Yellow-100 (#fef9c3) background with yellow-800 (#854d0e) text gives sufficient contrast (WCAG AA) while being visually distinct from the other workflow statuses. The colour choices follow a consistent semantic system: yellow = not yet started, blue = in progress, green = complete, gray = inactive.
⑧
.btn base class — transition-colors enables smooth hover colour transitions. border adds a 1px border — the modifier class sets its colour. This base class deliberately leaves background-color, color, and border-color unset so modifier classes can define them without specificity conflicts.
⑨
hover:bg-blue-700 — This is a Tailwind variant inside an @apply. At build time Tailwind generates a .btn-primary:hover { background-color: #1d4ed8; } rule. The variant prefix (hover:) works inside @apply blocks — it is not restricted to JSX class strings. The result is the button darkens slightly on hover without any JavaScript.
Design verification

The badge and button classes defined here are tested indirectly in PR D1 via WorkflowBadge.test.tsx and ClassificationBadge.test.tsx. Those tests assert that the correct CSS class string (badge badge-pending, badge badge-pathogenic etc.) is applied to rendered elements — confirming the CSS class names here match the class names used in the components.
