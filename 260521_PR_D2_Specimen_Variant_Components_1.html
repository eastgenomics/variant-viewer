01 What this PR does

PR D2 adds four React components that together form the interactive patient detail page. These components live between the read-only display layer (PR D1: badges, headers, patient list) and the classification panel (PR D3). They are the components a clinical analyst actually uses: viewing specimens, advancing workflow status, deleting samples when needed, and browsing variants to select one for classification.

Context in the PR stack

This PR targets pr/D1 (display components). It imports WorkflowBadge and ClassificationBadge from D1, and the lib modules (api.ts, display-utils.ts, pipeline-config.ts) from C2. No pages are introduced here — pages arrive in PR D4.

The four components have distinct, non-overlapping responsibilities:

SpecimenCard
Container / orchestrator

Top-level card for one sample. Renders specimen metadata and embeds the three child components below it. Memoizes pipeline filter defaults to prevent unnecessary VariantTable refetches.

82 lines
WorkflowControl
State machine buttons

Renders the allowed next-state buttons for the current workflow status. TRANSITIONS map mirrors the backend's VALID_TRANSITIONS. Prop-syncs via useEffect so an external status refresh is reflected without remounting.

57 lines
DeleteSampleButton
Destructive action with guard

Two-phase confirmation: a trigger button, then a confirm bar. Shows a high-risk amber warning for reported or archived specimens. Surfaces API errors inline rather than dismissing silently.

71 lines
VariantTable
Data table with server fetch

Fetches GET /api/samples/{id}/variants with filter params, renders a TanStack Table, and paginates. Manages five pieces of state: data, total, loading, error, pageIndex, filters, geneInput, sortBy, sortDir.

02 Component architecture

The four components have a clear parent–child tree. SpecimenCard is the root and the only component that receives props from outside this PR (the SampleDetail object from PatientDetailPage). It instantiates the other three as children.

The onDeleteSample callback originates in PatientDetailPage (PR D4) and passes through SpecimenCard as onDeleteSample? to DeleteSampleButton as onDelete?. When a delete succeeds, the callback fires up the chain, removing the specimen from the page's state array. SpecimenCard itself does not manage any lists — it is a pure relay for the callback.

Important: defaultFilters stability

SpecimenCard calls getPipelineDefaults(specimen.pipeline_key) and wraps the result in useMemo. Without the memo, every render of SpecimenCard would produce a new object reference for defaultFilters — and since VariantTable lists defaultFilters in a useEffect dependency array, this would trigger an unnecessary refetch on every parent render. The useMemo ensures the object reference only changes when pipeline_key actually changes.

No direct database or S3 access

All data operations go through the FastAPI REST API via the typed wrappers in api.ts or direct fetch calls (VariantTable) that include authHeaders(). The SPA has no psycopg2, boto3, or other backend SDK imports anywhere. This is Invariant 5 of the project.
