01 What this document set does

PR B adds five specification documents to specification/frontend/. Together they form a complete, self-contained engineering brief: a fresh developer or agent session should be able to read this directory, understand exactly what to build, and produce the working SPA without access to the original design conversation.

The documents are not code — they contain no runnable files — but they govern every decision made in PRs C1 through D4. Think of them as the architectural contract that the implementation PRs must satisfy.

Context

The variant-viewer frontend was originally prototyped as a Next.js 15 application on the discovery/nextjs branch, using React Server Components with direct PostgreSQL access. PRs 8–11 port that prototype into a standalone Vite + React SPA that communicates exclusively with the FastAPI backend introduced in PRs 6–7. This specification documents exactly how that port should be done.

02 The SPA at a glance

The React SPA serves six clinical workflows for bioinformaticians at East Genomics NHS Trust:

WorkflowRouteKey component
List patients — paginated table of all cases with MRN, specimen count, latest workflow status/PatientListTable
Patient detail — patient header + one SpecimenCard per specimen, each with a filterable variant table/patients/:idSpecimenCard + VariantTable
Classify variants — criterion checkbox panel; live score/label computed locally; Save draft and Confirm actions persist to backend/patients/:patientId/variants/:variantIdClassificationPanel + CriterionRow
Upload VCF — multi-step form; presigned S3 in prod, direct multipart in dev/uploadUploadForm
Workflow management — inline transition buttons (→ reviewing / → reported / → archived)Embedded in specimen cardsWorkflowControl
Delete patients / specimens — guarded confirm-in-place UIEmbedded in patient list and specimen cardsDeletePatientButton, DeleteSampleButton
Clinical target user

Clinical bioinformaticians reviewing germline and somatic variants as part of NHS diagnostic reporting. The interface enforces the ACGS SNV (Association for Clinical Genomic Science) and SVIG-UK (Somatic Variant Interpretation Group) classification frameworks without exposing raw database operations.

How build-prompt.md is used

When a developer or AI agent starts a new session to implement the SPA, they paste the contents of build-prompt.md as their first message. The prompt instructs them to read all four spec files in order, inspect the current frontend directory, and then work through milestones one at a time. It encodes the TDD rule, the commit message format, the milestone verification commands, and the five safety invariants in a compact, self-contained form.

04 Architecture

The SPA uses a layered architecture: pages fetch data and pass it down to components; components render it and call lib functions for formatting, scoring, and API access. No component reaches the network directly except through api.ts or VariantTable's direct fetch.

06 Non-goals and constraints

README.md lists explicit non-goals that are important context when reviewing the design decisions in later documents:

No server-side rendering
Static SPA only

All data fetching is client-side. The SPA is pure static HTML/CSS/JS — no Node.js runtime in production. Serves from nginx or CloudFront.

By design
No authentication UI
API key at nginx/ALB layer

The SPA has no login screen. The API key is injected via VITE_API_KEY at build time, or forwarded by the ALB. Per-user OIDC is post-PR-12.

Deferred
No patient PII display
MRN only

patient.name and patients.nhs_number are never rendered in any component. GDPR data-minimisation enforced at the component layer.

Invariant 1
No direct DB / S3 access
REST API only

The SPA calls only the FastAPI endpoints. No psycopg2, boto3, or any database/AWS SDK may be imported.

Invariant 5
No mobile-first design
Desktop clinical workstations

Designed for ≥1280px displays. Responsive enough to be usable at smaller sizes but not optimised for mobile.

Scope limit
No real-time updates
No WebSockets or polling

Users refresh manually. No service worker, no local caching, no offline support.
