12 upload.py

Single responsibility: validate a VCF filename and an optional run date, then return two presigned S3 PUT URLs — one for the VCF file and one for its companion FHIR manifest. No DB interaction; no file data passes through the server.

app/routes/upload.py · 82 lines · 1 route handler · 2 Pydantic models
get_upload_url lines 37–82 POST /api/upload-url

The only handler in the module. Returns a pair of presigned S3 PUT URLs so the browser can upload a VCF file and its manifest directly to S3.

Inputs

  • body.vcf_filename — e.g. "sample.vcf.gz"
  • body.run_date — optional "YYYY-MM-DD"; defaults to today

Returns

  • vcf_url — signed PUT URL for the VCF
  • manifest_url — signed PUT URL for the manifest
  • vcf_key, manifest_key — S3 object keys for the client to reference later
  • expires_in — always 3600 seconds

Validation sequence (all run before any AWS call)

  1. Extension check — _VCF_RE.search(body.vcf_filename) rejects anything that does not end with .vcf or .vcf.gz. Returns 400.
  2. Path traversal check — rejects filenames containing / or .. which could escape the runs/{date}/ key prefix and overwrite arbitrary S3 objects. Returns 400.
  3. Date format check — if run_date is supplied, datetime.strptime(run_date, "%Y-%m-%d") validates both the format and calendar correctness (month 13 or day 32 will raise ValueError). Returns 400.
  4. Bucket env check — verifies VCF_BUCKET_NAME is set. Returns 500 (server misconfiguration, not a client error).

Key construction

The S3 key for the VCF is runs/{date_prefix}/{safe_filename}. The manifest key is derived by replacing the VCF extension with .manifest.json via _VCF_RE.sub(".manifest.json", vcf_key) — so runs/2024-11-05/sample.vcf.gz becomes runs/2024-11-05/sample.manifest.json. Critically, safe_filename (the already-validated copy) is used for key construction, not the raw body.vcf_filename.

Design note

Returning the keys to the client (not just the URLs) is deliberate: the client needs the key values to later call POST /api/ingest and tell the server where the VCF ended up. The presigned URL itself contains the key, but extracting it from the URL is fragile — returning it explicitly is cleaner.

13 ingest.py

Triggers the full ingest pipeline for a VCF already sitting in S3. Wraps the heavy ingest_sample function (from PR 5) in a route-level validation layer, a DB transaction, and an exception-to-HTTP-status mapping.

app/routes/ingest.py · 73 lines · 1 route handler · 1 helper · 1 Pydantic model
_manifest_key lines 32–33 helper

One-line helper. Derives the S3 key for the companion manifest from a VCF key by substituting the extension.

Input

  • vcf_key: str — e.g. "runs/2024-11-05/sample.vcf.gz"

Returns

  • str — e.g. "runs/2024-11-05/sample.manifest.json"

This function is only called after the route-level _VCF_RE check has already confirmed the key ends with .vcf or .vcf.gz — so the regex substitution is guaranteed to match. Calling it on a non-VCF key would silently return the input unchanged, producing a wrong manifest path.

manual_ingest lines 36–73 POST /api/ingest

The main handler. Validates the S3 key, delegates to ingest_sample inside a transaction, records the triggering user in the audit log, and maps domain exceptions to HTTP status codes.

Inputs

  • body.vcf_s3_key — full S3 object key for the VCF
  • body.user_id — analyst who triggered the ingest

Returns / errors

  • 200 {"sample_id": int} — DB ID of the created sample
  • 400 — non-VCF key or bad manifest/VCF content
  • 409 — duplicate submission (same VCF already ingested) or race condition
  • 500 — VCF_BUCKET_NAME not configured

The _do closure

The heavy lifting is inside a nested _do(conn) function that captures body, bucket, s3, and manifest_key from the outer scope. It calls ingest_sample(vcf_key, manifest_key, bucket, s3, conn) — this downloads both files from S3, validates the manifest, parses the VCF, and writes all rows to the DB in the same connection. After it returns, _do writes a single audit_log INSERT using the same connection (same transaction).

Exception mapping

ExceptionHTTP statusWhy
DuplicateSubmissionError409ingest_sample detected the VCF was already processed (exact or near-duplicate)
psycopg2.errors.UniqueViolation409TOCTOU race: two concurrent ingests both passed the idempotency check, then the second lost the UNIQUE constraint INSERT
ValueError400Unsupported file format, failed manifest schema validation, or missing required manifest fields

All three raise ... from exc preserve the original exception as the __cause__, making stack traces more informative in logs.

14 workflow.py

Manages the four-state review lifecycle for a sample. The state machine is expressed as an explicit allowlist dictionary. Every transition is atomic and audited.

app/routes/workflow.py · 85 lines · 1 route handler · 1 exception class · 1 state machine dict
VALID_TRANSITIONS lines 28–33 constant

A module-level dictionary that encodes the complete state machine. Each key is a current status; the value is the list of statuses it may legally transition to. An empty list means the status is terminal.

VALID_TRANSITIONS: dict[str, list[str]] = {
    "pending":   ["reviewing", "archived"],
    "reviewing": ["reported",  "archived"],
    "reported":  ["archived"],
    "archived":  [],          # terminal — no further transitions
}

The check is if body.status not in VALID_TRANSITIONS.get(current, []). Using .get(current, []) rather than direct indexing means an unrecognised current status (which should not exist in a healthy DB) safely returns an empty list and triggers a 422 rather than a KeyError.

update_workflow lines 41–85 PUT /api/workflow/{sample_id}

Reads the current status, validates the requested transition, then updates the row and appends an audit entry in one atomic operation. Uses optimistic locking to detect concurrent modifications.

Inputs

  • sample_id: int — URL path parameter
  • body.status — target status (Literal — only 3 values accepted)
  • body.user_id — who is making the change

Returns / errors

  • 200 {"sample_id": int, "status": str}
  • 404 — sample_id not found in workflow table
  • 422 — requested transition not in allowlist
  • 409 — concurrent modification detected (rowcount = 0)

Two-phase read-then-write

Phase 1 (async, event loop): db.query reads the current status. If no row is found, 404. If the requested transition is not in VALID_TRANSITIONS[current], 422. Both checks happen before any transaction is opened.

Phase 2 (sync, thread pool): _do(conn) executes the UPDATE with AND status=%s as an extra guard. If another request changed the status between Phase 1 and Phase 2, c.rowcount will be 0 and _ConcurrentModification is raised. The transaction rolls back. The outer handler catches it and returns 409.

Why _ConcurrentModification instead of HTTPException

The _do closure runs inside db.run_in_transaction, which is a plain DB utility with no knowledge of HTTP. Raising HTTPException from inside it would couple the DB layer to FastAPI. Instead, the private _ConcurrentModification sentinel carries the signal out of the callback; the route handler converts it to a 409. This is the same pattern as DuplicateSubmissionError in the ingest layer.

15 classification.py

The most complex module. Exposes three endpoints over the same URL namespace: a score-only preview, a full persist-and-lock, and a reset. Uses the classification engine from PR 4 and maintains an append-only classification history via soft deletes.

app/routes/classification.py · ~230 lines · 3 route handlers · 2 helpers · 5 Pydantic models
_build_criteria & _build_rules lines 76–86 helpers

Two short private helpers that translate Pydantic input models to the classification engine's dataclasses. The translation is explicit field-by-field because the Pydantic models contain extra fields (notes, evidence_links, pre_computed) that the engine does not accept — passing them would raise a TypeError.

def _build_criteria(criteria: list[CriterionIn]) -> list[AppliedCriterion]:
    return [
        AppliedCriterion(
            criterion_code=c.criterion_code,  # only these three fields go to the engine
            applied=c.applied,
            strength=c.strength,
        )
        for c in criteria
    ]
score_classification lines 90–97 POST /api/variants/{id}/classify

The simplest handler. Converts the request to engine types, calls classify(), and returns the result. No DB interaction whatsoever — this is a pure scoring endpoint, useful for showing a live score preview in the UI as the analyst selects criteria.

Inputs

  • variant_id: int — URL param (not used in scoring — score is deterministic from criteria)
  • body.criteria — list of applied criteria
  • body.framework — "acgs_snv" or "svig"
  • body.combination_rules — pairwise conflict rules

Returns

  • score: int — Tavtigian point total
  • classification: str — e.g. "Likely_Pathogenic"
  • warnings: list[str] — combination rule violations, if any

The variant_id path parameter exists to keep the URL namespace consistent (/api/variants/{id}/… for all classification endpoints) but is not passed to the engine — the score depends only on the criteria, not which variant they belong to.

submit_classification lines 100–175 PUT /api/variants/{id}/classification

The most involved handler. Scores, then persists — soft-deleting any existing active classification and inserting a full new record with all criteria rows, locked to the requesting analyst. Everything in the DB write is transactional.

Inputs

  • variant_id: int — URL path
  • All fields of ClassificationSubmitRequest — criteria, framework, rules, locked_by, user_id

Returns / errors

  • 200 with classification_id, score, classification, warnings
  • 404 — variant not found
  • 422 — unknown framework value

Sequence of operations

  1. Verify variant exists — db.query("SELECT id … FROM variants WHERE id = %s"). Returns 404 if not found. This happens outside the transaction (read-only).
  2. Score — call classify() synchronously in the event loop. The engine is a pure function with no I/O, so asyncio.to_thread is not needed.
  3. Get framework version — get_framework_version(body.framework) returns a human-readable version string (e.g. "ACGS 2024 Best Practice Guidelines") that is stored alongside the score for traceability.
  4. _do(conn) — four SQL statements in one transaction:
    • Soft-delete: UPDATE variant_classification SET deleted_at=NOW() WHERE variant_id=%s AND deleted_at IS NULL
    • Insert classification: INSERT INTO variant_classification (…) VALUES (…) RETURNING id → classification_id
    • Insert criteria: one INSERT INTO classification_criterion per criterion in the list
    • Insert audit: INSERT INTO audit_log (…)
framework_version must be non-null

The variant_classification.framework_version column is NOT NULL in the schema. Passing NULL causes a PostgreSQL constraint violation. get_framework_version() is called before entering _do so the value is always available.

reset_classification lines 178–230 DELETE /api/variants/{id}/classification/{cid}

Soft-deletes an existing classification and inserts a blank replacement. The blank record preserves the variant↔framework relationship so the UI knows a classification attempt is in progress, while clearing the score, criteria, and lock — putting it back to an unscored state.

Inputs

  • variant_id: int — URL path
  • classification_id: int — URL path
  • body.user_id — for audit trail

Returns / errors

  • 200 {"new_classification_id": int}
  • 404 — classification not found, already deleted, or does not belong to variant_id

Ownership check

The SELECT query uses WHERE id = %s AND variant_id = %s AND deleted_at IS NULL. All three conditions must match. The variant_id condition is critical — without it, a malicious or accidental request to /api/variants/999/classification/50 would delete record 50 even if it belongs to variant 1, not 999.

Blank replacement

The replacement INSERT omits score, classification, locked_at, and locked_by — all of which default to NULL. It retains variant_id, framework, and framework_version from the deleted record (captured before the transaction via existing = rows[0]). The new ID is returned so the client can immediately reference it.
