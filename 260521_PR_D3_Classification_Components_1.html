01 What these files do

PR D3 adds the two components that implement the clinical variant classification workflow in the variant-viewer SPA. Together they let a genomic analyst apply ACGS SNV or SVIG-UK classification criteria to a variant, view a live-computed score and classification, save a draft, confirm a final result, and reset if needed.

CriterionRow.tsx

A leaf controlled component — it owns no persistent state itself. It renders a single classification criterion: a checkbox to apply or unapply it, an optional strength selector, a notes textarea, and an evidence link input. Its most security-critical function is isValidEvidenceLink(), which is exported and reused by ClassificationPanel to sanitise links loaded from the server.

The component is deliberately unaware of the framework, the scoring engine, or the backend API. All it knows is the definition of one criterion (CriterionDef) and its current state (CriterionState). Any change is communicated upward via an onChange callback.

ClassificationPanel.tsx

The orchestrator. It owns the complete classification session for one variant: which framework is selected, what all criteria are currently set to, the live score and classification (computed in-browser via the TypeScript classification engine), whether the result is saved as a draft or confirmed, and the reset flow. It renders a panel header with the score/classification display and save/reset controls, a warnings banner, and then a grid of CriterionRow components grouped by evidence category.

ClassificationPanel is the only component in this PR that calls the backend API (via api.ts). It also re-validates server-loaded evidence links through the same isValidEvidenceLink() function before they reach the DOM, as a defence-in-depth measure against stored cross-site scripting.

Architecture note

The classification score displayed in the panel header is computed entirely in-browser by classification-engine.ts (added in PR C2). The backend receives the criteria and also re-computes the score independently — the two results must agree. This means the user always sees an accurate preview before ever hitting Save.

02 Architecture & data flow

The diagram below shows the layered structure. Data flows from the backend through ClassificationPanel, down to each CriterionRow, and back up via callbacks before being persisted to the API.

The four phases of a classification session

Every classification interaction follows one of four phases. Understanding this state machine is essential before reading the code.

Phase 1
Initialise
Props arrive. initCriteriaState() maps criteria defs to state objects, re-validates server links. Framework selector is unlocked.
Phase 2
Edit
Analyst applies/adjusts criteria. Score updates live via useMemo → classify(). First checkbox change locks the framework selector.
Phase 3
Save
Draft save (locked_by: null) or Confirm (locked_by: userId). Panel stays editable on draft; locks on confirm.
Phase 4
Reset
Soft-deletes the classification on the backend. Blank slate reappears. Framework selector unlocks. Full audit trail preserved in DB.

Why JSON imports work at bundle time

Both criteria JSON files are bundled directly into the JavaScript — they are not fetched at runtime. This means the classification engine is available offline and there is no latency penalty for loading criteria definitions. The resolveJsonModule: true flag in tsconfig.json enables this. The trade-off is that a criteria update requires a new build deployment rather than a backend config change.

05 The 5 invariants

The variant-viewer specification defines five invariants that must hold at all times. PR D3 is directly responsible for enforcing three of them.

Invariant 1 — No patient PII
D1 enforces · D3 is not involved

No component may render patient.name or NHS number. ClassificationPanel receives only variantId, caseType, gene — no patient-identifying data reaches it.

Not in scope for D3
Invariant 2 — API key never logged
C2 api.ts enforces · D3 is not involved

VITE_API_KEY is read only inside authHeaders() in api.ts. ClassificationPanel calls putClassification() and apiReset() — it never touches the API key directly.

Not in scope for D3
Invariant 3 — Evidence links http/https only
Enforced here in D3

User-entered links are validated by isValidEvidenceLink() in CriterionRow before onChange is called. Server-loaded links are re-validated in initCriteriaState() before entering React state — so javascript: or data: URLs can never reach an href attribute. The backend also validates via a Pydantic field_validator.

Enforced by CriterionRow + ClassificationPanel
Invariant 4 — Engine matches Python
Exercised here in D3

ClassificationPanel's live score is produced by the TypeScript classify() function (tested in PR C2 with 4 golden cases). The final classification stored in the DB is independently computed by the Python backend on receipt of the PUT request. Divergence would produce a different confirmed result than the preview — this is explicitly prevented by the golden test suite.

Exercised by ClassificationPanel via classify()
Invariant 5 — No DB/S3 access from SPA
All PRs enforce · D3 is compliant

ClassificationPanel communicates with the backend only through api.ts wrapper functions. No direct database or AWS SDK calls anywhere in the frontend source tree.

No psycopg2/boto3 in frontend/src/
