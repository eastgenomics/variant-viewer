15 CriterionRow.tsx — functions

isValidEvidenceLink lines 4–10 Security

Purpose: Returns true only if the URL's protocol is http: or https:. All other protocols — including javascript:, data:, ftp:, blob: and relative paths — return false.

Input

  • url: string — any string; may be malformed

Output

  • boolean — true only for http/https

Key logic: Calls new URL(url.trim()) which parses the full URL according to the WHATWG URL Living Standard. On a malformed string this throws a TypeError; the try/catch converts that to false. On success, it checks parsed.protocol against exactly two allowed values. The function is exported so that ClassificationPanel.initCriteriaState() can reuse it without duplicating the logic.

Security design decision

Using new URL() rather than a regex or string prefix ensures the browser's own URL parser — the same engine that evaluates href attributes — is used for validation. A regex like /^https?:\/\// could be defeated by unusual encodings or newlines in adversarial inputs; the URL constructor normalises first. The url.trim() call handles accidental whitespace that a user might paste.

CriterionDef / CriterionState interfaces lines 12–30 Interfaces

Purpose: Define the shapes that flow between ClassificationPanel and CriterionRow. Both are exported; ClassificationPanel imports them to type its own state arrays.

CriterionDef fields

  • code — e.g. "PVS1"
  • direction — "pathogenic" | "benign" | "oncogenic"
  • adjustable — whether strength can be changed
  • permitted_strengths — valid values for selector
  • description — human text for tooltip/label

CriterionState fields

  • criterion_code — matches def.code
  • applied — is the checkbox ticked?
  • strength — current selected strength
  • notes — free text textarea value
  • evidence_links — validated URLs array
  • pre_computed / pre_computed_value

The separation of CriterionDef (read-only schema from JSON) and CriterionState (mutable per-session values) is deliberate: it ensures the schema cannot be accidentally mutated, and state can be reset independently by recreating CriterionState[] without touching the defs.

CriterionRow lines 38–196 React component

Purpose: Renders a single classification criterion as a controlled form row. Displays the criterion code (colour-coded by direction), description, optional pre-computed value badge, and — when applied — strength controls and a collapsible notes/links panel.

Props

  • def: CriterionDef — the criterion schema
  • crit: CriterionState — current values (read-only)
  • locked: boolean — true when classification is confirmed
  • onChange: (updates) => void — partial update callback

Local state (3 vars)

  • showNotes: boolean — notes panel open?
  • pendingLink: string — link input value
  • linkError: string | null — inline error message

Key logic:

  1. The checkbox calls onChange({applied: e.target.checked}) — the parent owns the actual boolean.
  2. The strength selector is only rendered when crit.applied is true. If def.adjustable is true, a <select> shows def.permitted_strengths; otherwise italic fixed-strength text is shown.
  3. The "Add notes / links" toggle shows/hides the notes panel. Clicking Hide while the panel is open calls setPendingLink("") and setLinkError(null) to clear transient state.
  4. Server-received evidence_links are rendered as clickable <a> tags with target="_blank" rel="noopener noreferrer". Each has an × remove button when unlocked.
  5. The useEffect([crit.applied]) resets all three local state vars when the criterion is unchecked from outside.
Why locked disables everything

When locked={true} is passed, the checkbox, strength selector, notes textarea, and the Add button all receive disabled={locked} or are conditionally not rendered ({!locked && (...)}). This means the component is rendered identically for confirmed classifications — the analyst can see the full state but cannot modify anything.

addLink (inner function) ~lines 60–70 inside CriterionRow Security

Purpose: Validates the current pendingLink value and either appends it to evidence_links via the onChange callback (on success) or sets linkError (on rejection). Clears pendingLink on success.

Input (from closure)

  • pendingLink — current input value
  • crit.evidence_links — existing links array

Side effects

  • Calls onChange with updated evidence_links
  • Calls setPendingLink("") on success
  • Calls setLinkError() on rejection

Key logic: Guards first with if (!pendingLink) return (prevents empty submissions). Then passes the link through isValidEvidenceLink(). On rejection, sets the inline error message and does not call onChange — the invalid URL never enters the parent's state. On success, clears the error, calls onChange with a new array (spread of existing plus new link), then clears the input.

16 ClassificationPanel.tsx — functions

getCriteriaDefs lines ~33–37 Utility

Purpose: Returns the criteria array for the specified framework from the bundled JSON files.

Input

  • framework: Framework — "acgs_snv" | "svig"

Output

  • CriterionDef[] — typed criteria array

Key logic: A simple conditional expression returning acgsCriteria.criteria or svigCriteria.criteria. The as unknown as CriterionDef[] cast is needed because the JSON is typed as a literal schema by TypeScript's resolveJsonModule; this cast asserts it matches the interface.

Why a standalone function?

This is extracted from the component so that the framework-switch handler inside the component's JSX can call getCriteriaDefs(next) with the new framework value before committing the framework state change. Calling getCriteriaDefs(framework) inside the onChange handler would use the stale framework closure value from before the state update.

initCriteriaState lines ~39–60 Security + Init

Purpose: Maps a criteria definitions array into a CriterionState[], merging any server-loaded existing values. Critically, re-validates server-loaded evidence links through isValidEvidenceLink() before storing them in state.

Inputs

  • defs: CriterionDef[] — full criteria schema
  • existing: Partial<CriterionDetail>[] — server-loaded criteria (may be empty)

Output

  • CriterionState[] — one entry per def, defaults filled in where no existing match

Key logic:

  1. For each def in the schema, find any matching existing criterion by criterion_code.
  2. Extract evidence_links from the existing entry (defaults to []).
  3. Filter links through isValidEvidenceLink() — any link that fails validation is silently dropped. The inline comment explains why: "a valid API key holder could inject javascript: URLs via API".
  4. Construct a CriterionState object with merged values, defaulting to false/default_strength/"" for unapplied criteria.
Why re-validate server-loaded links?

The frontend validation in addLink() prevents a user from entering a bad link via the form. The backend Pydantic validator prevents bad links in the PUT request body. But neither protects against a link that was written directly to the database (bypassing the API) by someone with database access, or a future bug that skips the backend validator. Re-validating on load ensures that even in those scenarios, no javascript: URL can ever reach an href attribute in the DOM.

This function is also called on reset (initCriteriaState(defs, [])) to return all criteria to their blank defaults, and on framework switch (initCriteriaState(getCriteriaDefs(next), [])) to start fresh in the new framework.

ClassificationPanel lines ~62–290 React component

Purpose: Orchestrates the complete classification session for a single variant. Manages 8 state variables, renders the panel header with live score, all criterion rows grouped by evidence category, warnings, error banners, and save/reset controls.

Props

  • variantId: number
  • caseType: "germline" | "somatic"
  • gene: string | null
  • initialClassification: Omit<ClassificationDetail, "criteria"> | null
  • initialCriteria: Partial<CriterionDetail>[]

State variables (8)

  • framework — "acgs_snv" | "svig"
  • frameworkLocked — bool
  • criteria — CriterionState[]
  • classId — number | null
  • lockedAt — string | null
  • saving — bool
  • saveError — string | null
  • showResetConfirm — bool

Derived values (3 useMemos)

  • defs — criteria schema for current framework (updates on framework change)
  • combinationRules — rule list for current framework
  • {score, classification, warnings} — live scoring result (updates on any criterion change)

Render structure:

  1. Panel header: framework selector + score display + classification badge + save/reset buttons
  2. Warnings banner (amber) — shown when combination rules are violated
  3. Save error banner (red) — shown after a failed API call
  4. Reset confirmation row (red) — "This will delete all criteria…"
  5. Criteria grid — EVIDENCE_CATEGORIES.map() → one section heading per category → CriterionRow per criterion
The framework selector lock

When the panel first renders with no existing classification, the framework selector is enabled (frameworkLocked: false). The moment the analyst applies any criterion ("applied" in updates in updateCriterion), setFrameworkLocked(true) is called. The rationale: criteria codes (PVS1, PP3 etc.) are framework-specific; allowing the analyst to switch frameworks after applying criteria would leave orphaned state. Once locked, the selector is only re-enabled on Reset (which wipes all criteria).

updateCriterion ~lines 115–126 useCallback

Purpose: Stable callback passed to every CriterionRow's onChange prop. Updates a single criterion in the criteria array by code, and locks the framework selector if the update included an applied change.

Inputs

  • code: string — criterion_code to update
  • updates: Partial<CriterionState> — fields to merge

Side effects

  • Calls setCriteria(prev => ...) with updated array
  • Calls setFrameworkLocked(true) if "applied" in updates

Key logic: Uses the functional update form of setCriteria — prev => prev.map(c => c.criterion_code === code ? {...c, ...updates} : c). This is important because updateCriterion is wrapped in useCallback([], []) (empty deps), meaning it closes over the initial state. The functional updater gives it access to the current state at call time, not the stale state at creation time.

save (async) ~lines 130–150 API

Purpose: Serialises current panel state and calls putClassification(). A single function handles both draft and confirmed saves, distinguished by the lock: boolean parameter.

Input

  • lock: boolean — false = draft, true = confirm

Side effects on success

  • setClassId(result.classification_id)
  • setLockedAt(now) — only if lock=true

Key logic:

  1. Sets saving: true and clears saveError.
  2. Calls putClassification(variantId, {framework, user_id: userId, locked_by: lock ? userId : null, criteria: [...]}).
  3. The criteria are serialised to include only fields the API expects: criterion_code, applied, strength, notes, evidence_links. Empty notes are converted to undefined (omitted in JSON); empty evidence_links arrays are similarly omitted.
  4. On success: sets classId (enables future updates rather than creates); conditionally sets lockedAt from the client clock — used only for the "Confirmed DD/MM/YYYY" label, not as the authoritative timestamp.
  5. On failure: sets saveError. Panel stays in exactly its previous state — no partial updates.
handleReset (async) ~lines 152–170 API

Purpose: Calls the backend reset endpoint, then on success clears all classification state back to blank. On failure, closes the confirmation row and shows an error banner — the panel remains locked and the analyst can retry.

Guard

  • if (!classId) return — no-op if nothing to reset

On success

  • setClassId(null), setLockedAt(null)
  • setFrameworkLocked(false)
  • setCriteria(initCriteriaState(defs, []))
  • setShowResetConfirm(false)

Error handling design: In the catch block, setShowResetConfirm(false) is called before setSaveError(). This dismisses the "Yes reset / Cancel" row so the analyst is not left staring at a confirmation prompt that does nothing — the panel returns to its locked state with the error banner explaining what happened. This is deliberately asymmetric with the success path: success clears all state, failure clears only UI state (the confirm row) while leaving the backend state unchanged.
