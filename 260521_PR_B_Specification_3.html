14 README.md — orientation

specification/frontend/README.md 135 lines · read first Orientation
§ "What this SPA does" 6 use cases Scope definition

Purpose: Lists the six user-facing workflows in numbered order. This is the entry point for a reviewer who wants to understand what the finished product does before reading the technical design.

What it covers

  • List patients (paginated)
  • Patient detail + specimen cards
  • Classify variants (local scoring)
  • Upload VCF (dev + prod paths)
  • Workflow transitions
  • Delete patients and specimens

What to check

  • Is the description of the classification workflow accurate — specifically that scoring runs locally and Save draft / Confirm are distinct actions?
  • Does the upload description correctly distinguish dev (ingest-direct) from prod (presigned S3)?
§ "Project layout (target)" ~50 lines of annotated file tree Structure

Purpose: Shows the complete directory layout with an inline comment on every file explaining its role. This is the single-source-of-truth for "what goes where" and is used as the checklist when scaffolding M19.

Design decision: The layout puts all test files under src/tests/ rather than co-located with their components (src/components/WorkflowBadge.test.tsx). The reasoning is that the test directory mirrors the structure of the implementation and is easy to find by convention; co-location was considered but rejected because it makes the component directory harder to scan visually.

§ "Non-goals" 9 bullet points Scope boundary

Purpose: Explicitly states what the SPA will NOT do in PRs 8–11. This prevents scope creep and documents why certain seemingly obvious features are absent.

The most important non-goals for reviewers: no SSR, no login screen (API key at nginx/ALB layer), no patient PII display (hardcoded by design, not an oversight), no direct DB access, no pagination on patient list (loads all patients in v0.1).

Watch for

If a reviewer sees that patient names are not shown and asks "is that a bug?", the answer is in README.md §Non-goals — it is deliberate. The field is returned by the API but discarded at the component layer.

15 DESIGN.md — architecture and contracts

specification/frontend/DESIGN.md 677 lines · read second Architecture
§1 Problem statement + §2 Architecture ~80 lines Context

Purpose: §1 explains why the port is necessary (SSR coupling, deployment constraints). §2 contains a Mermaid flowchart showing the component dependency graph — which pages render which components, which components call which lib modules, and which lib modules make API calls.

Key insight from the architecture diagram: Only api.ts and VariantTable make network calls. Everything else is either pure rendering or pure computation. This constraint makes the codebase highly testable because most components can be rendered with props alone, with no HTTP mocking needed.

§3 Module responsibilities §3.1–§3.13 covering 13 modules Contracts

Purpose: For each module, states what it must do and what it must NOT do. The "must NOT" clauses are as important as the positive responsibilities — they encode isolation guarantees that keep the codebase clean.

ModuleCritical "must NOT"
api.tsMust not log or expose the API key. Must not contain business logic.
classification-engine.tsMust not differ from the Python backend in scoring logic or thresholds.
display-utils.tsMust not make network calls or import React.
PatientListTableMust not display name or nhs_number columns.
ClassificationPanelMust not allow framework change after a criterion has been applied. Must not accept evidence links with non-http/https protocols.
WorkflowControlMust not optimistically update status before the API responds.

The WorkflowControl TRANSITIONS map in §3.9 is worth particular attention: it must be an exact mirror of VALID_TRANSITIONS in backend/app/routes/workflow.py. If the backend state machine changes and the frontend is not updated, users will see buttons that trigger API errors.

§4 Data model (TypeScript interfaces) ~120 lines of interface definitions Type contracts

Purpose: Defines every TypeScript interface that maps to a backend API response. These are the contracts that implementation PRs C2–D4 must satisfy.

Key design choices encoded in the interfaces:

  • PatientSummary.name is present (nullable) but never displayed — it exists in the type to match the backend response shape, while the UI intentionally ignores it.
  • VariantDetailResponse.case_type was added after review: ClassificationPage needs it to select the ACGS SNV vs SVIG-UK framework. Without it, all variants would be classified with the germline framework even for somatic cases.
  • PipelineFilters.gnomad_af_max is number | null (not just number) — null represents a cleared filter input where no AF limit is applied.
  • ClassificationDetail.criteria is a nested array inside active_classification. ClassificationPage must destructure this before passing to ClassificationPanel.
§5–§11 Error handling, styling, testing, compliance ~200 lines Cross-cutting concerns

§5 Error handling strategy — a table mapping every error condition to the component responsible and the user-visible result. Notably: delete failure keeps the confirmation dialog open with an inline error, rather than dismissing silently (a common UX bug in first-pass implementations).

§6 Styling conventions — the badge-* and btn-* class system. All workflow status and classification result badges must use these classes. The classes are defined in src/index.css's @layer components block, which means they are available to all components via Tailwind's purge mechanism.

§7 Testing strategy — lists what to mock and what to assert for each component. The key design decision here: classification-engine.ts is imported real (not mocked) in ClassificationPanel tests. This is intentional — the live score computation is part of what ClassificationPanel tests verify.

§9 Compliance alignment — DSPT/GDPR (no PII), DCB0129 hazard mitigation (evidence link validation), CAF A2 (API key not logged). Each has a one-line shell command for verification.

16 IMPLEMENTATION.md — milestone TDD build plan

specification/frontend/IMPLEMENTATION.md 1,496 lines · read third Build plan
§1 Backend pre-requisite milestones (M_pre1–8) Table of 8 rows with change + tests Pre-conditions

Purpose: Documents all backend changes that must be in main before frontend work begins. Each row specifies the module, the exact change, and the test(s) that verify it.

The most critical pre-requisite for clinical safety is M_pre6: making locked_by nullable in ClassificationSubmitRequest. Without this, the Save draft button cannot work — the backend would reject any classification submit without a locked_by user ID.

M_pre8 (POST /api/ingest-direct) enables the dev upload path. Without it, UploadForm cannot function in a local development environment because the prod path requires S3 credentials.

§2 Milestone plan table 9-row table mapping milestone → PR → test → verification Overview

Purpose: The master reference table. For each milestone, gives the PR it belongs to, the modules to build, the test file to write first (the "Red" step), and the condition that defines "done" (the "Green" step).

How milestones map to PRs

M_pre1–8 and M19–M22 ship in PRs A and C1–C2. M23–M24 ship in PR D1–D2. M25 ships in PR D3. M26 ships in PR D4. Each PR is independently reviewable, and each has exactly one milestone's worth of changes.

§3–§10 Individual milestone sections (M19–M26) ~1,300 lines of code sketches Implementation detail

Purpose: For each milestone, provides the complete test file to write (Red section) and enough of the implementation sketch to build from (Green section). A builder can follow these sections without needing any additional design documents.

Each milestone section is structured:

  1. Red — paste this test file and run npm test; all tests must fail.
  2. Green — implement until all tests pass. The sketch shows enough detail to avoid ambiguity on hard decisions.
  3. Verification — exact npm test command to confirm the milestone is complete.

Design decisions embedded in the sketches:

  • M21 (classification engine) — four golden test cases: PVS1+PM2 → LP (score 9), empty → VUS (score 0), BS1+BS2 → Benign (score −8), O2 very_strong → Likely_Oncogenic (score 8). The SVIG test uses O2 (not SVS1 or any invented code) because SVIG criteria are named O1–O11 and B1–B7 in the JSON config.
  • M25 (CriterionRow) — the evidence link rejection test is required (not optional) to satisfy Invariant 3. The test uses expect(onChange).not.toHaveBeenCalled() — not just "not called with the bad URL" — because the implementation returns early before calling onChange at all.
  • M26 (ClassificationPage) — variant.case_type is passed with a runtime validation (variant.case_type === 'somatic' ? 'somatic' : 'germline') rather than a TypeScript cast, providing defence against unexpected values from the database.

17 REFERENCE.md — API catalogue and configuration

specification/frontend/REFERENCE.md 645 lines · read fourth Reference
§0 Backend pre-requisites table 8-row table Pre-conditions

Purpose: Companion to IMPLEMENTATION.md §1. Provides a quick-reference table linking each backend pre-requisite to the frontend feature it enables, so a reviewer can immediately understand which frontend capability is blocked by which backend change.

§1 Backend API endpoint catalogue §1.1–§1.6 covering 15 endpoints API contracts

Purpose: For every endpoint used by the SPA: HTTP method, path, request parameters, and the exact JSON response shape. This is the most important section for reviewers checking that the TypeScript interfaces in DESIGN.md match the backend.

Key things to verify in this section:

  • GET /api/patients response — uses items key (not patients), and includes total, limit, offset. The frontend api.ts must read r.items, not r.patients.
  • GET /api/variants/{id} — active_classification contains nested criteria array. ClassificationPage must split this before passing to ClassificationPanel (initialClassification = classification minus criteria; initialCriteria = the criteria array).
  • PUT /api/variants/{id}/classification — response field is classification_id at the top level, not nested.
  • POST /api/upload-url — request body uses vcf_filename, not filename. An easy mistake to make when porting from the Next.js reference which used a different field name.
  • §1.4b POST /api/ingest-direct — dev-only endpoint. Accepts multipart/form-data. Returns 413 if VCF is over 500 MB.
§2 Environment variables 4-row table Configuration

Purpose: Documents the four VITE_ variables, their defaults, and when each is required. Particularly important is the VITE_APP_ENV note: the dev upload path is activated by import.meta.env.DEV (automatically true when running npm run dev) OR by VITE_APP_ENV === 'development' — the prod path requires an explicit production build.

§4 CSS class reference + §8 Workflow state machine ~60 lines Implementation aids

§4 — complete list of badge-* and btn-* classes with their Tailwind expansions. Used when implementing WorkflowBadge and ClassificationBadge to verify the correct class names.

§8 Workflow state machine — the four valid transitions expressed as a text diagram. Must match the VALID_TRANSITIONS dict in backend/app/routes/workflow.py and the TRANSITIONS map in WorkflowControl.tsx. Any discrepancy means the frontend renders buttons that will fail when clicked.

§9 Classification scoring + §11 Glossary ~50 lines Clinical reference

§9 — complete scoring tables for ACGS SNV and SVIG-UK. The ACGS SNV threshold table defines exactly where the Likely_Benign / Benign boundary falls (≤−6 is Benign, not ≤−7). An off-by-one error here would cause systematic misclassification.

§11 Glossary — defines MRN, VEP, HGVSc, HGVSp, gnomAD AF, REVEL, SpliceAI, ACGS SNV, SVIG-UK, and Specimen. Useful for reviewers not familiar with clinical genomics terminology.

18 build-prompt.md — the build session brief

specification/frontend/build-prompt.md 108 lines · used to start a build session Build brief
Starting instruction and build rules ~30 lines Execution rules

Purpose: When a developer or AI agent starts a new session to implement the SPA, they use this file as their initial prompt. It encodes:

  • The instruction to read all four spec files in order before writing any code.
  • The TDD rule — write the test first, confirm it fails, then implement.
  • The commit message format: feat(frontend): M<N> — <short description>.
  • The prohibition on global npm installs and on AI attribution in commits.
  • The reference implementation pointer: git show origin/discovery/nextjs:<path> — read the Next.js prototype before implementing each component.
  • The starting check: run pytest to verify M_pre1–8 are complete before starting M19.
Milestone verification table 9-row table Quality gates

Purpose: Compact version of the verification table from IMPLEMENTATION.md §2. Each row gives the exact shell command to run at the end of each milestone, and the expected output. A milestone is not complete until its verification command passes.

The M26 verification command is the most comprehensive:

# M26: every quality gate in sequence
cd frontend
npm test               # all tests green
npx tsc --noEmit       # no TypeScript errors
npm run build          # dist/ produced cleanly
docker build -t vv-frontend .  # Docker image builds
The five invariants with verification commands ~50 lines Safety gates

Purpose: The invariants in build-prompt.md are the authoritative version — more concise and actionable than the compliance section in DESIGN.md. Each invariant gives:

  • A one-sentence plain-English statement of the requirement.
  • A shell command or test file that verifies it.
  • The expected output for a passing check.
Why build-prompt.md exists separately from DESIGN.md

DESIGN.md is written for human readers who want to understand the architecture. build-prompt.md is written for an AI agent or a developer starting a fresh session with no prior context. It is intentionally terse and instruction-first. The two documents overlap on invariants and milestones, but the build-prompt is self-contained — a reader does not need to have read DESIGN.md first to follow it.
