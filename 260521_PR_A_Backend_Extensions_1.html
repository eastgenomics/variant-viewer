PR A — Backend API Extensions

Eight targeted additions to the FastAPI backend that give the frontend SPA the endpoints and fields it needs — delete routes, aggregate fields, filter params, nullable locks, evidence validation, and a dev-only direct ingest path.

01 What this PR does

The variant-viewer backend already shipped a read-only API and a classification engine (PRs 1–7). This PR, labelled M_pre1–8 in the milestone plan, adds the eight specific features the React frontend needs before it can be built. None of the existing endpoints are changed in a breaking way — everything here is additive.

The changes span five route files, one migration, and the Docker Compose configuration. The guiding principle throughout is that the backend should enforce correctness at the boundary: Pydantic validators reject bad input before it reaches the database, sentinel exceptions keep HTTP concerns out of transaction callbacks, and audit log entries record every destructive action before the final delete runs.

03 Data flow

All five route files follow the same structural pattern. An HTTP request arrives, FastAPI validates it against a Pydantic model, the handler calls asyncio.to_thread to push a blocking database operation onto a thread pool, and the result is serialised back to JSON via another Pydantic model. For write operations the DB call is wrapped in db.run_in_transaction to guarantee atomicity.

Key pattern

The _do(conn) closure pattern is used consistently for all write endpoints. It is a plain Python function that receives a connection, does work, and either returns a value or raises a private sentinel exception. The async handler wraps db.run_in_transaction(_do) in asyncio.to_thread, then catches the sentinel and converts it to an HTTPException. This keeps the database layer free of any knowledge about HTTP status codes.

04 Pydantic models introduced

Pydantic models serve two roles in FastAPI: they validate incoming request bodies and serialise outgoing responses. Every field name in a model becomes a JSON key in the API response — so the model definitions here are the contract that the TypeScript frontend is written against.

ModelFileRoleKey fields added
PatientSummary patients.py Response — patient list item sample_count, latest_sample_id, latest_sample_name, latest_workflow_status, latest_ingested_at, pipeline_key (all default 0/None)

PatientRef samples.py Nested in SampleDetailResponse.patient Slim model: id, lab_number, name only — no aggregate fields
VariantSummary samples.py Response — variant list item hgvs_c, hgvs_p, clinvar_sig (all default None)

ClassificationSubmitRequest classification.py Request — PUT classification body locked_by: str | None (None = draft, non-null = confirmed); validator rejects empty string

Why PatientRef instead of PatientSummary?

PatientSummary gained five aggregate fields in M_pre1. Those fields have default values of 0 or None, which is fine for the list endpoint where they are populated by subqueries. But when a patient object is nested inside SampleDetailResponse, the aggregate fields would always serialise as zeroes and nulls — misleadingly suggesting the patient has no samples when in fact the query simply did not fetch them. PatientRef solves this by declaring only the three fields that are actually retrieved: id, lab_number, and name.

06 Key design decisions

Sentinel exceptions
_PatientNotFound, _SampleNotFound, _ConcurrentReset

Transaction callbacks (_do(conn)) cannot raise HTTPException — FastAPI does not handle exceptions raised in threads. Private exception classes raised inside _do escape the thread, then the async handler catches them and converts to the correct HTTP status code.

Safety
Audit before delete
Clinical audit trail requirement

In both delete_patient and delete_sample, the audit log INSERT runs before the final DELETE FROM patients/samples. This ensures the audit entry is atomically part of the same transaction — if the delete fails, the audit entry is rolled back too — and the entity ID is still valid at insert time.

Compliance
Safe f-string SQL
list_sample_variants ORDER BY

The ORDER BY clause is built by interpolating order_col and order_dir directly into the SQL string — not via parameters. This is safe because: sort_by is regex-validated by FastAPI before the function body runs (422 on unknown values), the SORTABLE dict maps it to source-code string literals, and order_dir is a ternary between two hard-coded strings. No user input reaches the SQL string.

Security
locked_by null = draft
Classification save semantics

locked_by: str | None. When None, the INSERT uses the literal SQL string NULL for locked_at (injected via f-string after all user input has already been validated). When non-null, NOW() is used instead. An empty string is rejected by a Pydantic field validator with a 422 — it cannot accidentally be treated as a draft save.

Correctness
evidence_links server validation
Invariant 3 — defence-in-depth

The frontend validates evidence links before adding them to state, but the backend also validates them in a @field_validator on CriterionIn.evidence_links. Any URL that does not start with http:// or https:// (case-insensitive) is rejected with a 422. This prevents javascript: and data: URLs reaching the database even if the client-side check is bypassed.

Security
GDPR migration 004
UK data-minimisation principle

Migration 004 drops the dob column from the patients table. Date of birth is not required for variant interpretation, and retaining it would be unnecessary personal data under UK GDPR's data-minimisation principle. All code references to dob have been removed from the route models. The migration is wrapped in BEGIN/COMMIT for consistency with migrations 001–003.
