16 routes/patients.py

backend/app/routes/patients.py
3 endpoints · _PatientNotFound sentinel · aggregate subqueries
list_patients lines 50–96 Read

Purpose: Returns a paginated list of patients. Each item includes the five aggregate fields added in M_pre1: sample count and the most recently ingested sample's id, name, workflow status, ingested_at, and pipeline_key.

Inputs (query params)

  • limit — 1–200 (default 50)
  • offset — ≥0 (default 0)
  • search — optional; ILIKE matches on lab_number OR name

Output

  • PatientListResponse
  • items[] — array of PatientSummary
  • total, limit, offset

Key logic: Two queries run sequentially. First, a COUNT query determines the total (needed for pagination metadata). Second, the main SELECT uses five correlated subqueries — each finds the single most-recently-ingested sample for the patient and extracts one field. A comment in the code notes that this is acceptable at current scale but should be replaced with a LATERAL join if the patient count grows above roughly 10,000.

The WHERE clause is built by string concatenation based on whether search is provided. This is safe because the search value is passed as a %s parameter, not interpolated into the string. The GROUP BY p.id is needed because the LEFT JOIN to samples could produce multiple rows per patient.

get_patient lines 98–122 Read

Purpose: Returns full detail for a single patient including the list of associated samples. Each sample includes vcf_filename (added in M_pre7).

Input

  • patient_id — path parameter (int)

Output

  • PatientDetailResponse (extends PatientSummary)
  • Nested samples[] of SampleSummary
  • 404 if patient not found

Key logic: Two sequential queries — one for the patient row, one for all samples belonging to that patient ordered by ingested_at descending. The samples query LEFT JOINs to the workflow table to resolve status (defaulting to 'pending' via COALESCE if no workflow row exists). The response is constructed by spreading the patient row and appending the sample list.

delete_patient lines 124–159 Delete

Purpose: Deletes a patient and all dependent rows: variants, workflow entries, samples, and finally the patient row itself. Inserts an audit log entry before the patient delete.

Input

  • patient_id — path parameter (int)

Output

  • 204 No Content on success
  • 404 if patient not found

Key logic: Uses the _do(conn) closure pattern. The closure first verifies the patient exists (raises _PatientNotFound if not). It then runs four DELETEs in dependency order — variants first (so foreign keys don't block), then workflow entries, then samples — before inserting the audit log entry and finally deleting the patient row. The order of the audit INSERT relative to the patient DELETE matters: the entity_id column references a patient id that must still exist at INSERT time.

Why no soft-delete for variants?

variant_classification rows use soft-delete (a deleted_at timestamp) throughout the classification workflow. Here, however, the variants themselves are hard-deleted because a deleted patient should have no remaining data — the entire clinical record is being removed. The CASCADE constraint on variant_classification.variant_id handles the classification rows automatically when variants are deleted.

17 routes/samples.py

backend/app/routes/samples.py
3 endpoints · _SampleNotFound sentinel · dynamic filter builder · PatientRef
get_sample lines 55–97 Read

Purpose: Returns full detail for a single sample including patient identity (as PatientRef, not the full PatientSummary), workflow status, and variant count.

Input

  • sample_id — path parameter

Output

  • SampleDetailResponse
  • patient field is PatientRef (slim)
  • 404 if sample not found

Key logic: Single query with JOINs to patients (for PatientRef fields), workflow (for status), and variants (for count via COUNT aggregate). The patient is constructed explicitly as a PatientRef instance from the aliased columns patient_id, lab_number, patient_name — not directly from the row dict, because the column names differ from the model field names.

list_sample_variants lines 99–199 Read

Purpose: Returns a paginated, filtered, and sorted list of variants for a sample with their classification summary. This is the most complex function in the PR.

Inputs (query params)

  • limit, offset — pagination
  • sort_by — one of 6 columns (regex-validated)
  • sort_dir — "asc" or "desc"
  • gnomad_af_max — float 0–1, optional
  • consequences — comma-separated VEP terms
  • clinvar_exclude — comma-separated ClinVar values to exclude
  • gene — ILIKE match on gene name

Output

  • VariantListResponse
  • items[] of VariantSummary
  • Now includes hgvs_c, hgvs_p, clinvar_sig
  • 404 if sample not found

Key logic (filter builder): The function builds a dynamic WHERE clause by starting with ["v.sample_id = %s"] and appending additional clauses conditionally. Each clause is paired with its parameters in filter_params. The consequences filter uses PostgreSQL's ANY(%s) operator with a list parameter, and clinvar_exclude uses != ALL(%s). Both accept lists because psycopg2 correctly serialises Python lists to PostgreSQL array literals when used as parameters.

Key logic (ORDER BY): sort_by is looked up in the SORTABLE dict (which maps it to a SQL fragment like "v.gene"), and sort_dir is resolved to "ASC" or "DESC" by a ternary. Both are interpolated into the SQL f-string. The comment above the SORTABLE dict explains why this is safe.

chrom_order: The SELECT includes a CASE expression that converts chromosome names to integers for correct numeric ordering (X→23, Y→24, MT→25). This column is stripped from the result dict before constructing VariantSummary objects, so it never appears in the response.

delete_sample lines 202–226 Delete

Purpose: Deletes a sample and all its variants. Mirrors the delete_patient structure exactly.

Input

  • sample_id — path parameter

Output

  • 204 No Content on success
  • 404 if sample not found

Key logic: Uses _SampleNotFound sentinel. Deletes variants first, then workflow entries, then inserts the audit log entry (before the sample DELETE, so entity_id is still valid), then deletes the sample. The high-risk warning for reported/archived specimens is handled client-side only — the backend enforces no such rule, treating all deletions identically.

18 routes/variants.py

backend/app/routes/variants.py
1 endpoint · case_type added · nested classification + criteria
get_variant lines 58–120 Read

Purpose: Returns full variant detail including all annotation fields, the active classification (if any), and the classification criteria. The only change in this PR is adding case_type to the response.

Input

  • variant_id — path parameter

Output

  • VariantDetailResponse
  • case_type — "germline" or "somatic" (new)
  • active_classification — nested with criteria, or null
  • 404 if variant not found

Key logic: Three sequential queries. First: the variant row JOINed to samples to get case_type. Second: the active variant_classification row (where deleted_at IS NULL — the classification may have been soft-deleted and a blank replacement inserted on reset). Third: if a classification exists, the associated classification_criterion rows.

Why case_type matters: The frontend's ClassificationPage needs to select between the ACGS SNV framework (germline) and the SVIG-UK framework (somatic) before the user makes any changes. Without case_type in the variant response, the page would have to make an additional request to fetch the sample.

19 routes/classification.py

backend/app/routes/classification.py
3 endpoints · nullable locked_by · evidence_links validation · _ConcurrentReset
score_classification POST /classify Score only

Purpose: Runs the classification engine and returns the score, classification label, and any warnings. No database write. Used for live preview as the user applies criteria.

Input

  • ClassifyRequest body
  • criteria[], framework, combination_rules[]

Output

  • score — integer
  • classification — label string
  • warnings[] — combination rule violations

Key logic: Converts the request body to the internal AppliedCriterion and CombinationRule types via helper functions, calls classify() from lib/classification_engine.py, and returns the result dict. No DB access at all.

submit_classification PUT /classification Persist

Purpose: Scores and persists a classification. Soft-deletes any existing active classification, inserts a new variant_classification row plus all criteria rows, and writes an audit log entry. If locked_by is null, this is a draft save (no lock timestamp). If non-null, the classification is confirmed.

Input

  • ClassificationSubmitRequest
  • locked_by: str | None — null=draft, non-null=confirm
  • user_id: str — for audit log

Output

  • classification_id
  • score, classification, warnings
  • 404 if variant not found

Key logic: The function first verifies the variant exists outside the transaction (so a 404 can be raised cheaply without acquiring a transaction lock). It then runs the classification engine synchronously. The _do(conn) closure soft-deletes the existing active classification, inserts the new record, inserts all criteria rows (using psycopg2.extras.Json() to correctly store the evidence_links list as JSONB), and inserts the audit log entry. The locked_at value is determined by an f-string that interpolates the literal SQL keyword NULL or NOW() based on whether body.locked_by is None — this is safe because the decision is made in Python from a Python boolean, not from user input.

reset_classification DELETE /classification/{id} Reset

Purpose: Soft-deletes the current active classification and inserts a blank replacement — preserving the variant/framework association while clearing the score, lock, and criteria. This allows re-classification without losing the historical record.

Input

  • variant_id, classification_id — path
  • user_id — for audit log

Output

  • new_classification_id
  • 404 if classification not found
  • 409 on concurrent modification race

Key logic: The function first fetches the existing classification (outside the transaction, for 404 handling). Inside _do, it updates deleted_at = NOW() on the existing record, then checks c.rowcount. If rowcount == 0, another concurrent request already deleted it — the _ConcurrentReset sentinel is raised, which the handler converts to a 409. Otherwise, a blank replacement record is inserted (framework preserved, no score or criteria), and the audit log is written.

20 routes/ingest.py

backend/app/routes/ingest.py
2 endpoints · S3 path (existing) · ingest-direct (new, dev-only)
manual_ingest POST /ingest (existing) Ingest

Purpose: Triggers ingest of a VCF already uploaded to S3. Accepts a JSON body with the S3 key and user ID. Delegates to lib/ingest.ingest_sample() which downloads, validates, and parses the VCF and its FHIR R4 manifest sidecar.

This function was added in PR 7 and is unchanged in this PR. It is included here for context.

ingest_direct POST /ingest-direct (new) Dev ingest

Purpose: Dev-only endpoint. Accepts a VCF file uploaded as multipart/form-data along with patient and specimen metadata as form fields. Parses the VCF locally (no S3), then writes all necessary rows to the database in a single transaction: patient (upserted by lab_number), sample, variants, classification shells, pre-computed criteria, and workflow.

Inputs (form fields)

  • vcf — file (.vcf or .vcf.gz)
  • lab_number — required
  • specimen_name — required
  • case_type — "germline"|"somatic"
  • pipeline_key — optional
  • user_id — for audit log
  • sequencing_date — optional date

Output

  • sample_id — new sample row ID
  • message — success string
  • 400 on non-VCF file or parse error
  • 409 on duplicate upload
  • 413 on file > 500 MB

Key logic — file handling: The function reads the entire file into memory, enforces a 500 MB limit, writes to a named temporary file (deleted on context-manager exit), and calls parse_vcf() which requires a path. The vcf.filename is captured into vcf_name before the closure is defined — after await vcf.read(), the UploadFile object may be in an undefined state and its filename attribute should not be relied on inside a thread.

Key logic — _do closure: The transaction callback upserts the patient (using ON CONFLICT to avoid duplicates across multiple uploads), checks idempotency (same filename + patient = duplicate), inserts the sample with an s3_key of "direct:{vcf_name}" as a sentinel value, then iterates over all parsed variants. For each variant it inserts a variants row, selects the appropriate framework via select_framework(case_type, gene), inserts a blank variant_classification shell, and then inserts any pre-computed criteria (such as BA1 triggered by high gnomAD AF). Finally, a workflow row is inserted with status 'pending' and the audit log entry is written.

Classification shell

Every variant gets a blank variant_classification row inserted immediately on ingest. This shell records the framework version at ingest time and provides the foreign key target for classification_criterion rows. Pre-computed criteria (e.g. BA1 triggered when gnomAD AF exceeds the threshold) are stored as criteria with applied = FALSE and pre_computed = TRUE — the analyst can accept or override them during classification. This mirrors exactly what the production S3-path ingest_sample() function does.
