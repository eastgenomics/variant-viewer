08 React SPA vs SSR — why the port exists

Concept: Server-Side Rendering vs Single-Page Application Why the prototype had to be rewritten

The original variant-viewer prototype used Next.js 15 with React Server Components (RSC). In this model, React components run on the Node.js server, fetch data directly from PostgreSQL, and send HTML to the browser. The database password never leaves the server.

This works well for rapid prototyping, but it means the frontend and backend are entangled: deploying the frontend requires a Node.js runtime with database access. You cannot serve it from a CDN (S3/CloudFront) or an nginx container. Scaling the frontend independently of the database is not straightforward.

The SPA approach breaks this dependency. The browser loads static HTML/CSS/JS from nginx. All data access goes through the FastAPI REST API. The frontend knows only the URL of the API, not the database credentials.

// Next.js RSC (what we're moving away from)
// — runs on server, direct DB access, not deployable to CDN
async function PatientsPage() {
  const patients = await db.query('SELECT * FROM patients'); // ① direct SQL
  return <PatientList patients={patients} />;
}

// React SPA (what we're building)
// — runs in browser, fetches via REST, deployable anywhere
function PatientsPage() {
  const [patients, setPatients] = useState([]);
  useEffect(() => {
    listPatients().then(r => setPatients(r.items)); // ② REST API call
  }, []);
  return <PatientList patients={patients} />;
}
  • ①Direct SQL in RSC — works, but requires the Node.js process to have DB credentials. Not possible in a static CDN deploy.
  • ②REST call in SPA — the browser calls GET /api/patients via the FastAPI layer. The SPA has zero knowledge of the database schema.
In this specification

DESIGN.md §1 explains the problem statement in detail. REFERENCE.md §2 documents all the VITE_ environment variables needed because the frontend can no longer read server-side configuration.

09 TypeScript interfaces as API contracts

Concept: TypeScript interfaces How the spec encodes backend response shapes

A TypeScript interface is a named type definition. It describes the shape of an object — which fields it has, and what type each field is. Interfaces have no runtime existence: TypeScript checks them at compile time and then erases them from the JavaScript output.

In this spec, every backend API response has a corresponding TypeScript interface in DESIGN.md §4. These interfaces are the contract between the frontend and backend. If the backend changes a field name or adds a field, the interface must be updated, and TypeScript will then flag everywhere in the frontend that needs updating.

// Interface definition (DESIGN.md §4)
export interface PatientSummary {
  id: number;
  lab_number: string;
  name: string | null;      // ① nullable field
  sample_count: number;    // ② added by M_pre1 backend extension
  latest_workflow_status: string | null;
  pipeline_key: string | null;
}

// Usage in a component
function PatientRow({ patient }: { patient: PatientSummary }) {
  return <td>{patient.lab_number}</td>; // ③ type-checked access
}
  • ①Nullable fields — string | null means the backend may return either a string or JSON null. TypeScript forces you to handle both cases before using the value.
  • ②Backend extension note — some fields require M_pre1–M_pre8 backend changes before they exist. The spec comments which fields depend on which pre-requisite.
  • ③Type-checked access — if you try to access patient.nhs_number (which is not in the interface), TypeScript raises a compile-time error. This is how Invariant 1 (no PII display) is partially enforced.
Why this matters for PR review

When reviewing DESIGN.md §4, you are checking that the TypeScript interfaces accurately reflect the Pydantic models in the backend. A mismatch here means the SPA will silently receive data it doesn't expect — either undefined fields or fields with wrong types that only fail at runtime. Five rounds of automated code review were run to catch these mismatches before the spec was finalised.

In this specification

All TypeScript interfaces are defined in DESIGN.md §4. They cover PatientSummary, PatientDetailResponse, SampleDetail, VariantRow, VariantDetailResponse, ClassificationDetail, CriterionDetail, ClassifyPersistResponse, and PipelineFilters. Cross-reference against the Pydantic models in backend/app/routes/.

10 TDD with Vitest — red-green cycle

Concept: Test-Driven Development Write the test first; it must fail; then implement until green

Vitest is the test runner used in this SPA. It is configured to run in a jsdom environment, which simulates a browser's DOM in Node.js. @testing-library/react provides utilities for rendering React components and querying the rendered output by role, text, or label — the same way a user would interact with the page.

The TDD cycle used throughout IMPLEMENTATION.md is:

  1. Red — write a test that describes the desired behaviour. Run it; it must fail (because the implementation does not exist yet).
  2. Green — write the minimum implementation to make the test pass.
  3. Commit — commit with the message format feat(frontend): M<N> — <short description>.
// RED: write this test first (it will fail — WorkflowBadge doesn't exist yet)
it('renders "Pending" with badge-pending class', () => {
  const { container } = render(<WorkflowBadge status="pending" />); // ①
  const badge = screen.getByText('Pending');      // ② find by visible text
  expect(badge).toHaveClass('badge-pending');   // ③ assert CSS class
});

// GREEN: now write the component
export default function WorkflowBadge({ status }) {
  const labels = { pending: 'Pending', reviewing: 'Reviewing', ... };
  const classes = { pending: 'badge badge-pending', ... };
  return <span className={classes[status]}>{labels[status]}</span>;
}
  • ①render() — mounts the component into a fake DOM. No real browser needed. Returns utilities for querying the output.
  • ②screen.getByText() — finds a DOM element by its visible text content. Throws if not found (fails the test). This is preferable to querying by CSS class because it tests what the user actually sees.
  • ③toHaveClass() — a jest-dom matcher that checks the element has the given CSS class. Verifies that styling decisions (the badge-* system) are correctly applied.

Mocking strategy

API calls are mocked so tests don't require a running backend. Two patterns are used in the spec:

PatternWhen usedHow
Module mockComponents that call api.ts functions (WorkflowControl, ClassificationPanel, PatientListTable)vi.mock('../lib/api', async (importOriginal) => ({ ...actual, updateWorkflow: vi.fn() })) — keeps real types, replaces the function with a controllable stub
Global fetch stubVariantTable, which uses fetch() directly rather than an api.ts wrappervi.stubGlobal('fetch', vi.fn().mockResolvedValue({ ok: true, json: async () => ({ items: [...], total: 1 }) }))
In this specification

Every milestone in IMPLEMENTATION.md §3–§10 starts with a Red section giving the full test file to write, followed by a Green section giving the implementation. DESIGN.md §7 explains the mocking strategy and lists what each test file asserts.

11 Tavtigian point-scoring — the classification engine

Concept: ACGS SNV and SVIG-UK classification How variants are classified as Pathogenic, VUS, or Benign

Clinical variant classification follows the Tavtigian point-based model adopted by the Association for Clinical Genomic Science (ACGS) for germline single nucleotide variants, and a parallel scheme by the Somatic Variant Interpretation Group UK (SVIG-UK) for somatic variants.

Each criterion (e.g. PVS1 — "predicted loss-of-function in a gene where LoF is a known mechanism") carries a point weight based on its evidence strength. The weights for pathogenic and benign criteria are:

StrengthDirectionPointsExample criteria
very_strongPathogenic+8PVS1
strongPathogenic+4PS1, PS2
moderatePathogenic+2PM1–PM6
supportingPathogenic+1PP1–PP5
strongBenign−4BS1, BS2
supportingBenign−1BP1–BP7
standaloneBenign sentinel−999BA1 (gnomAD AF >5%)

The sum of all applied criteria weights gives the score. The score maps to a classification by thresholds:

// ACGS SNV thresholds (from classification-engine.ts)
if (score >= 10)  classification = "Pathogenic";
else if (score >= 6)   classification = "Likely_Pathogenic";
else if (score >= 0)   classification = "VUS";
else if (score >= -5)  classification = "Likely_Benign";
else                   classification = "Benign";

The engine also evaluates combination rules — for example, two PM-strength criteria together behave as one PS-strength criterion. These rules are stored in acgs-snv-criteria.json and svig-criteria.json and are passed into classify() at call time.

// Golden test case: PVS1 (8 pts) + PM2 (2 pts) = 9 pts → Likely_Pathogenic
it('PVS1 + PM2 → Likely_Pathogenic (score 9)', () => {
  const result = classify(
    [
      { criterion_code: 'PVS1', applied: true, strength: 'very_strong' },
      { criterion_code: 'PM2',  applied: true, strength: 'supporting' },
    ],
    'acgs_snv',
    acgsRules
  );
  expect(result.score).toBe(9);
  expect(result.classification).toBe('Likely_Pathogenic');
});
Why the engine runs client-side

The live score display in ClassificationPanel updates on every criterion toggle without a round-trip to the server. This requires the scoring algorithm to run in the browser. The TypeScript engine in classification-engine.ts must produce bit-for-bit identical results to the Python engine in backend/app/lib/classification_engine.py — Invariant 4 mandates this. The four golden test cases in IMPLEMENTATION.md §5 are the automated proof.

In this specification

DESIGN.md §3.2 describes the algorithm in prose. IMPLEMENTATION.md §5 (Milestone 21) has the four golden test cases. REFERENCE.md §9 has the complete scoring tables for both ACGS SNV and SVIG-UK frameworks.

12 VITE_ environment variables and API key safety

Concept: VITE_ env vars How configuration reaches the browser at build time

Vite exposes environment variables to the browser via import.meta.env. Only variables prefixed with VITE_ are included in the bundle — all other variables in .env files are filtered out for security. These values are baked into the JavaScript bundle at build time, not at runtime.

// In a .env file (not committed to git)
VITE_API_KEY=my-secret-api-key

// In api.ts — read at call time, not module load
export function authHeaders(): Record<string, string> {
  const key = import.meta.env.VITE_API_KEY;  // ①
  if (!key) return {};
  return { 'X-API-Key': key };              // ②
}

// WRONG — key would appear in stack traces and logs
// throw new Error(`Auth failed for key: ${key}`);
  • ①Read at call time — authHeaders() reads import.meta.env each time it is called, not once at module load. This makes the function testable: tests can stub the env var before calling it.
  • ②Single read point — VITE_API_KEY appears in exactly one place in the codebase. All components that need the header call authHeaders() rather than reading the env var directly. Invariant 2 requires the key never appear in logs or error messages.

The four VITE_ variables used in the SPA are:

VariableRequired?Purpose
VITE_API_KEYNo in dev, Yes in prodAPI key sent as X-API-Key on every request. Omit in local dev (Vite proxies to local FastAPI which accepts all).
VITE_APP_ENVNoSet to "development" to enable the dev upload path (POST /api/ingest-direct). Vite dev server sets import.meta.env.DEV = true automatically.
VITE_USER_IDNoUser identifier recorded in classification audit logs. Defaults to "analyst".
VITE_BACKEND_URLNoOverride backend URL. Not needed when using Vite proxy or nginx.
Important — VITE_ vars are public

Because VITE_ variables are baked into the JavaScript bundle, they are visible to anyone who can download the bundle. VITE_API_KEY is not a secret in the strong sense — it provides lightweight API key authentication, not cryptographic security. True security comes from OIDC at the ALB layer (post-PR-12). The invariant requirement is that the key is not also leaked via logs or error messages.

In this specification

REFERENCE.md §2 lists all four env vars with their defaults and descriptions. DESIGN.md §3.1 specifies that api.ts must not log or expose the API key value. The authHeaders() function that reads VITE_API_KEY is specified in DESIGN.md §3.1 and its test in IMPLEMENTATION.md §6.

13 The five clinical safety invariants

build-prompt.md defines five invariants — properties of the codebase that must always be true, enforced by automated tests and grep checks. These are not aspirational guidelines; failing any invariant means the build is not ready to ship.

1
No patient PII in the UI The SPA must never render patients.name or patients.nhs_number in any component or page. Only MRN (lab_number) is displayed. Verification: grep -r "nhs_number" frontend/src/components/ frontend/src/pages/ — expected: no output.
2
API key never logged VITE_API_KEY is read once in authHeaders(). It must never appear in a console.log, console.error, or Error message string. Verification: grep -n "VITE_API_KEY" frontend/src/lib/api.ts — expected: only the header assignment line.
3
Evidence links are http/https only CriterionRow validates every user-entered evidence link URL before adding it to state. javascript:, data:, and relative URLs are rejected with an inline error message. Server-loaded links are also re-validated before rendering as href values. Verification: CriterionRow.test.tsx contains a test asserting that a javascript:alert(1) URL is rejected.
4
Classification engine matches Python backend The TypeScript classify() function must produce identical score and classification values to the Python classification_engine.py for the four golden fixture inputs. Verification: the four golden test cases in classification-engine.test.ts (M21) must all pass.
5
No direct database or S3 access from the SPA The SPA must not import psycopg2, boto3, or any database or AWS SDK. All data operations go through the FastAPI REST API. Verification: grep -r "psycopg2|boto3|pg|postgres" frontend/src/ — expected: no output.
Invariants 1 and 3 — clinical safety connection

Invariant 1 is a direct UK GDPR data-minimisation requirement: displaying a patient's name alongside their genetic data in a clinical workflow tool is unnecessary and may constitute a reportable incident under DSPT obligations. Invariant 3 is a DCB0129 hazard mitigation: a malicious javascript: URL stored as evidence could execute when a clinician clicks it, potentially compromising a clinical workstation.

In this specification

All five invariants are defined with verification commands in build-prompt.md. Invariants 1 and 3 are also discussed in DESIGN.md §9 (Compliance and security alignment). The test that enforces Invariant 3 is specified in IMPLEMENTATION.md §9 (M25 CriterionRow test sketch).
