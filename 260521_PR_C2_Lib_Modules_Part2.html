08 TypeScript interfaces and generics

TypeScript adds a static type layer on top of JavaScript. The types are erased at runtime — they exist only to help the editor and compiler catch mistakes before the browser runs any code. Understanding three patterns is enough to read this PR.

Interfaces

An interface is a contract describing the shape of an object. In api.ts every interface mirrors a Pydantic model on the Python backend — if the backend adds a new field, the TypeScript interface should be updated to match.

// Defines the shape of what GET /api/patients returns per patient
export interface PatientSummary {
  id: number;
  lab_number: string;
  name: string | null;          // union type: string OR null
  sample_count: number;
  latest_sample_id: number | null;
}

Generic functions

The <T> syntax makes a function work with any type — you tell TypeScript which type to use at the call site. request<T> in api.ts is the key example: it fetches a URL and returns whatever type the caller specifies.

// T is a placeholder — the caller fills it in
async function request<T>(url: string): Promise<T> {
  const resp = await fetch(url);
  return resp.json() as Promise<T>;
}

// At the call site, T becomes PatientDetailResponse
const patient = await request<PatientDetailResponse>('/api/patients/1');

Extends (interface inheritance)

ClassifyPersistPayload extends ClassifyPayload means it has all the fields of ClassifyPayload plus the additional ones declared in ClassifyPersistPayload. This avoids repeating the criteria fields.

In this PR

All interfaces in api.ts mirror backend Pydantic models. If you see a field name with an underscore (e.g. lab_number) that is deliberate — it matches the snake_case field name the backend sends in JSON. TypeScript interfaces don't rename fields; they describe them as-is.

09 Vitest mocking patterns

Vitest is the test runner used in this project. The tests in this PR use three specific Vitest capabilities that are worth understanding before reading the test files.

vi.stubGlobal — replacing browser globals

The test environment (jsdom) does not make real HTTP requests. vi.stubGlobal("fetch", ...) replaces the browser's built-in fetch function with a fake that returns controlled responses. vi.restoreAllMocks() in beforeEach ensures each test starts with a clean slate.

vi.stubGlobal("fetch", vi.fn().mockResolvedValue({  // ①
  ok: true,
  json: async () => ({ items: [], total: 0 }),     // ②
}));
  • ①
    vi.fn().mockResolvedValue() creates a fake function that, when called, returns a Promise resolving to the given value. mockResolvedValue is shorthand for vi.fn().mockImplementation(() => Promise.resolve(...)).
  • ②
    The mock shape matters. The real fetch returns a Response object with an ok boolean and a json() async method. The mock must replicate this exact shape or the code under test will throw a TypeError.

vi.mock — replacing whole modules

Used in component tests (PRs D1–D4) to replace api.ts with a mock. In this PR's tests, vi.stubGlobal is sufficient because api.ts is the module under test.

JSON imports in tests

The classification-engine tests import the real criteria JSON files from src/config/. This is intentional — it tests the engine against the actual combination rules and verifies that the golden cases still pass when the config files are updated.

import acgsCriteria from "../config/acgs-snv-criteria.json";

const acgsRules = acgsCriteria.combination_rules as {
  rule: string; codes: string[]; message: string
}[];   // cast needed because JSON types are widened by TypeScript

10 The Tavtigian point-based scoring system

The ACGS SNV and SVIG-UK frameworks both use a point-based system introduced by Tavtigian et al. (2020). Instead of applying heuristic rules ("if PVS1 and two PM criteria then Likely_Pathogenic"), each criterion code carries a numeric weight depending on its strength. You sum the weights and apply a threshold table.

Strength weights

moderate+2−2PM1, BM1
supporting+1−1PP3, BP4
standalonesentinel (see below)sentinelBA1, O1, B1, B2

A worked example

A variant with PVS1 (very_strong = +8) and PM2 (supporting = +1) has score 9, which falls in the 6–9 range → Likely_Pathogenic. This is golden test case #1.

Why the golden cases matter

The four golden tests in classification-engine.test.ts are verified against the Python backend's classify() function. If the TypeScript and Python engines ever disagree on the same inputs, the UI would show a different classification than the one stored in the database — a patient safety issue. The golden cases are the contract that keeps them in sync.

11 ACGS SNV vs SVIG-UK frameworks

The application supports two classification frameworks because variant interpretation differs between germline and somatic contexts.

The selectFramework() function chooses between the two. The rule is simple: somatic always means SVIG-UK; germline means ACGS SNV. The CanVIG flag returned by selectFramework() is used by the UI to adjust which BA1/BS1 AF thresholds are shown to the analyst (gene-specific vs population-wide).

12 Sentinel code overrides

Some criteria codes bypass the point summation entirely and directly return a classification. These are called sentinel codes. The code checks for them before entering the main scoring loop, short-circuits, and returns immediately with a special score value that the UI can treat as a flag.

CodeFrameworkReturnsScoreMeaning
BA1ACGS SNVBenign−999Population allele frequency alone is sufficient evidence for Benign; no other criteria matter
O1SVIG-UKOncogenic+999Variant is in a well-curated canonical oncogenic database (e.g. COSMIC hotspot)
B1SVIG-UKBenign−999Population frequency evidence alone sufficient for Benign
B2SVIG-UKVUS0Conflicting evidence — forces VUS regardless of other criteria

The sentinel scores (±999) are out-of-range for any normal classification threshold. The UI uses them purely to detect sentinel state (e.g. to show "★" instead of a numeric score). They are not stored in the database directly; the backend stores the classification label and a null score for sentinel cases.

Priority order matters for SVIG-UK

If an analyst somehow applies both O1 and B1, the classification is Oncogenic (O1 wins). The priority order O1 > B1 > B2 is explicit in both the TypeScript and Python engines. A review finding during development caught an earlier version where B2 was checked first — this has been corrected and is covered by the "O1 + B2 → Oncogenic" test case.

13 Combination rules

Some pairs of criteria are logically contradictory — for example, PP3 (computational evidence supporting pathogenicity) and BP4 (computational evidence supporting benign) cannot both be meaningfully applied to the same variant. The criteria JSON config files include a combination_rules array that defines which code pairs should trigger a warning.

// From acgs-snv-criteria.json (abbreviated)
{
  "combination_rules": [
    {
      "rule": "PP3_BP4_conflict",
      "codes": ["PP3", "BP4"],
      "message": "PP3 and BP4 are mutually contradictory..."
    }
  ]
}

The classify() function checks combination rules before summing points. It builds a Set of applied criterion codes (for O(1) lookup) and fires a warning if two or more codes from the same rule are both applied. The warning is included in the ClassificationResult.warnings array — it does not change the score or classification, it is advisory only.

Why pass rules as a parameter?

The engine receives combinationRules as a parameter rather than importing the JSON internally. This keeps the engine a pure function of its inputs, making it trivially testable — tests can pass an empty array to skip rule checking, or pass a single hand-crafted rule to test a specific combination. The component (ClassificationPanel in PR D3) loads the appropriate JSON and passes it in.

14 FHIR R4 Bundle structure

FHIR (Fast Healthcare Interoperability Resources) is an international standard for exchanging healthcare data. The backend expects a FHIR R4 "collection" Bundle as the sidecar manifest that accompanies each VCF upload. The frontend's buildManifest() function constructs this JSON object.

Bundle anatomy

A Bundle is a container. Type "collection" means it is simply a list of resources held together. Each resource has a resourceType string identifying what kind of record it is.

{
  "resourceType": "Bundle",    // ① top-level FHIR type
  "type": "collection",        // ② bundle flavour — no transaction semantics
  "entry": [                   // ③ array of resource wrappers
    { "resource": { "resourceType": "Patient", ... } },
    { "resource": { "resourceType": "Specimen", ... } },
    { "resource": { "resourceType": "Task", ... } }
  ]
}

The three resources

ResourceEntry indexKey fieldsPurpose
Patiententry[0]identifier[0].system = NHS lab system URI
identifier[0].value = lab_number		Identifies the patient by their lab record number
Specimenentry[1]identifier[0].value = specimen name
extension[0].valueCode = "germline" or "somatic"
collection.collectedDateTime (optional)		Identifies the specimen with its case type and collection date
Taskentry[2]code.text = pipeline key (optional)
output[0].valueString = VCF filename		Records the bioinformatics pipeline and VCF filename
Divergence from the reference implementation

The Next.js reference implementation (discovery/nextjs branch) includes NHS number, patient name, and date of birth in the Patient resource. This SPA deliberately omits them — NHS number is not collected (GDPR minimisation), patient name is not displayed (privacy rule), and date of birth was dropped from the patients table by migration 004. The backend's parse_manifest() handles their absence gracefully with nullable fields.

15 Vite environment variables

Vite (the build tool) provides a mechanism for injecting environment variables into the browser bundle. Variables prefixed VITE_ are baked into the compiled JavaScript at build time. They are accessed via import.meta.env.VITE_KEY_NAME.

// Set in .env file or docker-compose environment section:
// VITE_API_KEY=changeme-replace-in-production

// Read in code:
const key = import.meta.env.VITE_API_KEY as string | undefined;

Two variables are used in this PR's api.ts:

  • VITE_API_KEY — the API key sent to the FastAPI backend as X-API-Key
  • VITE_USER_ID — the logged-in analyst identifier written into classification and audit records
Why authHeaders() reads at call time, not module load

If VITE_API_KEY were read once when the module is imported (const key = import.meta.env.VITE_API_KEY at the top level), Vitest tests could not change it between test runs — the value would be frozen from the first import. By reading inside authHeaders() on every call, tests can use vi.stubEnv("VITE_API_KEY", "test-key") and the change takes effect immediately. This is a testability decision, not a performance concern.

import.meta.env.DEV

Vite also provides a built-in boolean import.meta.env.DEV that is true when running the Vite dev server (npm run dev) and false in production builds (npm run build). The UploadForm uses this to switch between the direct-ingest dev path and the S3 presigned-URL production path.

16 The 204 No Content problem

HTTP 204 means "success, but there is no body to return." The browser's fetch API still returns a Response object for 204 responses, but calling resp.json() on an empty body throws a SyntaxError. The request<T> function handles this explicitly.

// 204 No Content — don't try to parse the body
if (resp.status === 204 || resp.headers?.get?.("content-length") === "0") {
  return undefined as unknown as T;   // callers typing void won't care
}

Both deletePatient and deleteSample are typed as returning Promise<void>. The as unknown as T cast is necessary because TypeScript does not allow returning undefined where a generic T is expected, even though the caller's void type means they will never read the value. It is the correct trade-off between type safety and practicality here.

The optional chaining (resp.headers?.get?.()) guards against test environments where the mocked response object may not have a headers property at all.
