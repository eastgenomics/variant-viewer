21 list_sample_variants — dynamic filter builder

The filter-building section of list_sample_variants (samples.py, ~lines 130–165) is the most complex piece of new logic in this PR. It constructs a WHERE clause and a parameter list dynamically based on which filter parameters were provided.

list_sample_variants Filter builder and ORDER BY construction · samples.py lines ~130–195 
    # ① Start with the mandatory filter — always present
    filter_clauses = ["v.sample_id = %s"]
    filter_params: list = [sample_id]

    if gnomad_af_max is not None:     # ② Check None, not falsy
        filter_clauses.append(
            "(v.gnomad_af IS NULL OR v.gnomad_af <= %s)"  # ③ Include nulls
        )
        filter_params.append(gnomad_af_max)

    if consequences:                   # ④ Non-empty string check
        csq_list = [c.strip() for c in consequences.split(",") if c.strip()]
        if csq_list:                    # ⑤ Guard against [""] after split
            filter_clauses.append("v.consequence = ANY(%s)")  # ⑥ PG ANY
            filter_params.append(csq_list)

    if clinvar_exclude:
        excl_list = [c.strip() for c in clinvar_exclude.split(",") if c.strip()]
        if excl_list:
            filter_clauses.append(
                "(v.clinvar_sig IS NULL OR v.clinvar_sig != ALL(%s))"  # ⑦
            )
            filter_params.append(excl_list)

    if gene:
        filter_clauses.append("v.gene ILIKE %s")    # ⑧ Case-insensitive
        filter_params.append(gene)

    where_sql = " AND ".join(filter_clauses)     # ⑨ Join all clauses

    SORTABLE = {                                  # ⑩ Whitelist
        "chrom": "chrom_order, v.pos",
        "gene":  "v.gene",
        "gnomad_af": "v.gnomad_af",
    }
    order_col = SORTABLE.get(sort_by, "chrom_order, v.pos")  # ⑪
    order_dir = "DESC" if sort_dir == "desc" else "ASC"   # ⑫

    rows = await asyncio.to_thread(
        db.query,
        f"""SELECT ... WHERE {where_sql}         -- ⑬ where_sql interpolated
        ORDER BY {order_col} {order_dir}      -- ⑭ order clauses interpolated
        LIMIT %s OFFSET %s""",               # ⑮ limit/offset parameterised
        tuple(filter_params) + (limit, offset),
    )
①
Always include the sample_id filter. This is the mandatory constraint — every query must be scoped to the requested sample. Starting the list with it means the resulting WHERE clause is never empty (which would require special-casing the JOIN logic).
②
is not None, not a truthiness check. gnomad_af_max could legitimately be 0.0 (filter to variants absent from gnomAD entirely). A truthiness check (if gnomad_af_max:) would skip the filter when the value is zero. Always use is not None for optional numeric parameters.
③
IS NULL OR gnomad_af <= threshold. Variants where gnomAD AF is NULL (absent from gnomAD databases) should pass a gnomAD filter — absence likely means the variant is rare or novel. Without the IS NULL guard, those variants would be excluded, hiding potentially significant rare variants.
④
Empty string is falsy. If the client sends consequences= (empty string), if consequences: is False and no filter clause is added. This means an empty consequences param is silently ignored — intentional behaviour documented in the spec.
⑤
Double-guard after split. "".split(",") produces [""], not []. After stripping and filtering, csq_list would be empty. Without this inner if csq_list:, an empty list would be appended and ANY('{}') would match nothing — silently returning zero variants.
⑥
PostgreSQL ANY(%s) with a list parameter. When psycopg2 receives a Python list as a parameter, it formats it as a PostgreSQL array literal: ARRAY['stop_gained','missense_variant']. = ANY(array) is PostgreSQL's way of testing membership. This is functionally equivalent to IN (?, ?) in other databases but avoids the need to generate a variable number of placeholders.
⑦
!= ALL(%s) with IS NULL guard. clinvar_sig IS NULL variants should pass the exclusion filter (not excluded because their ClinVar significance is absent, which is different from being classified as Benign). != ALL(array) is PostgreSQL's "not in array" equivalent. Without the IS NULL guard, null-clinvar variants would be dropped.
⑧
ILIKE for case-insensitive gene search. Gene names like BRCA1 may be entered as brca1 or Brca1 by the user. ILIKE is PostgreSQL's case-insensitive LIKE. No wildcard is added here — the user must supply their own % if they want prefix matching. The gene value is passed as a %s parameter (safe).
⑨
Join clauses with AND. Since the list always contains at least one clause (the mandatory sample_id filter), " AND ".join() always produces valid SQL. Result example: v.sample_id = %s AND (v.gnomad_af IS NULL OR v.gnomad_af <= %s) AND v.gene ILIKE %s.
⑩
SORTABLE is a source-code dictionary. Its keys are the exact values that sort_by may take (enforced by the pattern= regex in Query()). Its values are SQL fragments that will be interpolated into the ORDER BY clause. These are string literals written by a developer, never derived from user input.
⑪
SORTABLE.get(sort_by, default). The default handles the case where sort_by == "chrom" — the chrom sort requires two sub-columns (chrom_order from the CASE expression, then v.pos within a chromosome). The .get() fallback also provides a safe default if the regex ever allowed a value not in the dict.
⑫
Ternary over two literals. order_dir can only ever be the string "DESC" or "ASC" — both are source-code literals. The input sort_dir is compared to the string "desc" (validated by pattern=^(asc|desc)$). No user string ever reaches the SQL.
⑬
where_sql interpolated into the f-string. This is the assembled WHERE clause from step ⑨. It contains only SQL fragments and %s placeholders. All actual user values are in filter_params and are passed as parameters (not interpolated).
⑭
order_col and order_dir interpolated. These are safe because they came from the SORTABLE dict and the ternary respectively — neither can contain user-supplied strings. A SQL injection attempt via sort_by is caught at the Query(pattern=) layer before this code runs.
⑮
LIMIT and OFFSET are parameterised. Even though they are always integers validated by Query(ge=, le=), they are passed as %s parameters, not interpolated. This is belt-and-braces: mixing interpolation and parameterisation for different parts of the same query would be confusing to maintain.

22 delete_patient — sentinel cascade

The delete_patient function demonstrates the sentinel exception pattern, the transaction callback, and the deliberate ordering of DELETE statements and the audit INSERT.

delete_patient Sentinel pattern + cascade delete + audit · patients.py lines 124–159 
class _PatientNotFound(Exception):     # ①
    pass

@router.delete("/{patient_id}", status_code=204)
async def delete_patient(patient_id: int):
    def _do(conn):                         # ②
        with conn.cursor() as c:
            c.execute(
                "SELECT id FROM patients WHERE id = %s",
                (patient_id,)              # ③
            )
            if not c.fetchone():
                raise _PatientNotFound()   # ④

            c.execute(                     # ⑤
                "DELETE FROM variants WHERE sample_id IN "
                "(SELECT id FROM samples WHERE patient_id = %s)",
                (patient_id,)
            )
            c.execute(                     # ⑥
                "DELETE FROM workflow WHERE sample_id IN "
                "(SELECT id FROM samples WHERE patient_id = %s)",
                (patient_id,)
            )
            c.execute(                     # ⑦
                "DELETE FROM samples WHERE patient_id = %s",
                (patient_id,)
            )
            c.execute(                     # ⑧
                "INSERT INTO audit_log ..."
                "VALUES (%s, 'delete_patient', 'patient', %s, NULL, NULL)",
                ("system", patient_id)
            )
            c.execute(                     # ⑨
                "DELETE FROM patients WHERE id = %s",
                (patient_id,)
            )

    try:
        await asyncio.to_thread(db.run_in_transaction, _do)  # ⑩
    except _PatientNotFound:
        raise HTTPException(status_code=404, ...)  # ⑪
①
Module-level sentinel class. Declared at module level so both the _do closure and the handler can reference it. The leading underscore marks it as an implementation detail. It extends plain Exception with no added fields — the type alone carries the meaning.
②
Inner function (closure). _do is defined inside delete_patient. It captures patient_id from the outer scope. It is a plain synchronous function — psycopg2 is synchronous and must run in a thread, not in the event loop.
③
Existence check before any deletes. This SELECT runs inside the transaction, so if the row is deleted between this check and the subsequent DELETEs by another concurrent request, the DELETEs simply affect zero rows — no error. The existence check is primarily for user-facing correctness (returning 404 vs silently doing nothing).
④
Raise the sentinel, not HTTPException. If this raised HTTPException(404), it would propagate from the thread back to asyncio.to_thread, then to the await — but FastAPI's exception handler is set up in the event loop context, not in the thread. The result would be a 500 Internal Server Error. The sentinel is caught after the thread completes, in the async handler where FastAPI can process it correctly.
⑤
Delete variants first. The variants table has a foreign key to samples. Attempting to delete samples before their variants would fail with a foreign key constraint violation. The subquery SELECT id FROM samples WHERE patient_id = %s finds all sample IDs for this patient in one pass.
⑥
Delete workflow rows. The workflow table also has a foreign key to samples. Like variants, it must be deleted before the sample rows.
⑦
Delete samples after their dependants. At this point all variants and workflow rows for this patient's samples have been removed, so the foreign key constraints are satisfied and this DELETE will succeed.
⑧
Audit INSERT before the patient DELETE. The audit log records entity_id = patient_id. If the patient row is deleted first, and the audit_log.entity_id column has a foreign key reference to patients.id, this INSERT would fail. Even if there is no such constraint, inserting with a patient_id that no longer exists would be logically inconsistent. The audit must precede the final delete — both remain atomic within the transaction.
⑨
Patient row deleted last. All dependent rows are gone, the audit is written. The patient row is now safe to delete. If any step above raised an exception, db.run_in_transaction rolls back the entire transaction — no partial state is left in the database.
⑩
asyncio.to_thread runs _do on a thread pool. The event loop is free to serve other requests while the thread is blocked waiting for PostgreSQL. The thread pool is managed by the event loop; the default size is the number of CPU cores × 5.
⑪
Convert sentinel to HTTP response. The _PatientNotFound exception propagates from the thread back to the await asyncio.to_thread(...)` call. The except block catches it here, in the async handler, where FastAPI can return a proper 404 response.

23 submit_classification — locked_by SQL construction

The submit_classification handler contains a subtle but important pattern: the SQL keyword NULL or NOW() is interpolated into the INSERT statement based on whether body.locked_by is Python None. This is safe precisely because the decision is made by Python code, not by user input.

submit_classification — _do closure locked_by nullable INSERT · classification.py lines ~148–190 
    def _do(conn) -> int:
        with conn.cursor() as c:
            c.execute(                                   # ①
                "UPDATE variant_classification SET deleted_at=NOW() "
                "WHERE variant_id=%s AND deleted_at IS NULL",
                (variant_id,)
            )

            # ② Decide the SQL fragment based on Python None check
            locked_at_sql = "NOW()" if body.locked_by is not None else "NULL"

            c.execute(                                   # ③
                "INSERT INTO variant_classification "
                "(variant_id, framework, framework_version, score, classification, "
                "locked_at, locked_by) "
                f"VALUES (%s, %s, %s, %s, %s, {locked_at_sql}, %s) RETURNING id",
                (
                    variant_id,
                    body.framework,
                    framework_version,
                    result.score,
                    result.classification,
                    body.locked_by,              # ④
                ),
            )
            classification_id: int = c.fetchone()[0]

            for crit in body.criteria:       # ⑤
                c.execute(
                    "INSERT INTO classification_criterion (...) VALUES (%s,...,%s,...)",
                    (
                        classification_id,
                        crit.criterion_code,
                        crit.applied,
                        crit.strength,
                        crit.notes,
                        psycopg2.extras.Json(crit.evidence_links),  # ⑥
                        crit.pre_computed,
                        crit.pre_computed_value,
                    ),
                )
        return classification_id
①
Soft-delete the existing active classification. A variant can only have one active classification (one with deleted_at IS NULL). Before inserting a new one, the existing one is soft-deleted by setting deleted_at = NOW(). This preserves the historical record while making the new one the active classification.
②
The locked_at SQL fragment is determined in Python. body.locked_by is either None (Python None, set by the JSON null value) or a non-empty string (validated by the field validator). The ternary produces either the SQL keyword "NOW()" or "NULL" — both are string literals written by a developer. No user-supplied string reaches this interpolation.
③
f-string INSERT with interpolated SQL keyword. The {locked_at_sql} expands to either NOW() or NULL — SQL function calls, not parameter placeholders. This is necessary because %s can only represent values, not SQL expressions like function calls. The pattern is safe because locked_at_sql can never contain user input.
④
locked_by is the last parameter. The user-supplied string (or Python None, which psycopg2 serialises as SQL NULL) is always passed as a %s parameter — never interpolated. There are therefore seven parameters for seven %s placeholders in the VALUES clause. The locked_at column does not consume a parameter slot because it uses the literal SQL expression.
⑤
One INSERT per criterion. Criteria are stored individually in classification_criterion, not as a JSON blob in the classification row. This allows future queries to filter or group by criterion code, strength, or pre-computed status without parsing JSON.
⑥
psycopg2.extras.Json(list) for JSONB column. The evidence_links column is JSONB. Without the Json() wrapper, psycopg2 would try to bind a Python list as a PostgreSQL ARRAY, which would fail because the column type is JSONB, not an array type. The Json() wrapper instructs psycopg2 to JSON-serialise the list and bind it as a JSON string, which PostgreSQL then stores as JSONB.

24 ingest_direct — the _do transaction pipeline

The ingest_direct function's transaction callback is the most complex single block of code in this PR. It writes seven different tables in a carefully ordered sequence. Each step builds on the primary keys returned by the previous INSERT.

ingest_direct — _do closure Full write pipeline: patient → sample → variants → classification → criteria → workflow → audit · ingest.py lines ~133–220 
    def _do(conn):
        with conn.cursor() as cur:

            cur.execute("""INSERT INTO patients (lab_number)      # ①
               VALUES (%s)
               ON CONFLICT (lab_number) DO UPDATE
                 SET lab_number = EXCLUDED.lab_number
               RETURNING id""", (lab_number,))
            patient_id: int = cur.fetchone()[0]             # ②

            cur.execute("SELECT id FROM samples WHERE             # ③
               patient_id = %s AND name = %s AND s3_key = %s",
               (patient_id, specimen_name, f"direct:{vcf_name}"))
            if cur.fetchone():
                raise DuplicateSubmissionError(...)           # ④

            cur.execute("""INSERT INTO samples                     # ⑤
               (patient_id, name, vcf_filename, s3_key, ...)
               VALUES (%s, %s, %s, %s, %s, %s, %s)
               RETURNING id""", (patient_id, specimen_name,
               vcf_name, f"direct:{vcf_name}", ...))
            sample_id: int = cur.fetchone()[0]

            for v in variants:                              # ⑥
                cur.execute("""INSERT INTO variants (...) RETURNING id""", ...)
                variant_id: int = cur.fetchone()[0]       # ⑦

                framework, _ = select_framework(case_type, v.gene)  # ⑧
                framework_version = get_framework_version(framework)
                cur.execute(                                  # ⑨
                    "INSERT INTO variant_classification "
                    "(variant_id, framework, framework_version) "
                    "VALUES (%s, %s, %s) RETURNING id", ...)
                classification_id: int = cur.fetchone()[0]

                for suggestion in pre_compute_criteria(v, case_type):  # ⑩
                    cur.execute(
                        "INSERT INTO classification_criterion "
                        "(..., applied, ..., pre_computed, pre_computed_value) "
                        "VALUES (%s, %s, FALSE, %s, TRUE, %s)",  # ⑪
                        (classification_id, suggestion.criterion_code, ...)
                    )

            cur.execute(                                       # ⑫
                "INSERT INTO workflow (sample_id, status) VALUES (%s, 'pending')",
                (sample_id,)
            )
            cur.execute(                                       # ⑬
                "INSERT INTO audit_log (...) VALUES (%s, 'ingest_direct', ...)",
                (user_id, sample_id)
            )
            return sample_id
①
UPSERT patient by lab_number. The same patient may be submitted multiple times (e.g. multiple specimens over time). ON CONFLICT (lab_number) DO UPDATE SET lab_number = EXCLUDED.lab_number is a no-op update that still triggers the RETURNING id clause, ensuring we always get the existing patient's id. A plain INSERT would fail with a unique constraint violation on re-submission.
②
RETURNING id fetched immediately. PostgreSQL's RETURNING clause emits the newly generated or existing primary key back to the client without a second query. cur.fetchone()[0] retrieves the single integer. This pattern repeats for every INSERT in the closure.
③
Idempotency check on s3_key sentinel. Direct uploads use "direct:{vcf_filename}" as the s3_key (a sentinel value). If the same filename is uploaded again for the same patient and specimen, this query finds the existing row and the DuplicateSubmissionError is raised. The check must happen inside the transaction so it is serialised correctly against concurrent uploads.
④
DuplicateSubmissionError escapes the closure cleanly. This is the existing exception class from lib/ingest.py. Unlike _PatientNotFound, it is imported (not a local sentinel) because it is also used by manual_ingest and the async handler catches it in both cases to return a 409.
⑤
s3_key = "direct:{vcf_name}". The samples table has a UNIQUE constraint on s3_key. For direct uploads there is no S3 key, so a distinguishable sentinel string is used instead. This approach allows the idempotency check at ③ to work correctly across S3 and direct uploads using the same column.
⑥
One loop iteration per variant. The variants list was populated by parse_vcf() before the closure was called. Parsing happens outside the transaction intentionally — it may take seconds for large files, and holding a transaction open during parsing would hold database locks unnecessarily.
⑦
variant_id fetched per variant. Each INSERT returns the new row's id via RETURNING. This id is immediately used to insert the classification shell and criteria for that variant — the foreign key relationship means the variant must exist before the classification shell can reference it.
⑧
select_framework per variant. The classification framework is determined per-variant based on case_type (from the form field) and the variant's gene (from the VCF INFO). Germline variants in CanVIG-UK genes use ACGS SNV; all somatic variants use SVIG-UK. This mirrors what the production ingest path does.
⑨
Classification shell without score or criteria. The INSERT only specifies variant_id, framework, and framework_version. The score, classification, locked_at, and locked_by columns default to NULL. This shell exists so the analyst can see the framework assignment and pre-computed criteria when they first open the classification panel.
⑩
pre_compute_criteria(v, case_type) returns suggestions. This function analyses the variant's annotation fields (gnomAD AF, ClinVar significance, etc.) and returns a list of criterion suggestions — e.g. BA1 (stand-alone benign) if gnomAD AF is above the threshold. Each suggestion has a criterion code, a suggested strength, and a pre-computed value string.
⑪
applied = FALSE for pre-computed criteria. Pre-computed criteria are stored as suggestions, not as applied criteria. The analyst can accept them (setting applied = TRUE via the classification panel) or leave them unapplied. They appear in the UI with a purple badge indicating their pre-computed origin.
⑫
Workflow row inserted after all variants. The workflow row (with status 'pending') is a sample-level record, inserted once regardless of how many variants the sample has. It is inserted after all variant rows to ensure the variant data is present before the sample appears in the patient list as 'pending' review.
⑬
Audit log inserted last (before return). Records who triggered the direct ingest and which sample was created. Returning sample_id from the closure allows the async handler to include it in the response without any additional database query.
