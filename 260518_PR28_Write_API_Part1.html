01 What this PR delivers

PR 28 completes the HTTP API layer for the Variant Viewer backend. The preceding PRs (2–6) built the underlying machinery — database connection pool, VCF parser, classification engine, Lambda ingest pipeline, authentication middleware, and read-only query routes. This PR adds the write side: everything a user needs to submit data, advance a clinical review, and record a classification decision.

Four new route modules are added, each in its own file under backend/app/routes/. Together they expose six HTTP endpoints and implement three significant patterns: presigned S3 URL generation, a four-state workflow machine with optimistic concurrency control, and a soft-delete / append-only classification history.

Scope boundary

This PR adds write routes only. It does not change the DB schema, the Lambda function, the classification engine, or the authentication mechanism — all of those landed in PRs 2–6. The PR also does not add any frontend code; the React SPA is scheduled for PRs 8–11.

02 Tech stack

If you are coming to this codebase fresh, the following libraries will appear throughout the code. This section explains what each one does and why it is used here — before you need to understand any particular function.

FastAPI
Web framework

A Python web framework that turns annotated functions into HTTP endpoints. You declare what a route expects (path parameters, a JSON body, a header) using Python type hints, and FastAPI handles parsing, validation, and error responses automatically. It is built on Starlette (the async HTTP layer) and uses Pydantic for data validation.

async-native
Pydantic v2
Data validation

When the server receives a JSON body, Pydantic checks that all required fields are present, that types match, and that any constraints (e.g. Literal["acgs_snv", "svig"]) are satisfied — returning a structured Python object if valid, or an automatic 422 response if not. Think of it as a schema enforcer at the boundary.

type-safe
boto3
AWS SDK for Python

The official Python library for interacting with AWS services. In this PR it is used in two ways: boto3.client("s3") to generate presigned URLs that allow a browser to PUT files directly to S3, and implicitly by the auth and DB modules to resolve secrets from AWS Secrets Manager.

AWS SDK
psycopg2
PostgreSQL driver

A synchronous Python library for talking to PostgreSQL. All DB reads and writes go through it. Because it is synchronous (blocking), the routes use asyncio.to_thread() to run DB work on a background thread so the async event loop stays responsive. psycopg2.extras.Json() is used to serialise Python lists to PostgreSQL JSONB columns correctly.

sync driver
asyncio
Python async runtime

Python's built-in concurrency library. FastAPI routes are declared async def, meaning they can yield control while waiting for I/O (network, disk) without blocking other requests. The key function used here is asyncio.to_thread(fn), which runs a blocking function in a thread pool and awaits the result without stalling the event loop.

concurrency
auth middleware
API key validation (PR 6)

Every write route carries dependencies=[Depends(require_api_key)]. FastAPI calls the require_api_key dependency before the route handler runs. It reads the X-API-Key header, compares it against the resolved key (from API_KEY env var or AWS Secrets Manager) using secrets.compare_digest to prevent timing attacks, and returns 401 if the key is absent or wrong.

security

03 Request lifecycle

Every write request goes through the same sequence of stages. Understanding this sequence is the key to reading any of the four route modules — they all follow the same pattern, varying only in which stages involve S3 versus DB versus the classification engine.

Stage-by-stage breakdown

① Auth check
FastAPI dependency injectionEvery router in this PR declares dependencies=[Depends(require_api_key)]. FastAPI calls this before the route function body runs. If the header is missing or wrong, a 401 is returned immediately — no route logic executes.
② Pydantic parse
Automatic schema enforcementFastAPI passes the JSON request body through the route's Pydantic model. If required fields are missing or types are wrong (e.g. "framework": "unknown" when only "acgs_snv" or "svig" are valid), FastAPI returns a 422 with a detailed error — before any handler code runs.
③ Route guards
Business-rule validationEach handler applies additional checks that Pydantic cannot express: file extension validation (_VCF_RE), path-traversal rejection, calendar-valid date parsing via strptime, env-var presence, and workflow state-machine legality. These run synchronously in the async event loop — they do no I/O so this is fine.
④ to_thread
Blocking I/O off the event loopDatabase queries and S3 calls are synchronous (blocking). If run directly in an async def function they would freeze the event loop, preventing any other request from being handled. await asyncio.to_thread(fn, arg) runs fn(arg) in a thread pool and awaits the result without blocking.
⑤ Exception map
Domain exceptions → HTTP status codesEach handler wraps the to_thread call in a try/except block that converts known domain exceptions to appropriate HTTP responses: DuplicateSubmissionError → 409, UniqueViolation → 409, ValueError → 400, _ConcurrentModification → 409.

05 Module structure & conventions

File organisation

Each route module follows the same top-to-bottom layout:

  1. Module docstring — lists every HTTP endpoint the file exposes
  2. Imports — standard library, then third-party, then internal (app.lib.*, app.middleware.*)
  3. Module-level constants — compiled regexes (_VCF_RE, _DATE_RE), expiry constants, state machine dicts
  4. Router declaration — router = APIRouter(prefix=…, dependencies=[Depends(require_api_key)])
  5. Pydantic models — request and response classes
  6. Private helpers — underscore-prefixed functions that support the handlers
  7. Route handlers — the public async def functions decorated with @router.post/put/delete

Naming conventions

The _do closure pattern

Three of the four handlers (manual_ingest, update_workflow, submit_classification, reset_classification) use the same structural pattern: an inner function _do(conn) is defined inside the route handler, capturing the validated request fields from the outer scope via closure. This function is then passed to db.run_in_transaction — which opens a connection, calls _do(conn), and commits or rolls back. The pattern cleanly separates "what SQL to run" from "how to manage the transaction".

Design rationale

The _do closure raises only domain exceptions (like _ConcurrentModification), never HTTPException. The outer route handler catches domain exceptions and converts them to HTTP status codes. This keeps the DB layer free of HTTP knowledge — a deliberate architectural boundary.
