17 display-utils.ts — Format functions

frontend/src/lib/display-utils.tsLines 1–33

Seven small pure functions. Four format a number or date to a display string; three return a Tailwind CSS class based on a value. All return a safe default (em-dash or "absent" or "text-gray-700") when the input is null or undefined — they never throw.

formatYearOfBirth L1–5 display-utils

Extracts the 4-digit year from an ISO date string. Handles both full dates ("1990-05-14") and year-only strings ("1990"). Returns em-dash for null or undefined.

Input

  • dob: string | null | undefined

Output

  • string — "1990", or "—"
const match = dob.match(/^(\d{4})(?:-|$)/);
return match ? match[1] : "—";

The regex captures exactly 4 digits at the start of the string, followed by either a dash (full ISO date) or end of string (year-only). Group 1 is the year.

Privacy note

This function is intentionally the only function that shows any patient age-related information. The full date of birth is never displayed; only the year is shown, and even then only in limited contexts. The dob column was dropped from the database by migration 004 — this function is kept for any future re-introduction.

formatGnomadAf L7–11 display-utils

Formats a gnomAD allele frequency for display. Very small values (below 0.0001) use scientific notation to avoid strings like "0.0000" that look like zero. Returns "absent" (not em-dash) for null because an absent value in gnomAD is clinically meaningful — it means the variant was not observed in the reference population.

Input

  • af: number | null

Output

  • "absent", "1.00e-5", or "0.0123"

Boundary case: af = 0.0001 returns "0.0001" (4 decimal places, not scientific). The check is af < 0.0001 (strictly less than), so the boundary value itself uses the regular format.

formatRevel / formatSpliceAi L13–19 display-utils

Identical pattern: 3 decimal places, or em-dash for null. REVEL and SpliceAI scores are always in [0, 1]; 3dp gives enough precision to distinguish values without being noisy.

18 display-utils.ts — CSS class helpers

gnomadAfClass L21–23 display-utils

Returns "text-amber-600" if the allele frequency exceeds 1% (0.01), otherwise "text-gray-700". The 1% threshold is a rough population-frequency filter: common variants (AF > 1%) are unlikely to be disease-causing, so they are highlighted amber to draw the analyst's eye for potential de-prioritisation.

Design decision

Null returns the neutral gray class rather than a distinct "unknown" class. Missing gnomAD data is common for rare or novel variants and should not be visually alarming — the "absent" label from formatGnomadAf already communicates absence.

revelClass L25–30 display-utils

REVEL scores range 0–1. Scores ≥ 0.7 indicate computational evidence for pathogenicity (red); ≤ 0.4 indicate evidence against (green); between 0.4 and 0.7 are inconclusive (gray). These thresholds match the ACGS recommended REVEL cutoffs.

spliceAiClass L32–33 display-utils

SpliceAI delta scores ≥ 0.5 indicate a strong splice-site effect (orange); below 0.5 they are considered low-risk (gray). The orange colour distinguishes splice effects from the red used for REVEL pathogenic scores.

19 classification-engine.ts — Private helpers

frontend/src/lib/classification-engine.tsLines 1–80
classifyAcgs not exported private

Applies the ACGS SNV score threshold table. The hasBA1 parameter is checked first because BA1 overrides the score — even a score of +50 returns Benign if BA1 was applied. Called only from classify() after the BA1 sentinel check confirms BA1 is not present, so in practice hasBA1 will always be false here; the parameter exists to mirror the Python backend's structure exactly.

classifySvig not exported private

Applies the SVIG-UK threshold table, respecting sentinel priority O1 > B1 > B2 > point thresholds. The priority order is a deliberate departure from B2 being checked first in an earlier draft — if both O1 and B2 are applied, the variant is Oncogenic, not VUS.

getCriterionDirection not exported private

Determines whether a criterion code contributes pathogenic, benign, or oncogenic points, based on its prefix. Uses regex matching to classify the prefix: /^(PVS|PS|PM|PP)/ → pathogenic (ACGS); /^(BA|BS|BP)/ → benign (ACGS); /^O/ → oncogenic (SVIG); /^B/ → benign (SVIG). Returns null for unrecognised codes (which are silently skipped).

Difference from Python

The Python backend raises a ValueError on unrecognised codes ("typos fail loud"). The TypeScript engine returns null and skips unknown codes silently. This is a deliberate frontend trade-off: the UI receives criteria codes from the database (which were validated by the backend at ingest time), so unrecognised codes should not crash the UI — they simply contribute zero points.

20 classification-engine.ts — classify()

classify L96–162 core engine

The central function. Takes the full array of criteria (applied and unapplied), the framework, and the combination rules. Returns score, classification label, and any warnings. This function is covered in detail in Part 4 (line-by-line reference).

Inputs

  • criteria: AppliedCriterion[] — all criteria, applied or not
  • framework: Framework — "acgs_snv" or "svig"
  • combinationRules: CombinationRule[] — conflict rules from config

Output

  • ClassificationResult
  • score: integer (or ±999 for sentinels)
  • classification: e.g. "Likely_Pathogenic"
  • warnings: string array

Algorithm steps

  1. Filter to applied criteria only (criteria.filter(c => c.applied))
  2. Build a Set of applied codes for O(1) combination-rule checking
  3. Check all combination rules; append messages to warnings array
  4. Check for sentinel codes (BA1 for ACGS; O1/B1/B2 for SVIG) — return immediately if found
  5. Sum points using STRENGTH_POINTS (pathogenic/oncogenic) or BENIGN_STRENGTH_POINTS (benign)
  6. Check minimum-criteria warning for ACGS (≥2 required for non-VUS)
  7. Apply threshold table via classifyAcgs() or classifySvig()

21 classification-engine.ts — selectFramework() and display helpers

selectFramework L164–178 framework selection

Returns the correct framework and a boolean indicating whether the gene is in the CanVIG panel. The CanVIG set is loaded at module initialisation and stored as a JavaScript Set for O(1) membership checks. Gene names are normalised to uppercase before lookup.

Inputs

  • caseType: "germline" | "somatic"
  • gene: string | null

Output

  • {framework: Framework, isCanvig: boolean}

The CANVIG_GENE_SET constant (module-level) is computed once when the module is first imported. It reads from the bundled JSON and builds a Set<string> of uppercase gene symbols. The 33 CanVIG genes include BRCA1, BRCA2, TP53, MLH1, MSH2, and others on the CanVIG-Germline panel.

classificationLabel / classificationBadgeClass L180–217 display helpers

classificationLabel converts internal label strings to display text. "Likely_Pathogenic" → "Likely Pathogenic" (underscore removed, proper spacing). Returns em-dash for null. Unknown strings pass through unchanged (future-proof for new classifications).

classificationBadgeClass maps a classification string to the CSS suffix used for the badge component: "Pathogenic" → "pathogenic" (used as class="badge badge-pathogenic" in the UI). Falls back to "vus" for null or unknown values — the neutral badge style.

22 api.ts — ApiError class

frontend/src/lib/api.ts
ApiError exported class error type

Extends the built-in Error class with two additional properties: status (the HTTP status code, e.g. 401, 409) and detail (the error message from the backend's JSON {"detail": "..."} response body). Components catch ApiError and use its properties to show appropriate error messages or handle specific status codes.

class ApiError extends Error {
  constructor(public readonly status: number, public readonly detail: string) {
    super(detail);   // sets this.message = detail
    this.name = "ApiError";
  }
}

The public readonly shorthand in the constructor parameters automatically creates and assigns class properties — no need for separate property declarations. Setting this.name ensures error.toString() shows "ApiError: message" rather than "Error: message", which helps in test assertions.

23 api.ts — authHeaders() and request()

authHeaders exported auth

Returns a headers object containing X-API-Key when VITE_API_KEY is set; empty object otherwise. Reading the env var at call time (not module load) means tests can stub it between test cases. Exported so components making direct fetch() calls (e.g. VariantTable) can use the same auth without duplicating the logic.

request<T> private HTTP client

The internal HTTP client that all public endpoint functions call. Merges auth headers, checks resp.ok, throws ApiError on failure, handles 204 No Content, and returns the JSON-decoded body typed as T. Covered in detail in Part 4.

24 api.ts — Patient and sample endpoints

listPatients exported read

Builds a query string from the optional search, limit, and offset parameters using URLSearchParams. Parameters are only appended if defined — this avoids sending ?search=&limit=undefined to the backend. Returns a paginated response with items, total, limit, and offset.

deletePatient / deleteSample exported write

Both issue a DELETE request and return void (the backend responds with 204 No Content). The await request(...) call is not assigned to anything — the return value is discarded. If the request fails, request() throws an ApiError which propagates to the caller.

25 api.ts — Variant endpoints

listVariants exported read

Accepts an optional VariantFilterParams object (which extends PipelineFilters via Partial<>). The parameter serialisation loop skips null and empty-string values, which matters for the gnomad_af_max: null case when the user clears the filter field.

Object.entries(params).forEach(([k, v]) => {
  if (v != null && v !== "") q.set(k, String(v));   // skip null and ""
});

Note: v != null uses loose equality, which catches both null and undefined in one check.

26 api.ts — Upload, workflow, and classification

updateWorkflow exported workflow

Issues a PUT to /api/workflow/{sampleId} with {status, user_id} as JSON body. The userId is recorded in the audit log on the backend. The WorkflowStatus type ("pending" | "reviewing" | "reported" | "archived") ensures the caller cannot pass an invalid status — TypeScript will report a compile error.

putClassification exported classification

Issues a PUT to persist a classification. The key field is ClassifyPersistPayload.locked_by: when null, the backend stores a draft (no locked_at timestamp); when a non-empty string (the analyst's user ID), the backend sets locked_at = NOW(). This is the draft-vs-confirm distinction that Invariant 2 of the clinical safety requirements depends on.

resetClassification exported classification

Soft-deletes the current active classification and inserts a blank replacement. Uses a DELETE request with a body ({user_id}) — unusual but permitted by HTTP and supported by the FastAPI backend. Returns {new_classification_id} which the component uses to update its local state.

27 pipeline-config.ts

frontend/src/lib/pipeline-config.tsLines 1–25
getPipelineDefaults L11–17 config

Looks up the default filter configuration for a pipeline key. Uses the optional chaining (?.) and nullish coalescing (??) operators to handle a null/unknown key gracefully. If the pipeline key is null or not found in the JSON, returns a conservative default: 1% AF threshold, empty consequence filter, empty ClinVar exclusion filter.

const config = pipelineKey ? pipelines[pipelineKey] : null;
return config?.default_filters ?? { gnomad_af_max: 0.01, consequences: "", clinvar_exclude: "" };

config?.default_filters: if config is null (unknown pipeline), evaluates to undefined. The ?? then supplies the fallback object. This single line replaces an if/else block.

getPipelineOptions L19–23 config

Converts the pipelines.json object into an array of {key, label} pairs suitable for a <select> element. Object.entries() returns an array of [key, value] tuples; the .map() picks just the key and the label from each tuple.

28 fhir-manifest.ts — buildManifest()

frontend/src/lib/fhir-manifest.tsLines 1–56
buildManifest L13–56 upload

Constructs a FHIR R4 collection Bundle from the upload form's field values. Returns a plain JavaScript object — the caller is responsible for JSON-stringifying it and uploading it to the presigned S3 manifest URL.

Input

  • labNumber
  • specimenName
  • caseType: "germline" | "somatic"
  • pipelineKey: string | null
  • sequencingDate: string | null
  • vcfFilename

Output

  • FhirBundle object with 3 entries: Patient, Specimen, Task

Key design points

  • The Patient resource uses only the NHS Lab System identifier (https://fhir.example-lab.org/Id/lab-number). Name and NHS number are deliberately omitted.
  • The Specimen collection field is conditionally included — sequencingDate ? {...} : undefined. When the field is undefined, JSON.stringify() omits it entirely from the output.
  • The case type is stored as a custom FHIR extension on the Specimen resource using the CASE_TYPE_EXT URL. The backend's parse_manifest() looks for this exact extension URL.
  • The Task code field is pipelineKey ? {text: pipelineKey} : undefined — optional, same pattern as collection.
Backend compatibility

The backend's parse_manifest() in app/lib/fhir_manifest.py navigates this exact JSON structure to extract patient lab number, specimen name, case type, pipeline key, sequencing date, and VCF filename. The constants NHS_LAB_SYSTEM and CASE_TYPE_EXT must match the corresponding constants in the Python file precisely. The 9 fhir-manifest tests verify the bundle shape; the backend integration tests verify the round-trip.
