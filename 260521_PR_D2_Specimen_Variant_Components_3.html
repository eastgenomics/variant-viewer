12 SpecimenCard

SpecimenCard.tsx
82 lines · container component
SpecimenCard lines 10–82 Container

Purpose: Top-level card for one sample. Renders a metadata header row (specimen name, case type badge, pipeline badge, workflow badge, variant count) plus optional tissue/date metadata, then embeds WorkflowControl, DeleteSampleButton, and VariantTable.

Props (inputs)

  • specimen: SampleDetail — full sample object from API
  • patientId: number — passed through to VariantTable for Classify links
  • onDeleteSample?: (id: number) => void — optional callback fired after successful deletion

Outputs (JSX)

  • Outer <div> containing a metadata card and VariantTable
  • No local state — purely derived from props

Key logic

1. Memoize defaultFilters. useMemo(() => getPipelineDefaults(specimen.pipeline_key), [specimen.pipeline_key]) ensures the PipelineFilters object keeps a stable reference across re-renders (see Part 2 for why this matters). getPipelineDefaults reads from the bundled pipelines.json and returns an object — without memo, a new object reference on every render would cause VariantTable to reset its filters unnecessarily.

2. Conditional metadata row. The tissue and date row only renders when at least one value is non-null: {(specimen.tissue || specimen.sequencing_date) && (...)}. This avoids an empty row in the card layout for samples where this metadata was not supplied.

3. Callback relay. onDeleteSample (the name used in SpecimenCard's props) is passed directly to DeleteSampleButton as onDelete. SpecimenCard does not maintain any list state itself — it simply relays the callback from the parent page down to the delete button.

Design decision: no state in SpecimenCard

SpecimenCard is intentionally stateless. All mutable state — the current workflow status, whether deletion is pending, the variant rows — lives in the child components closest to the data. This keeps SpecimenCard predictable and easy to test: the three tests in SpecimenCard.test.tsx need only mount it with a fixture and assert on the rendered output.

13 WorkflowControl

WorkflowControl.tsx
57 lines · workflow state machine UI
WorkflowControl lines 12–57 Mutation

Purpose: Renders a row of buttons for each allowed workflow transition from the current status. When clicked, calls the backend and updates local status on success. Shows an inline error message on failure.

Props (inputs)

  • sampleId: number — passed to updateWorkflow API call
  • currentStatus: string — initial value for local status state; also synced via useEffect

Local state

  • status — current displayed status (starts from prop, updated on success)
  • loading — disables all buttons during an in-flight request
  • error — inline error string, cleared on each new attempt

The prop-sync useEffect

useEffect(() => { setStatus(currentStatus); }, [currentStatus]) ensures that if the parent page refreshes the specimen data (e.g. after navigating away and back), the displayed status reflects the new value from the server — not a stale value from a previous transition. Without this, status would be frozen at the value it had when the component first mounted.

Potential race condition

If the user triggers a transition and the parent component refreshes currentStatus from the server concurrently, the useEffect and handleTransition success path might both call setStatus on the same render cycle. In practice this is benign — both would set the same (new) status — but it is worth noting for reviewers.

handleTransition lines 27–36 Mutation

Purpose: Async function called when a transition button is clicked. Calls the API, updates local status on success, sets error string on failure, clears loading in all cases.

Inputs

  • newStatus: WorkflowStatus — one of the values from TRANSITIONS[status]

Side effects

  • Calls PUT /api/workflow/{id}
  • Sets status, loading, error state

User ID source: import.meta.env.VITE_USER_ID ?? "analyst" — reads from Vite's environment injection, falling back to the literal string "analyst" in development. This value is recorded in the backend's audit log for the transition.

Error handling: The catch block checks err instanceof Error before accessing err.message — this is necessary because anything can be thrown in JavaScript (not just Error subclasses). ApiError extends Error, so error messages from the API surface correctly.

14 DeleteSampleButton

DeleteSampleButton.tsx
71 lines · two-phase destructive action
DeleteSampleButton lines 4–71 Mutation

Purpose: A button that requires two interactions to execute a DELETE. The first click shows a confirmation bar; the second click executes the deletion. The confirmation bar shows different content depending on whether the specimen is in a high-risk state.

Props

  • id: number — sample ID for the API call
  • name: string — specimen name shown in confirmation text
  • workflowStatus: string — determines high-risk warning
  • onDelete?: (id: number) => void — called after successful delete

Local state

  • confirming — toggles between trigger and confirmation bar
  • busy — disables buttons during API call
  • deleteError — inline error message; cleared on each new attempt and on cancel

The high-risk warning

isHighRisk is true when workflowStatus === "reported" || workflowStatus === "archived". In the confirming state, the component renders different confirmation text depending on this flag:

  • High risk: amber warning "⚠ This specimen has been reported/archived." — signals that deleting has audit implications
  • Normal: neutral "Delete SPEC_001?" — uses the specimen name

There is no hard server-side block for high-risk statuses — the backend returns 204 regardless. The warning is a UX safeguard. The backend's audit log records the deletion either way.

Silent failure prevention

The delete confirmation does not close on API failure. The finally block only sets busy = false; the catch block sets deleteError and the component stays in the confirming state. This means the user sees the error inline and can try again or cancel — they are never left wondering whether the deletion succeeded.

Callback chain

On success, the component calls onDelete?.(id) (the optional chaining ?. means it is safe to call even when no callback is provided) and then sets confirming = false. In the normal use case — inside SpecimenCard inside PatientDetailPage — the callback removes the specimen from the page's state array, causing the SpecimenCard to unmount. The component does not need to reset its own state after success because it will no longer exist.

15 COLUMNS constant

VariantTable.tsx
lines 19–98 · module-level column definitions

The COLUMNS array is declared at module level, not inside the component. This is intentional: TanStack Table compares the columns reference on each render to decide whether to rebuild its internal model. Declaring at module level gives a constant reference — the same array object for the lifetime of the module. Declaring inside the component would create a new array on every render, forcing TanStack to rebuild unnecessarily.

Each column is created with col.accessor("fieldName", { header, cell }). The accessor string tells TanStack which field to extract from each VariantRow object. The cell function receives a cell context object i; calling i.getValue() returns the typed value for that cell's accessor field.

Why display-utils are used in columns

The gnomAD AF, REVEL, and SpliceAI columns delegate formatting and colour class selection to display-utils.ts (PR C2) rather than inlining the logic. This ensures the same formatting rules apply whether a value is shown in the table or in any other context — a single source of truth.

16 VariantTable component

VariantTable.tsx
lines 102–280 · component body and JSX
VariantTable lines 102–280 Fetch + Render

Purpose: Fetches variants from the server, manages pagination and filter state, and renders a TanStack Table with a filter bar above and pagination controls below.

Props

  • sampleId: number
  • patientId: number — for Classify links
  • defaultFilters: PipelineFilters — initial filter values (memoized by parent)
  • pipelineKey: string | null — shown as a preset label in the filter bar

Local state (9 variables)

  • data: VariantRow[] — current page of variants
  • total: number — server-reported total count
  • loading: boolean
  • error: string | null
  • pageIndex: number — 0-based
  • filters: PipelineFilters
  • geneInput: string
  • sortBy, sortDir — sort state (not yet wired to column headers)

Filter reset on sample change

The component has a dedicated useEffect (lines 120–124) that runs whenever sampleId or defaultFilters changes: it resets filters to the pipeline defaults, clears the gene input, and resets pageIndex to 0. This ensures that when the user views a second specimen on the same patient page, the variant table starts fresh with the correct defaults for that specimen's pipeline.

gnomAD AF NaN guard

The gnomAD AF filter input uses type="number". When the user clears the field, parseFloat("") returns NaN. If NaN were stored in filters.gnomad_af_max and sent to the backend as a query param, it would produce the string "NaN" — an invalid float that FastAPI would reject with 400. The guard prevents this:

setFilters((f) => ({
  ...f,
  gnomad_af_max: Number.isNaN(val) ? null : val,
}));

When the field is empty, gnomad_af_max is set to null. In fetchVariants, null values are simply not added to the query string: if (filters.gnomad_af_max != null) q.set(...). The backend then returns all variants regardless of gnomAD AF, which is the user's intent when they cleared the filter.

Table instance creation

useReactTable({ data, columns: COLUMNS, getCoreRowModel: getCoreRowModel(), manualPagination: true, pageCount }) creates the table instance. getCoreRowModel() is a built-in TanStack factory that returns a row model function — it processes the data array into rows that the render logic can iterate. manualPagination: true tells TanStack not to slice data itself; the component fetches the correct page from the server and passes only that page's rows in data.

Render logic

The JSX has three conditional render paths for the table body: a loading row (full-width, colSpan), an empty-state row ("No variants match the current filters."), and the normal row iteration. The loading and empty states use colSpan={COLUMNS.length + 1} — the +1 accounts for the Classify action column added after the generated columns.

17 fetchVariants

VariantTable.tsx
lines 124–158 · useCallback-wrapped fetch
fetchVariants lines 124–158 Fetch

Purpose: Builds the query string from current filter/pagination/sort state, fetches GET /api/samples/{sampleId}/variants, and updates data, total, or error state accordingly. Wrapped in useCallback so its reference only changes when a dependency changes.

Dependencies (useCallback array)

  • sampleId
  • pageIndex
  • filters (object reference — stable via useMemo in parent)
  • geneInput
  • sortBy, sortDir

Side effects

  • Sets loading = true at start
  • Sets data, total on success
  • Sets error on failure
  • Sets loading = false in finally

Query string construction

Mandatory params (limit, offset, sort_by, sort_dir) are always included. Optional filter params are only added when they have meaningful values:

  • gnomad_af_max — only when not null (handles cleared input)
  • consequences, clinvar_exclude — only when non-empty strings
  • gene — only when the trimmed input is non-empty

authHeaders() usage

fetch(..., { headers: authHeaders() }) reads VITE_API_KEY inside the authHeaders function at call time. This is the correct pattern — it avoids capturing the key at module load time (when it might not yet be set in some test environments). It is the single point in the codebase where the API key is read for direct fetch calls.

Response parsing

json.items (not json.rows or json.data) — this matches the backend's VariantListResponse Pydantic model, which uses the field name items. json.total is the server-reported total count across all pages, used to compute pageCount.
