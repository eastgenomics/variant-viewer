20 _get_api_key() — lazy singleton with Secrets Manager fallback

File: app/middleware/auth.py · lines 19–47. The most important function for understanding how authentication works at startup.

_get_api_key() auth.py · resolves the expected API key once per process lifetime 
def _get_api_key() -> str:
    global _resolved_key                              # ①
    if _resolved_key:                                  # ②
        return _resolved_key

    arn = os.environ.get("API_KEY_SECRET_ARN")        # ③
    if arn:
        region = os.environ.get("AWS_REGION", "eu-west-2")
        sm = boto3.client("secretsmanager", region_name=region)
        resp = sm.get_secret_value(SecretId=arn)       # ④
        secret = json.loads(resp["SecretString"])     # ⑤
        if "api_key" not in secret:                   # ⑥
            raise RuntimeError(
                f"Secrets Manager secret {arn!r} must contain an 'api_key' field"
            )
        _resolved_key = secret["api_key"]             # ⑦
    else:
        _resolved_key = os.environ.get("API_KEY")    # ⑧

    if not _resolved_key:                             # ⑨
        raise RuntimeError(
            "API_KEY or API_KEY_SECRET_ARN must be set"
        )
    return _resolved_key
①
global _resolved_key — tells Python that the name _resolved_key inside this function refers to the module-level variable, not a new local. Without this, the assignment on line ⑦ or ⑧ would create a function-local variable that disappears when the function returns, and the singleton would never be cached.
②
Cache hit check — the fast path. After the first successful resolution, every subsequent call returns here immediately without touching the environment or network. This is the "lazy" part of the lazy singleton: no work is done at import time.
③
Resolution order branch — checks for the Secrets Manager ARN first. If the env var is absent, os.environ.get returns None and the if arn: branch is skipped, falling straight to the else which reads the plain env var. This gives operators the choice of two deployment modes without changing code.
④
Synchronous network call — get_secret_value makes an HTTPS request to the AWS Secrets Manager regional endpoint. This is a blocking call and runs on the FastAPI event loop thread (because _get_api_key is called from inside the async def require_api_key dependency). For ECS long-lived containers this is acceptable because it only happens once at cold start.
⑤
json.loads(resp["SecretString"]) — Secrets Manager returns the secret value as a JSON-encoded string in the SecretString key. json.loads parses it into a Python dict. The expected shape is {"api_key": "the-actual-key"}. If the operator stored the raw key without JSON-encoding it, this line would raise json.JSONDecodeError.
⑥
Field presence check — added after code review. Without this guard, secret["api_key"] on line ⑦ would raise a bare KeyError if the secret was created with a different field name (e.g. "API_KEY"). A KeyError propagates as HTTP 500 with a traceback that doesn't mention the configuration problem. The explicit RuntimeError names both the ARN and the expected field, making the misconfiguration immediately diagnosable.
⑦
Cache write — stores the resolved key in the module-level variable. All future calls to _get_api_key() in this process will return this cached value without touching Secrets Manager again.
⑧
Env var fallback — the development/CI path. The operator sets API_KEY=dev-api-key in their .env file. os.environ.get returns None if the variable is unset (not KeyError — this is the safe variant). The sentinel check on line ⑨ catches the case where the variable is set but empty.
⑨
Final sentinel — catches all paths that produced no key: neither env var was set, or API_KEY was set to an empty string. Raising here rather than letting secrets.compare_digest(None, expected) fail with a TypeError gives a much clearer error message.

21 with_transaction() — BEGIN / COMMIT / ROLLBACK context manager

File: app/lib/db.py · lines 81–92. Understanding this function is prerequisite for understanding run_in_transaction and all write routes in PR 7.

with_transaction() db.py · wraps a block of DB operations in an explicit transaction 
@contextmanager
def with_transaction() -> Generator[psycopg2.extensions.connection, None, None]:
    with _get_connection() as conn:        # ①
        try:
            conn.autocommit = False        # ②
            yield conn                     # ③
            conn.commit()                  # ④
        except Exception:
            conn.rollback()                # ⑤
            raise                          # ⑥
        finally:
            conn.autocommit = True         # ⑦
①
Nested context manager — borrows a connection from the pool. The outer with _get_connection() guarantees the connection is returned in its own finally block, even if the inner try/except raises. This nesting means you cannot leak a connection from a transaction, regardless of what the caller does.
②
conn.autocommit = False — psycopg2 connections start with autocommit off by default, but the pool may have returned a connection that was previously used in autocommit mode. Setting it explicitly here ensures the transaction is always started correctly. The paired reset on line ⑦ returns the connection to a known state before it goes back to the pool.
③
yield conn — this is where the caller's with with_transaction() as conn: body runs. The connection is in an open (implicit) transaction at this point — any cursor.execute() the caller issues is part of the transaction. Control returns here when the with body exits, either normally or via exception.
④
conn.commit() — runs only when the yield returns normally (no exception). Makes all changes durable and releases any row locks held by the transaction. After this line, the writes are visible to other transactions.
⑤
conn.rollback() — runs when any exception propagates out of the yield. Undoes all changes made since the yield. This includes partial writes — if the caller executes three INSERT statements and the third raises, the first two are also rolled back.
⑥
Bare raise — re-raises the original exception after rolling back. Without this, the exception would be swallowed and the caller would not know the transaction failed. The caller (or FastAPI's error handler) needs to see the exception to return the correct HTTP response.
⑦
finally: conn.autocommit = True — runs unconditionally on exit. Resets autocommit before the connection returns to the pool. Without this, the next caller who borrows this connection would find it in autocommit=False mode and their query() call would silently start an implicit transaction that never gets closed, eventually causing the server to run out of connections.

22 list_patients() — dynamic WHERE + pagination

File: app/routes/patients.py · lines 45–72. Shows the standard pattern for optional filtering and pagination used across the read routes.

list_patients() patients.py · GET /api/patients — paginated list with optional search 
@router.get("", response_model=PatientListResponse)
async def list_patients(
    limit: int = Query(50, ge=1, le=200),    # ①
    offset: int = Query(0, ge=0),
    search: str | None = Query(None),
):
    where = ""
    base_params: tuple = ()                    # ②
    if search:
        where = " WHERE lab_number ILIKE %s OR name ILIKE %s"
        base_params = (f"%{search}%", f"%{search}%")  # ③

    total_rows = await asyncio.to_thread(      # ④
        db.query,
        "SELECT COUNT(*) AS n FROM patients" + where,
        base_params,
    )
    total = total_rows[0]["n"]               # ⑤

    rows = await asyncio.to_thread(
        db.query,
        "SELECT id, lab_number, name FROM patients"
        + where
        + " ORDER BY lab_number LIMIT %s OFFSET %s",
        base_params + (limit, offset),          # ⑥
    )
    return PatientListResponse(
        items=[PatientSummary(**r) for r in rows],  # ⑦
        total=total,
        limit=limit,
        offset=offset,
    )
①
Query(50, ge=1, le=200) — Query is FastAPI's mechanism for declaring query parameter metadata. ge=1 means "greater than or equal to 1"; le=200 means "less than or equal to 200". FastAPI validates these constraints before calling the handler. A client sending ?limit=0 or ?limit=999 gets HTTP 422 with a clear error message — the handler never runs.
②
Conditional WHERE construction — where and base_params start empty. If search is provided, both are populated. This pattern avoids string formatting that could introduce SQL injection. The WHERE clause is concatenated as a constant string; only the search values come from user input, and they go into the params tuple where psycopg2 escapes them.
③
f"%{search}%" repeated twice — the ILIKE wildcard pattern. % is the SQL "any characters" wildcard; wrapping the search term with % on both sides gives a substring match. The pattern appears twice in base_params because the WHERE clause has two %s placeholders (one for lab_number, one for name).
④
Count query first — the total count is fetched in a separate query rather than via a window function (COUNT(*) OVER()) in the main query. This is the simpler approach: it runs two round-trips instead of one, but is easier to read and the performance difference is negligible for expected dataset sizes.
⑤
total_rows[0]["n"] — db.query always returns a list of dicts. COUNT(*) always returns exactly one row; that row has one column aliased as n. The [0]["n"] indexing extracts the integer count. If the table is empty, COUNT(*) returns 0 (not an empty list), so this is safe without a length check.
⑥
base_params + (limit, offset) — tuple concatenation appends the pagination values to the filter values. If search was provided, base_params = ("%Jane%", "%Jane%") and the final params tuple is ("%Jane%", "%Jane%", 50, 0), matching the three %s placeholders in the query (two in WHERE, two in LIMIT/OFFSET).
⑦
List comprehension with unpacking — PatientSummary(**r) unpacks each dict row as keyword arguments to the Pydantic model constructor. This works because db.query returns rows where the key names match the SQL column aliases, which in turn match the Pydantic field names exactly. Any extra keys in the dict would be silently ignored by Pydantic v2's default behaviour.

23 list_sample_variants() — existence check + soft-delete join + chromosomal sort

File: app/routes/samples.py · lines 95–148. The most operationally interesting read route; demonstrates three patterns in sequence.

list_sample_variants() samples.py · GET /api/samples/{id}/variants 
async def list_sample_variants(sample_id: int, limit: int = ..., offset: int = ...):
    sample_rows = await asyncio.to_thread(
        db.query,
        "SELECT 1 FROM samples WHERE id = %s",  # ①
        (sample_id,),
    )
    if not sample_rows:                           # ②
        raise HTTPException(status_code=404, detail="Sample not found")

    total_rows = await asyncio.to_thread(
        db.query,
        "SELECT COUNT(*) AS n FROM variants WHERE sample_id = %s",
        (sample_id,),
    )
    total = total_rows[0]["n"]

    rows = await asyncio.to_thread(
        db.query,
        """
        SELECT v.id, v.chrom, v.pos, ...,
               vc.classification, vc.score, vc.framework, vc.locked_at
        FROM variants v
        LEFT JOIN variant_classification vc      # ③
               ON vc.variant_id = v.id AND vc.deleted_at IS NULL
        WHERE v.sample_id = %s
        -- TODO: assumes bare chrom names ('1'–'22')  # ④
        ORDER BY
            CASE v.chrom
                WHEN 'X'  THEN 23
                WHEN 'Y'  THEN 24
                WHEN 'MT' THEN 25
                WHEN 'M'  THEN 25
                ELSE v.chrom::integer             # ⑤
            END, v.pos
        LIMIT %s OFFSET %s""",
        (sample_id, limit, offset),
    )
    return VariantListResponse(
        items=[VariantSummary(**r) for r in rows],
        ...
    )
①
SELECT 1 FROM samples WHERE id = %s — asks the database "does this sample exist?" without fetching any actual data. SELECT 1 returns the integer 1 for every matching row. It is faster than SELECT * because PostgreSQL knows it does not need to fetch any column values from the heap pages.
②
Why not just count variants? Without this check, a caller asking for variants of sample ID 99999 would receive {"items": [], "total": 0} — indistinguishable from a real sample that has simply not had any variants ingested yet. This makes debugging from the client side very confusing. The explicit 404 signals "this sample does not exist", while a 200 with an empty list signals "this sample exists but has no variants".
③
LEFT JOIN variant_classification ... AND vc.deleted_at IS NULL — the join condition includes the soft-delete filter. An INNER JOIN would drop variants that have no classification at all; a LEFT JOIN without the soft-delete condition would return both active and deleted classifications. The two-part join condition (ON vc.variant_id = v.id AND vc.deleted_at IS NULL) is the only way to get "active classification or nothing" in a single query.
④
Production caveat comment — added after code review. The CASE expression assumes chromosomes are stored without the chr prefix. This needs confirming against a real DRAGEN VCF from the lab. The comment is in SQL inside a Python string, so it appears in the query sent to PostgreSQL — PostgreSQL ignores it, but it is visible in any query log or EXPLAIN output.
⑤
ELSE v.chrom::integer — PostgreSQL's ::integer cast converts the string '17' to the integer 17. If the value is 'chr17', this cast fails with a PostgreSQL error (invalid input syntax for type integer: "chr17"). The surrounding CASE handles 'X', 'Y', 'MT', and 'M' before reaching the ELSE, so those values never hit the cast.

24 get_variant() — three sequential queries with conditional assembly

File: app/routes/variants.py · lines 53–102. The most structurally complex route: it conditionally issues a third query only when needed, and assembles a deeply nested response object from flat database rows.

get_variant() variants.py · GET /api/variants/{id} — variant + optional classification + criteria 
async def get_variant(variant_id: int):
    variant_rows = await asyncio.to_thread(
        db.query,
        """SELECT v.*, s.case_type               # ①
           FROM variants v
           JOIN samples s ON s.id = v.sample_id
           WHERE v.id = %s""",
        (variant_id,),
    )
    if not variant_rows:
        raise HTTPException(status_code=404, ...)

    variant = variant_rows[0]                   # ②

    classification_rows = await asyncio.to_thread(
        db.query,
        """SELECT id, framework, framework_version, score, classification,
               locked_at, locked_by
           FROM variant_classification
           WHERE variant_id = %s AND deleted_at IS NULL""",  # ③
        (variant_id,),
    )

    active_classification = None                 # ④
    if classification_rows:
        clf = classification_rows[0]
        criteria_rows = await asyncio.to_thread(  # ⑤
            db.query,
            """SELECT id, criterion_code, applied, strength, notes,
                      evidence_links, pre_computed, pre_computed_value
               FROM classification_criterion
               WHERE classification_id = %s ORDER BY id""",
            (clf["id"],),
        )
        active_classification = ClassificationDetail(
            **clf,                                 # ⑥
            criteria=[CriterionDetail(**c) for c in criteria_rows],
        )

    return VariantDetailResponse(
        **{k: variant[k] for k in variant if k != "case_type"},  # ⑦
        active_classification=active_classification,
    )
①
v.*, s.case_type — selects all variant columns plus the case_type from the parent sample. case_type is not stored on the variants table (it belongs to samples); the JOIN pulls it in. It is not included in the VariantDetailResponse model — its purpose is to be available to the PR 7 classification routes that call select_framework(case_type, gene) to determine which scoring framework to apply.
②
variant = variant_rows[0] — the query has a WHERE v.id = %s condition, and variant IDs are unique (primary key), so at most one row can be returned. Assigning to variant rather than destructuring immediately makes the subsequent field access more readable.
③
WHERE variant_id = %s AND deleted_at IS NULL — the soft-delete filter. A partially unique index on (variant_id) WHERE deleted_at IS NULL enforces that at most one active classification exists per variant at the database level. If the PR 7 classify-persist route is called twice concurrently for the same variant, the second INSERT will violate this constraint; the route handles that via a UniqueViolation catch.
④
active_classification = None — the default value for an unclassified variant. The VariantDetailResponse model declares this field as ClassificationDetail | None, so FastAPI will serialise it as "active_classification": null in the JSON response. Frontend components can check for null to decide whether to show a "not yet classified" state.
⑤
Conditional third query — issued only if query 2 found an active classification. For unclassified variants, this await is never reached, saving a database round-trip. For classified variants, the criteria are fetched by classification_id (not variant_id) because each classification has its own set of criteria records — a reset operation creates a new blank classification with zero criteria.
⑥
ClassificationDetail(**clf, criteria=[...]) — **clf unpacks the classification row dict as keyword arguments. The criteria field is not in the DB row (it comes from query 3), so it is passed as an explicit keyword argument alongside the unpacked dict. Pydantic's constructor accepts this mix; fields in clf that match model field names are used, and any extras are discarded.
⑦
Excluding case_type — the actual code unpacks all variant fields individually by name rather than using a dict comprehension; shown here as a dict comprehension for clarity. The key point is that case_type is present in the variant dict (from the JOIN in query 1) but is not a field of VariantDetailResponse. Passing it via **variant directly would cause a Pydantic validation error in strict mode, so it is omitted from the response construction.
