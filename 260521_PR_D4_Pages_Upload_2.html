07 React Router: useParams and Navigate

React Router maps URL paths to React components. It works by wrapping the whole app in a <BrowserRouter> (done in main.tsx) and declaring which component renders at which path using <Routes> and <Route>.

useParams — reading the URL

When a route has a dynamic segment like /patients/:id, the colon introduces a named parameter. Any component rendered at that route can read the current value with useParams():

const { id } = useParams<{ id: string }>();
// id is always a string from the URL — Number(id) is needed for API calls
String only

useParams() always returns strings, even if the URL segment looks like a number. This is why Number(id) appears in every page — and why the NaN guard isNaN(Number(id)) is essential: if someone navigates to /patients/abc, Number("abc") returns NaN, which would be passed to the API and return a 422 or a confusing error.

Navigate — programmatic redirect

<Navigate to="/" replace /> is a component, not a function call. When React renders it, the browser immediately navigates to the given URL. The replace prop means the current history entry is replaced rather than pushed — so the back button does not take the user back to the 404'd page.

if (notFound) return <Navigate to="/" replace />;
// This renders the Navigate component, which triggers the redirect.
// Nothing below this line runs for the 404 case.

In this file

PatientDetailPage uses useParams<{ id: string }>() to get the patient id from /patients/:id. ClassificationPage uses useParams<{ patientId: string; variantId: string }>() to get both parameters from /patients/:patientId/variants/:variantId. Both pages redirect to <Navigate to="/" replace /> when the API returns 404.

08 The thin-wrapper page pattern

A "thin wrapper" page has one job: fetch, hold state, render children. It contains no formatting logic, no business rules, and no inline styles beyond layout.

export default function ExamplePage() {
  const [data, setData] = useState<Item[] | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    fetchItems()
      .then(setData)
      .catch((e) => setError(e.detail ?? "Failed to load"))
      .finally(() => setLoading(false));
  }, []);  // empty array: run once on mount

  if (loading) return <div>Loading…</div>;
  if (error)   return <div>{error}</div>;
  return <ChildComponent items={data!} />;
}

Why this pattern?

  • Testability: child components can be tested with static props, no mocking of fetch required.
  • Replaceability: swapping ChildComponent for a different display component requires no changes to the fetch logic.
  • Clarity: a reviewer can read the page and know immediately what API calls it makes and what data flows where.
In this file

All four pages in D4 follow this pattern exactly. PatientsPage is the simplest — one fetch, one list component. PatientDetailPage is the most complex — two levels of fetch with Promise.all (see Section 10). ClassificationPage adds a case_type runtime validation step before passing props (see Section 14 in Part 4).

09 import.meta.env — Vite environment detection

Vite (the frontend build tool) exposes environment variables through import.meta.env. This is a special object injected at build time — it is not available in Node.js or in the browser at runtime; Vite replaces it with the actual values when it compiles the bundle.

VariableValueWhen
import.meta.env.DEVtrueRunning via npm run dev (Vite dev server)

// Inside handleSubmit — evaluated at call time, not module load time
const isDev = import.meta.env.DEV || import.meta.env.VITE_APP_ENV === "development";
if (isDev) {
  await handleDevUpload();
} else {
  await handleProdUpload();
}
Why not a module-level constant?

An earlier version of the code used const IS_DEV = import.meta.env.VITE_APP_ENV !== "production" at module level. This was changed so that tests can control the isDev value via vi.stubEnv without reloading the module. Evaluated inside handleSubmit, the check sees the current env at the moment the form is submitted — not the snapshot taken when the file was first imported.

10 Promise.all for parallel fetches

Promise.all() takes an array of Promises and returns a single Promise that resolves when all of the input promises resolve, or rejects as soon as any one of them rejects.

// Sequential — slow: each fetch waits for the previous to finish
for (const s of p.samples) {
  const detail = await getSample(s.id);
  details.push(detail);
}

// Parallel — fast: all fetches fire simultaneously
const details = await Promise.all(
  p.samples.map((s) => getSample(s.id))
);

In PatientDetailPage, after the initial getPatient() call returns the patient record with an array of specimen summaries, the page needs the full SampleDetail for each specimen (to show variant counts, tissue, sequencing date, etc. in each SpecimenCard). With Promise.all, all specimen fetches are in-flight simultaneously, so the total wait time is the time for the slowest single fetch, not the sum of all fetches.

N+1 by design

This is an intentional N+1 query pattern: one call to /api/patients/:id followed by N calls to /api/samples/:id. It is acceptable because a patient typically has only a handful of specimens. A future optimisation could add a GET /api/patients/:id/samples endpoint returning full detail in a single call, but this would only be worthwhile if specimen counts grew into the dozens.

11 useCallback and stable callbacks

useCallback(fn, [deps]) returns a memoized version of the function fn that only changes when one of the listed dependencies changes. Without it, every render of the parent component creates a new function object, which causes every child component that receives it as a prop to re-render unnecessarily.

// Without useCallback — new function on every render
const handleDelete = (id: number) => setSamples((p) => p.filter((x) => x.id !== id));

// With useCallback — same function reference across renders
const handleDelete = useCallback(
  (id: number) => setSamples((p) => p.filter((x) => x.id !== id)),
  []  // empty deps: function never needs to change
);

The empty dependency array is safe here because the function uses the updater form of setSamples — setSamples((prev) => ...) — rather than reading samples directly from the outer scope. The updater form is always passed the current state value by React, so there is no closure over a stale value.

In this file

PatientDetailPage uses useCallback for handleDeleteSample, which is passed to each SpecimenCard as onDeleteSample. Without the memoization, every state update (e.g. the loading flag changing) would recreate the callback, causing all rendered SpecimenCard components to re-render even when their data had not changed.

12 FHIR R4 Bundles

FHIR (Fast Healthcare Interoperability Resources) is an international standard for exchanging healthcare information. A FHIR R4 Bundle is a JSON document that packages multiple healthcare resource records together in a single container.

In this codebase, a Bundle is used as a sidecar manifest uploaded to S3 alongside the VCF file. The ingest Lambda reads the manifest to find the patient lab number, specimen name, case type, pipeline key, and VCF filename — information that cannot be inferred from the VCF itself.

{
  "resourceType": "Bundle",
  "type": "collection",
  "entry": [
    { "resource": { "resourceType": "Patient", "identifier": [...] }},
    { "resource": { "resourceType": "Specimen", "extension": [...] }},
    { "resource": { "resourceType": "Task", "output": [...] }}
  ]
}

13 S3 presigned PUT URLs

Normally, uploading a file to S3 requires AWS credentials. Presigned URLs are a way to delegate that permission temporarily: the backend generates a URL that is pre-authenticated for a specific operation (PUT), a specific object key, and a specific expiry time (1 hour in this codebase). The browser can then PUT directly to S3 without ever holding AWS credentials.

The backend generates both URLs in a single POST /api/upload-url call, returning vcf_url, manifest_url, vcf_key, and manifest_key. The VCF key follows the pattern runs/YYYY-MM-DD/filename.vcf.gz; the manifest key replaces the .vcf.gz extension with .manifest.json.

14 FormData and multipart/form-data

FormData is the browser API for building the body of a multipart/form-data HTTP request — the same format a normal HTML form uses when it submits a file upload. Each field is appended as a named part, and the browser automatically sets the correct Content-Type header with the multipart boundary.

const fd = new FormData();
fd.append("vcf", file);                  // File object → multipart file part
fd.append("lab_number", labNumber);       // string → multipart text part
fd.append("specimen_name", sampleName);   // corresponds to Form(...) in FastAPI

await fetch("/api/ingest-direct", {
  method: "POST",
  headers: authHeaders(),  // X-API-Key only — DO NOT set Content-Type manually
  body: fd,
});
Critical: do not set Content-Type manually

When the request body is a FormData object, the browser sets Content-Type: multipart/form-data; boundary=----WebKitFormBoundary… automatically, including the unique boundary string that separates the parts. If you manually set Content-Type: multipart/form-data in the headers, the boundary string is missing and the server cannot parse the body — the request will return 422 or a parse error. This is why authHeaders() only returns {X-API-Key: ...} with no Content-Type.

Field name alignment with the backend

Each fd.append(name, value) call must exactly match the parameter name declared in the FastAPI endpoint. The POST /api/ingest-direct endpoint declares:
