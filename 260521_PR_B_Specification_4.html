19 TypeScript interfaces — annotated

These are the hardest parts of DESIGN.md §4 to understand correctly. Each interface below has inline annotations explaining every non-obvious decision.

PatientSummary DESIGN.md §4 — items[] entry from GET /api/patients 
export interface PatientSummary {
  id: number;
  lab_number: string;                         // ①
  name: string | null;                        // ②
  // dob removed — migration 004 (GDPR)       // ③
  sample_count: number;                       // ④
  latest_sample_id: number | null;
  latest_sample_name: string | null;
  latest_workflow_status: string | null;      // ⑤
  latest_ingested_at: string | null;
  pipeline_key: string | null;
}
①
lab_number is the MRN — the Medical Record Number. In the NHS context this is the primary patient identifier. It is displayed in the UI as "MRN" (the column header), not as "lab_number".
②
name is present but never rendered — the backend returns it, the TypeScript type includes it, but no component renders it. This is deliberate data minimisation. A reviewer should check that no component accesses patient.name for display purposes.
③
dob deliberately absent — Migration 004 (ALTER TABLE patients DROP COLUMN IF EXISTS dob) removed this column from PostgreSQL for UK GDPR data-minimisation reasons. Any code that queries patients.dob will produce a SQL error at runtime. The comment in the interface makes this explicit so implementors don't assume it's a mistake.
④
Aggregate fields from M_pre1 — sample_count and the latest_* fields are computed by subqueries in the backend list_patients SQL. They don't exist in the database as columns; they are derived at query time. Before M_pre1 is implemented, the backend returns only id, lab_number, name.
⑤
Nullable workflow status — a patient with no specimens has latest_workflow_status: null. PatientListTable must handle this: if null, show a dash rather than rendering a WorkflowBadge with an undefined status.
VariantDetailResponse DESIGN.md §4 — response from GET /api/variants/{id} 
export interface VariantDetailResponse {
  id: number;
  chrom: string; pos: number; ref: string; alt: string;
  gene: string | null;
  consequence: string | null;
  hgvs_c: string | null;
  hgvs_p: string | null;
  gnomad_af: number | null;
  revel_score: number | null;
  spliceai_max: number | null;
  clinvar_sig: string | null;
  info_json: Record<string, unknown>;         // ①
  case_type: string;                           // ②
  active_classification: ClassificationDetail | null;  // ③
}

export interface ClassificationDetail {
  id: number;
  framework: string;
  framework_version: string;
  score: number | null;
  classification: string | null;
  locked_at: string | null;
  locked_by: string | null;
  criteria: CriterionDetail[];                 // ④
}
①
info_json is an opaque bag — the raw VCF INFO field stored as JSON. The SPA does not render it directly (no column in VariantTable for it), but it is included in the type because it is returned by the API. Record<string, unknown> allows any key-value structure without TypeScript errors.
②
case_type was added after review — ClassificationPage uses it to call selectFramework(case_type, gene). Without it, all variants would be classified with the ACGS SNV (germline) framework, even somatic variants. The backend routes/variants.py was updated in PR A to include this field in the SQL SELECT.
③
active_classification can be null — a variant that has never been classified has active_classification: null. ClassificationPage must handle this: pass initialClassification={null} and initialCriteria={[]} to ClassificationPanel. The panel will show an empty form ready for the first classification.
④
criteria is nested inside active_classification — not a top-level field. ClassificationPage must destructure: pass the classification (minus criteria) as initialClassification and the criteria array separately as initialCriteria. Passing the whole active_classification object including criteria would mean the ClassificationPanel receives criteria it doesn't expect.
PipelineFilters DESIGN.md §4 — filter preset shape returned by getPipelineDefaults() 
export interface PipelineFilters {
  gnomad_af_max: number | null;  // ①
  consequences: string;          // ②
  clinvar_exclude: string;       // ③
}
①
null means "no filter" — when the user clears the gnomAD AF input field, parseFloat("") returns NaN. The VariantTable component converts NaN to null and omits the gnomad_af_max parameter from the API query entirely. If we used a non-nullable number, we'd have to choose an arbitrary fallback value that changes filter behaviour.
②
Comma-separated VEP terms — e.g. "stop_gained,frameshift_variant,missense_variant". An empty string means no consequence filter (all consequences shown). The backend splits this on commas and applies consequence = ANY(%s).
③
Comma-separated ClinVar values to exclude — e.g. "Benign,Likely_benign". An empty string means no exclusion. The backend applies clinvar_sig != ALL(%s). Note: variants with clinvar_sig = null are never excluded (the SQL condition is (v.clinvar_sig IS NULL OR v.clinvar_sig != ALL(...))).

20 API response shapes — the tricky parts

Most API response shapes are straightforward. These four deserve extra attention because they have non-obvious conventions or have been corrected after review.

GET /api/patients — items wrapper REFERENCE.md §1.1 
{
  "items": [ ... ],    // ① NOT "patients"
  "total": 100,        // ② server-side total, not items.length
  "limit": 50,
  "offset": 0
}
①
items, not patients — this is the standard FastAPI pagination wrapper. The field is named items (generic) not patients (specific). PatientsPage must read r.items, not r.patients. This was one of the critical findings from the round-1 code review.
②
total is the server count, not the array length — items.length will be at most limit (50 by default). total is the count of all matching records. PatientsPage uses total for the count subtitle and decrements it when a patient is deleted locally.
PUT /api/variants/{id}/classification — response REFERENCE.md §1.3 
{
  "classification_id": 45,   // ①
  "score": 9,
  "classification": "Likely_Pathogenic",
  "warnings": []
}

// Request body: locked_by field
{
  "locked_by": null,         // ② draft save
  "locked_by": "analyst-1"  // ③ confirmed save
}
①
Top-level classification_id — the ID of the newly created classification record is at the top level of the response, not nested inside an object. ClassificationPanel reads result.classification_id to update its classId state. If you tried to read result.id or result.classification.id, you'd get undefined.
②
null locked_by = draft save — the backend sets locked_at = NULL in the INSERT when locked_by is null. The classification is saved but not locked. ClassificationPanel keeps the Save draft and Confirm buttons visible after a draft save.
③
Non-null locked_by = confirmed save — the backend sets locked_at = NOW(). ClassificationPanel sets lockedAt = new Date().toISOString() on success and switches to showing the Reset button. The locked_by value is taken from import.meta.env.VITE_USER_ID ?? "analyst".
POST /api/upload-url — request and response REFERENCE.md §1.4 
// Request body (note: vcf_filename, not filename)
{
  "vcf_filename": "sample.vcf.gz",   // ①
  "run_date": "2026-05-18"           // ②
}

// Response
{
  "vcf_url": "https://s3...",        // ③ presigned PUT URL for VCF
  "manifest_url": "https://s3...",   // ④ presigned PUT URL for manifest
  "vcf_key": "runs/2026-05-18/sample.vcf.gz",
  "manifest_key": "runs/2026-05-18/sample.manifest.json",
  "expires_in": 3600
}
①
vcf_filename not filename — the backend UploadUrlRequest Pydantic model uses the field name vcf_filename. The Next.js reference used a different field name. This was caught in round-3 code review. Sending filename would result in a 422 Validation Error from FastAPI.
②
run_date is optional — if omitted, the backend defaults to today's date as the S3 key prefix (runs/YYYY-MM-DD/...). UploadForm omits it, relying on the backend default.
③④
Two separate presigned URLs — the prod upload path requires two S3 PUTs: one for the VCF file and one for the FHIR R4 Bundle manifest (built by fhir-manifest.ts). The manifest is a JSON sidecar that the Lambda ingest function reads to extract patient metadata. Uploading only the VCF without the manifest will cause the ingest to fail with a "manifest not found" error.

21 The classification scoring algorithm — annotated

classify(criteria, framework, combinationRules) classification-engine.ts — the core algorithm 
export function classify(
  criteria: AppliedCriterion[],
  framework: Framework,
  combinationRules: CombinationRule[]
): ClassificationResult {
  const applied = criteria.filter(c => c.applied);          // ①

  const appliedCodeSet = new Set(applied.map(c => c.criterion_code));
  for (const rule of combinationRules) {                     // ②
    if (rule.codes.length < 2) continue;
    const matchCount = rule.codes.filter(code =>
      appliedCodeSet.has(code)).length;
    if (matchCount >= 2) warnings.push(rule.message);
  }

  if (framework === 'acgs_snv') {
    const hasBA1 = applied.some(c => c.criterion_code === 'BA1');
    if (hasBA1) return { score: -999, classification: 'Benign', warnings };  // ③

    let score = 0;
    for (const c of applied) {
      const dir = getCriterionDirection(c.criterion_code, framework);  // ④
      if (dir === 'pathogenic') score += STRENGTH_POINTS[c.strength] ?? 0;
      else if (dir === 'benign') score += BENIGN_POINTS[c.strength] ?? 0;
    }

    if (applied.length < 2 && score !== 0) {
      warnings.push('ACGS requires minimum 2 criteria...');  // ⑤
    }

    return { score, classification: classifyAcgs(score, false), warnings };
  } else {
    // SVIG path: O1 (Oncogenic sentinel) > B1 (Benign sentinel) > B2 (VUS)  // ⑥
    const hasO1 = applied.some(c => c.criterion_code === 'O1');
    if (hasO1) return { score: 999, classification: 'Oncogenic', warnings };
    const hasB1 = applied.some(c => c.criterion_code === 'B1');
    if (hasB1) return { score: -999, classification: 'Benign', warnings };
    const hasB2 = applied.some(c => c.criterion_code === 'B2');
    if (hasB2) return { score: 0, classification: 'VUS', warnings };
    // ... normal SVIG point scoring follows
  }
}
①
Filter applied-only upfront — unapplied criteria (checkbox unchecked) contribute zero points and are excluded from all downstream processing. The criteria array always contains all criteria (one per criterion definition), but most are unapplied at any given time.
②
Combination rule check using a Set — uses a Set of applied criterion codes (not an array) for O(1) lookup. For each rule (e.g. "two PM criteria act as one PS"), if two or more of the rule's codes are present in the applied set, a warning is pushed. Note: the warning is advisory — it does not change the score.
③
BA1 standalone override returns sentinel score −999 — BA1 (gnomAD AF >5%) immediately overrides all other criteria and returns Benign with sentinel score −999 (not the calculated sum). This sentinel is never shown to the user — the display shows "Benign" not "−999". The sentinel distinguishes BA1-driven Benign from score-driven Benign (≤−6).
④
getCriterionDirection() from code prefix — direction is not stored in the applied criterion state. It is derived from the criterion code: PVS|PS|PM|PP prefixes → pathogenic; BA|BS|BP prefixes → benign. This means the direction lookup uses the code string, not a field in the criteria JSON. A typo in a criterion code would silently produce zero weight.
⑤
Minimum 2 criteria warning — ACGS guidelines require at least 2 applied criteria for any non-VUS classification (BA1 excepted). With only 1 criterion applied and a non-zero score, a warning is emitted but the classification is still computed and displayed. The warning does not block saving.
⑥
SVIG sentinel priority order: O1 > B1 > B2 — critically, this must match the Python backend. An earlier version of the TypeScript engine had the order reversed (B2 before B1 and O1), which would cause misclassification of variants with O1+B2 co-applied. O1 (standalone Oncogenic) always wins; then B1 (standalone Benign); then B2 (forces VUS regardless of score). This order was verified by golden test cases O1+B2 → Oncogenic and B1+B2 → Benign.

22 Invariant verification commands

These are the exact commands from build-prompt.md that verify each invariant. They should pass on the tip of PR D4 before merging.

# Invariant 1 — No patient PII in the UI
# Expected: no output (comments are permitted)
grep -r "nhs_number" frontend/src/components/ frontend/src/pages/

# Invariant 2 — API key never logged
# Expected: only one line — the header assignment in authHeaders()
grep -n "VITE_API_KEY" frontend/src/lib/api.ts

# Invariant 3 — Evidence links validated (automated)
# Expected: test passes
cd frontend && npm test -- CriterionRow

# Invariant 4 — Classification engine matches Python (automated)
# Expected: all 4 golden cases pass
cd frontend && npm test -- classification-engine

# Invariant 5 — No direct DB/S3 access
# Expected: no output
grep -r "psycopg2\|boto3\|pg\|postgres" frontend/src/
Common violations to watch for

Invariant 1 is most commonly violated by a well-intentioned "show patient name in the header" change. Invariant 2 is violated by including the key in a thrown Error message for debugging: throw new Error(`Request failed for key ${apiKey}`). Invariant 3 is violated if the rejection logic uses startsWith('http') instead of a proper URL parse — this would accept httpexample.com as valid.
