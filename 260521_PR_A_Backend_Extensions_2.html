08 FastAPI routers and Pydantic models

FastAPI is a Python web framework that uses type annotations to do two things automatically: validate incoming data and generate API documentation. Understanding these two mechanisms explains why the route files are structured the way they are.

APIRouter

Groups related endpoints under a shared URL prefix and dependency

Each route file creates one APIRouter with a prefix (e.g. /api/patients) and a shared dependencies list. Any dependency in that list runs before every endpoint in the router — here, require_api_key checks the X-API-Key header and raises a 403 if it is missing or wrong.

router = APIRouter(
    prefix="/api/patients",
    dependencies=[Depends(require_api_key)],  # runs before every endpoint below
)

# All these routes require the API key:
@router.get("")           # → GET /api/patients
@router.get("/{id}")      # → GET /api/patients/{id}
@router.delete("/{id}")   # → DELETE /api/patients/{id}

In this PR: All five route files use this pattern. The shared dependency means no endpoint can accidentally be left unprotected.

Pydantic BaseModel

Declares the shape of request bodies and response objects

A BaseModel subclass declares fields with type annotations. FastAPI automatically deserialises a JSON request body into the model (returning 422 if the shape is wrong) and serialises a model instance back to JSON in the response.

class PatientSummary(BaseModel):
    id: int
    lab_number: str
    name: str | None          # nullable — serialises as JSON null
    sample_count: int = 0     # default value — omit from JSON, get 0

# FastAPI uses it as response_model= to serialise:
@router.get("", response_model=PatientListResponse)
async def list_patients(...):
    return PatientListResponse(items=[PatientSummary(**r) for r in rows], ...)

In this PR: PatientSummary gained five aggregate fields with defaults of 0 or None. The defaults matter: PatientDetailResponse extends PatientSummary, so it inherits those fields. On the detail endpoint the subqueries are not run, so the fields serialise as their defaults — which is correct, because the detail response exposes samples directly.

Query() parameters

Declare URL query string parameters with validation

Query() declares a URL query parameter with optional constraints: ge (greater-than-or-equal), le (less-than-or-equal), pattern (regex). If the client sends a value that violates the constraint, FastAPI returns a 422 before the function body runs.

@router.get("/{sample_id}/variants")
async def list_sample_variants(
    sample_id: int,
    limit: int = Query(50, ge=1, le=200),     # 1–200 only
    sort_by: str = Query("chrom",
        pattern=r"^(chrom|gene|gnomad_af|...)$"),  # whitelist via regex
    gnomad_af_max: float | None = Query(None, ge=0, le=1),
):

In this PR: The pattern= on sort_by is crucial for SQL safety — it ensures that only known column names reach the SORTABLE dict. Any other value causes a 422 before the function body executes, so no user-controlled string ever reaches the f-string SQL interpolation.

09 asyncio.to_thread — bridging async and blocking code

FastAPI is an async framework: route handlers are declared with async def and run on an event loop. The database library (psycopg2) is synchronous — it blocks the calling thread while waiting for PostgreSQL. Calling a blocking function directly from an async handler would freeze the entire event loop, blocking all other requests.

asyncio.to_thread

Runs a blocking function on a thread pool without blocking the event loop

asyncio.to_thread(fn, *args) submits fn(*args) to a thread pool and returns an awaitable. The event loop can serve other requests while the thread is blocked waiting for the database. When the thread finishes, the result is returned to the calling coroutine.

# Without to_thread — BAD: blocks entire event loop
rows = db.query("SELECT ...")       # blocks for 50ms → no other requests served

# With to_thread — GOOD: event loop free while DB runs
rows = await asyncio.to_thread(
    db.query,                          # function to call in thread
    "SELECT ...",                      # positional arg 1
    (patient_id,),                     # positional arg 2
)

In this PR: Every db.query() and db.run_in_transaction() call is wrapped in asyncio.to_thread. This is the standard pattern throughout the codebase.

10 The sentinel exception pattern

This pattern appears in three places in this PR: _PatientNotFound, _SampleNotFound, and _ConcurrentReset. Understanding why it is needed requires understanding what happens when you raise an exception inside a thread.

Why not raise HTTPException inside _do(conn)?

The problem with HTTP concerns inside threads

The _do(conn) function runs inside a thread (via asyncio.to_thread). If it raises an HTTPException, that exception propagates from the thread back to the async handler — but FastAPI's exception handling is not set up to catch exceptions that originated in threads. The result is an unhandled exception and a 500 error, regardless of what status code was in the HTTPException.

A second problem is conceptual: the database callback should not need to know about HTTP. It is a pure data operation — the decision about what HTTP status code a "not found" condition maps to belongs in the async handler, not in the transaction.

The sentinel pattern

Private exception classes that carry meaning without HTTP knowledge
# 1. Declare a private sentinel at module level
class _PatientNotFound(Exception):
    pass                               # no fields needed — just a type signal

# 2. Raise it inside _do when the condition occurs
def _do(conn):
    with conn.cursor() as c:
        c.execute("SELECT id FROM patients WHERE id = %s", (patient_id,))
        if not c.fetchone():
            raise _PatientNotFound()    # ← no HTTPException here
        # ... rest of deletion ...

# 3. Catch the sentinel in the async handler and convert
try:
    await asyncio.to_thread(db.run_in_transaction, _do)
except _PatientNotFound:
    raise HTTPException(status_code=404, detail="Patient not found")

Why the leading underscore? Python convention: a name starting with _ is module-private. It signals that this exception is an implementation detail and should never be raised or caught outside the file. The name conveys its meaning to a reader while preventing accidental reuse elsewhere.

_ConcurrentReset in classification.py: The same pattern handles a TOCTOU (time-of-check-time-of-use) race. Two requests could both pass the deleted_at IS NULL SELECT and then both attempt to UPDATE. The second one finds rowcount == 0 (the row is already deleted), raises _ConcurrentReset, and the handler converts it to a 409 Conflict.

11 Pydantic field validators

Field validators are methods on a Pydantic model that run after the type conversion but before the model is returned. They can raise ValueError (which Pydantic wraps into a 422 response) or return the (possibly modified) value.

@field_validator — anatomy

Declared with a decorator; runs at parse time, not at definition time
class CriterionIn(BaseModel):
    evidence_links: list[str] = []

    @field_validator("evidence_links")   # which field to validate
    @classmethod                           # must be classmethod in Pydantic v2
    def validate_evidence_links(cls, v: list[str]) -> list[str]:
        _safe = re.compile(r'^https?://', re.IGNORECASE)
        for link in v:
            if not _safe.match(link.strip()):
                raise ValueError(        # ← NOT HTTPException
                    f"evidence_links must use http:// or https:// — got {link!r}"
                )
        return v                          # must return the value (possibly modified)

When a client sends an evidence link like javascript:alert(1), Pydantic catches the ValueError and returns:

# HTTP 422 Unprocessable Entity
{
  "detail": [{
    "loc": ["body", "criteria", 0, "evidence_links"],
    "msg": "Value error, evidence_links must use http:// or https://...",
    "type": "value_error"
  }]
}

locked_by field validator

Closing the gap between None (draft) and empty string

Without the validator, a client could send "locked_by": "". That is not None, so the code would treat it as a confirmed save (setting locked_at = NOW()) — but storing an empty string as the confirming user's identity is meaningless in an audit trail. The validator rejects it explicitly:

@field_validator("locked_by")
@classmethod
def locked_by_must_not_be_empty(cls, v: str | None) -> str | None:
    if v is not None and v.strip() == "":
        raise ValueError(
            "locked_by must be a non-empty string or null (use null for draft saves)"
        )
    return v

The three valid states are now: null (draft), "analyst-1" (confirmed), or missing from request (treated as null via the default). The ambiguous empty string is rejected.

12 f-string SQL safety

SQL injection is one of the most common and destructive security vulnerabilities in web applications. The standard defence is parameterised queries: pass user-supplied values as %s parameters, never as part of the SQL string itself. But there are two situations where parameters cannot be used: column names in ORDER BY clauses, and SQL keywords like ASC/DESC. This PR uses both, and it is safe — but the reasoning needs to be understood.

Why you cannot parameterise ORDER BY

SQL parameters are for values, not identifiers

SQL parameters (the %s placeholders) are for values — strings, numbers, dates. The database driver quotes and escapes them safely. They cannot be used for structural parts of the SQL statement like column names, table names, or keywords. If you tried ORDER BY %s and passed "v.gene", the database would interpret it as a string literal, not a column reference, and the ORDER BY would have no effect.

# WRONG — %s produces: ORDER BY 'v.gene' ASC (string literal, no effect)
cursor.execute("... ORDER BY %s %s", ("v.gene", "DESC"))

# CORRECT — whitelist first, then interpolate into the SQL string
SORTABLE = {
    "gene":       "v.gene",          # source-code literals, not user input
    "gnomad_af":  "v.gnomad_af",
}
order_col = SORTABLE[sort_by]        # sort_by is regex-validated by FastAPI
order_dir = "DESC" if sort_dir == "desc" else "ASC"
cursor.execute(f"... ORDER BY {order_col} {order_dir}", params)

13 Transaction callbacks and db.run_in_transaction

A database transaction is a set of operations that either all succeed or all fail together. In the variant-viewer codebase, write operations use a callback pattern: a plain Python function _do(conn) is passed to db.run_in_transaction, which opens a connection, begins a transaction, calls _do(conn), and either commits (if no exception) or rolls back (if an exception escapes).

The _do(conn) closure pattern

Transaction work as a captured-variable closure
async def delete_patient(patient_id: int):
    def _do(conn):                          # ① inner function defined here
        with conn.cursor() as c:
            c.execute("SELECT id FROM patients WHERE id = %s", (patient_id,))
            # ② patient_id captured from outer scope (closure)
            if not c.fetchone():
                raise _PatientNotFound()
            c.execute("DELETE FROM patients WHERE id = %s", (patient_id,))

    try:                                    # ③ run on a thread, await result
        await asyncio.to_thread(db.run_in_transaction, _do)
    except _PatientNotFound:
        raise HTTPException(status_code=404, detail="Patient not found")

① Inner function: _do is defined inside the async handler. It is a plain synchronous function — not async — because psycopg2 is synchronous.

② Closure: _do can read patient_id from the enclosing scope without receiving it as an argument. This is how Python closures work: the inner function captures a reference to the variable, not a copy of it.

③ Thread: db.run_in_transaction(_do) opens a connection and calls _do(conn). The whole thing runs in a thread. Any exception from _do propagates to the await call, where the try/except converts it.

14 Multipart file uploads with FastAPI

The POST /api/ingest-direct endpoint is the only one in this PR that accepts a file upload. The HTTP content type is multipart/form-data — the same format browsers use for HTML file inputs.

UploadFile and Form

FastAPI's multipart parameter declarations
from fastapi import File, Form, UploadFile

async def ingest_direct(
    vcf: UploadFile = File(...),          # binary file part
    lab_number: str = Form(...),         # text field (required)
    case_type: Literal["germline", "somatic"] = Form("germline"),  # with default
    sequencing_date: date | None = Form(None),   # optional typed date
):

UploadFile provides vcf.filename (the original filename from the client), vcf.size (byte count, if the client sends Content-Length), and await vcf.read() which reads the full file into memory as bytes.

Form(...) means the field is required (no default). FastAPI parses text form fields and converts them to the declared type — so sequencing_date: date | None = Form(None) accepts a YYYY-MM-DD string and returns a datetime.date object, or None if absent.

In this PR: the endpoint reads the entire VCF into memory, caps it at 500 MB, writes it to a temporary file, parses it with the VCF parser library, then deletes the temp file and does all DB work in a transaction. The temp file approach is needed because the VCF parser requires a file path, not a byte buffer.

15 UK GDPR data minimisation and migration 004

The UK General Data Protection Regulation (UK GDPR) establishes "data minimisation" as one of its key principles: personal data collected and retained must be "adequate, relevant and limited to what is necessary in relation to the purposes for which they are processed." Retaining data that is not necessary for those purposes is itself a compliance violation, even if the data is kept securely.

Regulatory context

The variant-viewer's purpose is variant classification for diagnostic genomics. A patient's date of birth is not required for variant interpretation — variants are classified based on allele frequency, computational predictions, and clinical evidence, none of which require the patient's age. Retaining dob would therefore be unnecessary personal data with no processing justification.

Migration 004

ALTER TABLE with BEGIN/COMMIT for transactional safety
-- migrations/004_remove_patient_dob.sql
-- Remove date of birth from the patients table.
-- DOB is not required for variant interpretation and is unnecessary
-- personal data under UK GDPR data-minimisation principles.
BEGIN;
ALTER TABLE patients DROP COLUMN IF EXISTS dob;
COMMIT;

The IF EXISTS clause makes the migration idempotent: running it twice does not error. The BEGIN/COMMIT wrapper ensures the DDL operation is atomic — consistent with how migrations 001–003 are written in this project.

The downstream consequence is that PatientSummary no longer declares a dob field. Any TypeScript code or test that expected dob in the API response must be updated. The PR addresses this by removing dob from the Pydantic model, the SQL queries, the TypeScript interface, and the frontend components — no backwards-compatibility layer is needed because this is a pre-release project.
