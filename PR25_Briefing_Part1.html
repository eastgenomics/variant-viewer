01 What this PR delivers

PR 25 (feat/pr6-read-api) adds the first HTTP-facing layer to the Variant Viewer backend. PRs 2–5 built the full business logic — database connection pooling, VCF parsing, FHIR manifest parsing, a variant classification engine, and a Lambda ingest pipeline — but left the FastAPI app as a skeleton with only a single /api/health stub. This PR wires all of that together behind a protected API surface.

Two milestones are delivered in a single commit:

  • M14 — Authentication middleware. Every route except /api/health now requires a valid X-API-Key header. The key is resolved lazily from AWS Secrets Manager (production) or an environment variable (development/CI), using a process-lifetime singleton so the Secrets Manager round-trip happens at most once per container restart.
  • M15 — Seven read-only endpoints. Patients (list + detail), samples (detail + variant list), a single variant detail with its active classification and criteria, and a config endpoint that serves the JSON classification criteria files directly from disk. All database calls are dispatched through asyncio.to_thread so the synchronous psycopg2 driver does not block the FastAPI event loop.

A supporting addition to db.py — the run_in_transaction helper — is also included here because it is consumed by the write routes in PR 7, and having it available in PR 6 avoids a merge-ordering problem.

Compliance note

M14 (auth middleware) closes the most critical pre-clinical-use blocker identified in the project compliance review: the absence of application-level authentication. Until this PR merged, any network-reachable instance of the backend accepted unauthenticated reads and writes.

02 Architecture overview

The PR adds two new directories to backend/app/: middleware/ (one module) and five new modules in the existing routes/ package. The diagram below shows all modules and their dependency arrows — an arrow means "imports from".

The routes/ modules are registered in main.py via app.include_router(). Each route module declares its own APIRouter with an inline dependencies=[Depends(require_api_key)], so authentication is enforced at router level rather than on individual endpoint functions — a single line in the router definition protects every route in the module.

03 Request flow

Every inbound HTTP request travels through the same five-stage pipeline. The diagram traces a GET /api/patients/42 request end-to-end.

Stage 3 (require_api_key) is where most authentication decisions happen. FastAPI evaluates all Depends before calling the route handler, so by the time get_patient runs, the key has already been validated. If the header is absent or wrong, FastAPI short-circuits and returns HTTP 401 without the route handler ever executing.

Stage 4 calls the psycopg2 driver, which is synchronous — it blocks the OS thread until the database responds. The asyncio.to_thread wrapper moves this blocking call off the event loop thread onto a worker thread from Python's default thread pool, letting FastAPI continue handling other requests concurrently while the database query runs.

Note on boto3

boto3 is imported at module level in both auth.py and db.py. This means the SDK is imported on every cold start even if Secrets Manager is not being used (i.e., when the plain env-var path is taken). This is acceptable for the ECS deployment pattern where containers run for hours; the import cost (~40 ms) is negligible.

06 Naming conventions

Underscore prefix — private / internal
Functions not part of the public API

Functions beginning with _ are module-internal and not intended to be called from outside the module. Examples: _get_api_key, _get_pool, _get_connection, _resolve_secrets. The public surfaces are query, with_transaction, run_in_transaction, and require_api_key.

auth.py · db.py
TypeVar T — generic return type
Preserves the caller's return type through the wrapper

T = TypeVar("T") appears in db.py alongside run_in_transaction. It tells the type checker that whatever type fn(conn) returns, run_in_transaction returns the same type — so callers don't lose type information when wrapping their function in the transaction helper.

db.py
*Response / *Summary suffixes
Pydantic models for HTTP response shapes

Response models are always named with a clear suffix: PatientListResponse, PatientDetailResponse, PatientSummary, SampleDetailResponse, etc. This distinguishes them from the ORM-style models in app/lib/models.py (which are Patient, Sample, etc.). The two sets are intentionally separate — HTTP shapes are often composite and don't map 1:1 to DB rows.

all route modules
UPPER_SNAKE constants
Module-level values that don't change at runtime

_VERSION = "0.2.0" in health.py and _FRAMEWORK_FILES = {...} in config.py follow the Python convention for module-level constants (underscore prefix because they're module-private; UPPER_SNAKE because they're immutable). _CONFIG_DIR is computed once at import time using Path(__file__).
