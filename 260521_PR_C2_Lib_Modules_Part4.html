29 classify() — annotated

The most safety-critical function in the frontend. Its output determines what classification the analyst sees and confirms. The Python backend has an identical algorithm; discrepancies between them would be a patient safety issue. The annotations explain the non-obvious choices.

classify classification-engine.ts · L96–162 · exported · pure function 
export function classify(
  criteria: AppliedCriterion[],
  framework: Framework,
  combinationRules: CombinationRule[]
): ClassificationResult {
  const applied = criteria.filter((c) => c.applied);          // ①
  const warnings: string[] = [];

  const appliedCodeSet = new Set(applied.map((c) => c.criterion_code)); // ②
  for (const rule of combinationRules) {
    if (rule.codes.length < 2) continue;                           // ③
    const matchCount = rule.codes.filter((code) => appliedCodeSet.has(code)).length;
    if (matchCount >= 2) warnings.push(rule.message);              // ④
  }

  let score = 0;

  if (framework === "acgs_snv") {
    const hasBA1 = applied.some((c) => c.criterion_code === "BA1"); // ⑤
    if (hasBA1) {
      return { score: -999, classification: "Benign", warnings };   // ⑥
    }

    for (const c of applied) {
      const direction = getCriterionDirection(c.criterion_code, framework);
      if (direction === "pathogenic") {
        score += STRENGTH_POINTS[c.strength] ?? 0;                  // ⑦
      } else if (direction === "benign") {
        score += BENIGN_STRENGTH_POINTS[c.strength] ?? 0;
      }
    }

    if (applied.length < 2 && score !== 0) {                       // ⑧
      warnings.push("ACGS requires a minimum of 2 applied criteria...");
    }

    return { score, classification: classifyAcgs(score, false), warnings };

  } else {  // svig
    const hasO1 = applied.some((c) => c.criterion_code === "O1");
    const hasB1 = applied.some((c) => c.criterion_code === "B1");
    const hasB2 = applied.some((c) => c.criterion_code === "B2");

    if (hasO1 || hasB1 || hasB2) {                                    // ⑨
      const classification = classifySvig(0, hasO1, hasB1, hasB2);
      const sentinelScore = classification === "Oncogenic"
        ? 999 : classification === "Benign" ? -999 : 0;              // ⑩
      return { score: sentinelScore, classification, warnings };
    }

    for (const c of applied) {
      const direction = getCriterionDirection(c.criterion_code, framework);
      if (direction === "oncogenic") {
        score += STRENGTH_POINTS[c.strength] ?? 0;
      } else if (direction === "benign") {
        score += BENIGN_STRENGTH_POINTS[c.strength] ?? 0;
      }
    }

    return { score, classification: classifySvig(score, false, false, false), warnings };
  }
}
①
Filter applied only. Unapplied criteria (pre-computed suggestions the analyst did not accept) are completely ignored for scoring. They may still be persisted to the database as audit records but contribute zero points.
②
Build the applied-code Set once before the loop. This is an O(n) scan done once; looking up each rule's codes against a Set is then O(1) per code. The alternative — scanning applied for every rule — would be O(n × r) where r is the number of rules. For 20 rules and 30 criteria this is a trivial difference, but matching the Python implementation's approach keeps the algorithm verifiable as a direct port.
③
Skip single-code rules. The combination-rules array may contain single-code "sentinel" rules (BA1, O1, B1, B2). These are handled explicitly below. A rule with only one code can never produce a two-code conflict, so we skip it here to avoid false warnings.
④
Warning fires on two or more matching applied codes — not just exactly two. If a hypothetical future rule listed three conflicting codes (A, B, C) and the analyst applied all three, the warning fires once. The message text is defined in the JSON config file, not hardcoded here.
⑤
BA1 sentinel check before any scoring. BA1 (population frequency evidence alone is sufficient for Benign) short-circuits the entire scoring algorithm. Its presence means the variant is common in the healthy population — regardless of any pathogenic evidence, common variants are not disease-causing in an autosomal dominant context.
⑥
Sentinel score −999. This is a flag value, not a real score. The threshold table has no entry for scores below −7, so −999 would produce "Benign" through the normal path too — but using −999 makes it detectable in the UI (e.g. to show "★" instead of "−999"). The combination-rule warnings computed before this check are still included in the return value.
⑦
Nullish coalescing ?? 0. If a criterion has an unrecognised strength string (e.g. a typo or a new strength not yet in the table), STRENGTH_POINTS[c.strength] returns undefined. The ?? 0 treats that as zero points rather than throwing an error. This differs from the Python engine which raises ValueError — a deliberate frontend decision (see Part 3, getCriterionDirection discussion).
⑧
Minimum-criteria warning. ACGS guidelines require at least two criteria for any non-VUS result (except BA1). The condition is applied.length < 2 && score !== 0 — if the score is zero, the result is VUS regardless, so the warning would be misleading. The warning is advisory; the classification is still returned.
⑨
SVIG sentinel block. O1, B1, and B2 are checked before the scoring loop. The short-circuit uses the same logic as BA1 in ACGS — but SVIG has three sentinels with different priorities. The classifySvig(0, hasO1, hasB1, hasB2) call with score=0 ensures the priority logic (O1 > B1 > B2) is handled by the same function used in normal scoring.
⑩
Sentinel score assignment. Oncogenic → +999, Benign → −999, VUS (B2 case) → 0. The VUS sentinel score is 0 rather than a special flag because 0 is the correct VUS score — B2 forces VUS rather than bypassing the normal path. The UI shows "0" as the score for a B2 case, which is correct and not misleading.

30 request<T>() — annotated

The HTTP client used by every public endpoint function. Short but dense with decisions about error handling, generic types, and 204 edge cases.

request<T> api.ts · private · generic async function 
async function request<T>(url: string, init?: RequestInit): Promise<T> {
  const resp = await fetch(url, {
    ...init,
    headers: { ...headers(), ...init?.headers }   // ①
  });
  if (!resp.ok) {                                   // ②
    let detail = `HTTP ${resp.status}`;
    try {
      detail = (await resp.json()).detail ?? detail; // ③
    } catch { /* ignore */ }
    throw new ApiError(resp.status, detail);
  }
  if (resp.status === 204 || resp.headers?.get?.("content-length") === "0") { // ④
    return undefined as unknown as T;              // ⑤
  }
  return resp.json() as Promise<T>;              // ⑥
}
①
Header merging with spread syntax. headers() returns {Content-Type: "application/json", X-API-Key: "..."}}. The caller may pass additional headers via init?.headers. Spreading both with caller headers last means callers can override Content-Type for multipart requests. The optional chaining init? handles the common case where no init is provided.
②
resp.ok is false for any 4xx or 5xx status code. It is true for 2xx. The check happens before trying to parse the body — this is the correct order. Parsing first and then checking status would work for JSON error responses but would throw a SyntaxError for HTML error pages (e.g. a 502 Bad Gateway from nginx).
③
Graceful body parsing on error. FastAPI returns {"detail": "..."} for validation errors and custom HTTP exceptions. The try/catch around resp.json() handles cases where the error body is not JSON (e.g. a raw nginx 502 page). The ?? operator then uses the "HTTP 502" fallback if .detail is absent. Note: await resp.json() is safe here because the body has not been read yet — unlike calling resp.json() after a 204 where there is no body.
④
204 No Content guard. Two conditions: status code 204 exactly, OR Content-Length header is "0". The second condition catches edge cases where some proxies respond with 200 and an empty body. Both optional-chaining operators (?.) guard against the test environment where the mocked response may not have a headers object at all.
⑤
The as unknown as T double cast. TypeScript will not allow returning undefined where T is expected — the types are incompatible. The cast goes through unknown first (which every type is assignable to and from) to "reset" the type, then asserts T. Callers that type the return as void (e.g. deletePatient) will never use the returned value; callers returning a typed object will never hit this branch because the backend never returns 204 with a body. The cast is safe in practice.
⑥
as Promise<T> is a type assertion, not a runtime conversion. resp.json() actually returns Promise<any>. The cast tells TypeScript to treat that any as T. There is no runtime validation that the JSON body actually conforms to T. If the backend sends a field the interface does not declare, TypeScript won't complain — but if the backend removes a required field, the component accessing it will get undefined at runtime without a compiler error. This is the standard trade-off in typed API clients without runtime schema validation.

31 selectFramework() — annotated

Short function with an important module-level side effect — the CanVIG Set is initialised when the module is first imported.

selectFramework + CANVIG_GENE_SET initialisation classification-engine.ts · L11–16 (module init) + L164–178 (function) 
// Module-level — runs once at import time
const CANVIG_GENE_SET = new Set(
  Object.keys((canvigGeneMtaf as { genes: Record<string, unknown> }).genes)
    .map((g) => g.toUpperCase())           // ①
);

export function selectFramework(
  caseType: "germline" | "somatic",
  gene: string | null
): { framework: Framework; isCanvig: boolean } {
  if (caseType === "somatic") {
    return { framework: "svig", isCanvig: false };   // ②
  }
  const normalisedGene = gene?.trim().toUpperCase();  // ③
  if (normalisedGene && CANVIG_GENE_SET.has(normalisedGene)) {  // ④
    return { framework: "acgs_snv", isCanvig: true };
  }
  return { framework: "acgs_snv", isCanvig: false };
}
①
Uppercase normalisation at Set construction time. All 33 gene symbols are converted to uppercase when building the Set. This means the lookup in the function body also uses toUpperCase() for consistent case-insensitive matching. The JSON file stores mixed-case symbols (e.g. "BRCA1") — the uppercase normalisation is belt-and-suspenders.
②
Somatic always means SVIG-UK, no CanVIG check needed. CanVIG (Cancer Variant Interpretation Group) is a germline-specific initiative. Somatic variants are by definition not inherited germline variants, so SVIG-UK is always the correct framework.
③
Optional chaining on gene lookup. gene?.trim().toUpperCase() returns undefined if gene is null. The subsequent if (normalisedGene && ...) then short-circuits to false — a null gene is treated as "not in CanVIG". This is correct: if the variant has no gene annotation, it cannot be on the CanVIG panel.
④
Set.has() is O(1), whereas Array.includes() would be O(n). For 33 genes the difference is negligible, but Set is the correct data structure semantically — it communicates "membership test" more clearly than an array search. The Set is created once at module load; subsequent calls to selectFramework() pay no construction cost.

32 buildManifest() — annotated

A pure object-construction function with no logic beyond conditional field inclusion. The annotations focus on why each field is structured as it is — the FHIR conventions are not obvious from the code alone.

buildManifest fhir-manifest.ts · L13–56 · exported 
export function buildManifest(params: { ... }): FhirBundle {
  const { labNumber, specimenName, caseType, pipelineKey,
          sequencingDate, vcfFilename } = params;
  return {
    resourceType: "Bundle",
    type: "collection",                            // ①
    entry: [
      {
        resource: {
          resourceType: "Patient",
          identifier: [{ system: NHS_LAB_SYSTEM,      // ②
                         value: labNumber }],
        },
      },
      {
        resource: {
          resourceType: "Specimen",
          identifier: [{ value: specimenName }],       // ③
          collection: sequencingDate
            ? { collectedDateTime: sequencingDate }    // ④
            : undefined,
          extension: [{
            url: CASE_TYPE_EXT,                        // ⑤
            valueCode: caseType,
          }],
        },
      },
      {
        resource: {
          resourceType: "Task",
          status: "completed",
          identifier: [],
          code: pipelineKey ? { text: pipelineKey } : undefined, // ⑥
          output: [{ type: { text: "vcf" },
                     valueString: vcfFilename }],       // ⑦
        },
      },
    ],
  };
}
①
Bundle type "collection" vs "transaction". A FHIR "transaction" Bundle would instruct the server to process all resources atomically. A "collection" Bundle is just a container — no processing semantics. The backend's parse_manifest() validates that the type is exactly "collection" and rejects anything else.
②
NHS_LAB_SYSTEM identifier. FHIR identifiers are namespaced: the system URI identifies what kind of identifier the value is. Using a project-specific URI (https://fhir.example-lab.org/Id/lab-number) rather than an NHS-official OID is intentional — this is an internal system. The backend's parse_manifest() filters patient identifiers by this exact URI to extract the lab number.
③
Specimen identifier has no system URI. The specimen name is a local identifier with no external namespace. Omitting the system URI is valid in FHIR for locally-scoped identifiers. The backend extracts it simply as identifier[0].value.
④
Conditional collection block. If sequencing date is null, the collection field is set to undefined. When JavaScript's JSON.stringify() encounters an undefined value in an object, it omits that key entirely from the output — so the manifest JSON will simply not have a collection property. The backend handles this gracefully: manifest.specimen.sequencing_date will be None.
⑤
FHIR extension for case type. The standard Specimen resource has no field for germline/somatic. FHIR's extension mechanism allows adding custom fields: any URL can be used as the extension identifier. The URL https://example.org/fhir/StructureDefinition/case-type is project-specific. The backend looks for this exact URL when parsing: e["url"] == CASE_TYPE_EXT. If this URL were changed in either the frontend or backend without updating the other, case type would silently become None for all new uploads.
⑥
Task code is optional. If no pipeline key is provided, code is undefined and absent from the JSON output. The backend uses the pipeline key from the Task code to override the VCF metadata pipeline if present. Omitting it means the backend falls back to whatever pipeline the VCF header declares.
⑦
Task output records the VCF filename. The output array follows FHIR's Task output structure: each item has a type (a CodeableConcept with a text label) and a value. The backend cross-checks this filename against the actual S3 key basename — if they differ it means the manifest was paired with the wrong VCF upload and the ingest is rejected.

33 Series summary

PR C2 establishes the pure-function foundation that all visual components (PRs D1–D4) build on. The five modules are deliberately layered and kept free of React so they can be tested independently. The key invariants to remember when reading or modifying this code:

  • classification-engine.ts must stay in sync with the Python backend. Any change to scoring weights, thresholds, sentinel codes, or priority order must be reflected in both. The four golden-case tests are the contract.
  • authHeaders() reads VITE_API_KEY at call time, not module load time. This is intentional for testability. Do not move it to module level.
  • request<T> does not validate the JSON body at runtime. If the backend schema changes, TypeScript will not warn you — tests or runtime errors will. Consider adding Zod validation if backend contracts become less stable.
  • The FHIR extension URLs are contract surfaces. NHS_LAB_SYSTEM and CASE_TYPE_EXT must match the Python constants in app/lib/fhir_manifest.py. They are not tested by the unit tests in this PR — only the bundle shape is tested.
  • The 204 guard uses optional chaining on headers. Test environments may not provide a full Response object. Do not simplify it to resp.headers.get("content-length") without updating the tests.
