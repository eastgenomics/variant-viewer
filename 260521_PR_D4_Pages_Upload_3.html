15 App.tsx

frontend/src/App.tsx 26 lines (updated from placeholder in C1)
App default export · ~26 lines Routing shell

Purpose: The root component rendered by main.tsx. Provides the top-level layout: <Navbar> at the top, and a <main> block containing the full <Routes> tree.

Inputs

  • None (no props)

Renders

  • <Navbar>
  • 4 <Route> elements
  • Catch-all <Navigate to="/">

Key logic: The four routes are declared in order of specificity — most specific first (/patients/:patientId/variants/:variantId) before the shorter /patients/:id. React Router matches routes in declaration order, so order matters. The catch-all <Route path="*"> at the end silently redirects any unmatched URL back to the cases list.

Design decision

This file was committed as a one-line placeholder in PR C1 so that npm run build could pass before any components existed. D4 replaces it with the real routing tree. This means the C1 PR can be reviewed for scaffold correctness without the reviewer needing to understand routing logic yet.

16 PatientsPage

frontend/src/pages/PatientsPage.tsx 56 lines
PatientsPage default export Route: /

Purpose: The default landing page. Fetches all patients and renders them in <PatientListTable>. Shows a count badge, loading spinner, and error banner.

State

  • patients: PatientSummary[]
  • total: number — from API, not patients.length
  • loading: boolean
  • error: string | null

API calls

  • listPatients() on mount
  • No calls on user interaction — deletes handled by child

Key logic: The count shown under the page heading is total from the API response, not patients.length from the local state array. This matters because the local array is filtered on delete — using its length would show a decreasing count that is inconsistent with the server. setTotal(t => Math.max(0, t - 1)) decrements it in sync. The count is hidden entirely when there is an error (!loading && !error) to avoid showing "0 cases" when the error might be a network failure.

17 PatientDetailPage

frontend/src/pages/PatientDetailPage.tsx 77 lines
PatientDetailPage default export Route: /patients/:id

Purpose: Renders a patient header followed by one <SpecimenCard> per specimen. Requires two levels of API fetch: patient summary (with specimen list), then full specimen detail for each specimen in parallel.

State

  • patient: PatientDetailResponse | null
  • samples: SampleDetail[]
  • loading / notFound / error

API calls

  • getPatient(id) → patient + sample summaries
  • Promise.all(p.samples.map(s => getSample(s.id))) → full SampleDetail ×N

Key design decisions:

  • NaN guard: useParams always returns a string. If the URL contains a non-numeric segment (/patients/abc), Number("abc") is NaN. The guard if (!id || isNaN(Number(id))) catches this before the API call and sets notFound = true, which triggers <Navigate to="/" replace />.
  • String id as useEffect dep: The effect depends on [id] (the raw string from useParams), not on [patientId] (the derived number). NaN !== NaN in JavaScript, so if patientId were used as a dep and the URL contained a non-numeric id, the effect would re-fire on every render — an infinite loop. The raw string changes only when the URL actually changes.
  • useCallback for delete handler: handleDeleteSample is memoized so that all <SpecimenCard> components receive the same callback reference across renders. Without this, every state update (e.g. the loading flag) would re-render all specimen cards.

18 ClassificationPage

frontend/src/pages/ClassificationPage.tsx 100 lines
ClassificationPage default export Route: /patients/:patientId/variants/:variantId

Purpose: Fetches a single variant by id and renders a variant detail card (gene, HGVS notation, position, consequence) plus the <ClassificationPanel> component.

State

  • variant: VariantDetailResponse | null
  • loading / notFound / error

API calls

  • getVariant(Number(variantId)) on mount
  • On 404: Navigate to /patients/:patientId (not root)

case_type runtime validation: ClassificationPanel accepts caseType: "germline" | "somatic". The backend stores only these two values, but the TypeScript type from the API is string (not a literal union). Rather than a type cast like variant.case_type as "germline" | "somatic" (which silences the compiler but does nothing at runtime), the code uses a runtime guard:

caseType={
  variant.case_type === "somatic" ? "somatic" : "germline"
}

This is a safe default — if the database somehow contained an unexpected value (e.g. a future migration adds "mosaic"), the classification panel would default to "germline" rather than passing an invalid value through to the classification engine.

Passing active classification to the panel: The variant detail response nests the classification inside active_classification (which includes its criteria array). ClassificationPanel takes these as two separate props: initialClassification (the classification metadata, without criteria) and initialCriteria (the criteria array). The page destructures them from the response:

initialClassification={variant.active_classification ? {
  id: variant.active_classification.id,
  framework: variant.active_classification.framework,
  // ... other fields, but NOT criteria
} : null}
initialCriteria={variant.active_classification?.criteria ?? []}

20 UploadForm — form state and structure

frontend/src/components/UploadForm.tsx ~254 lines

Unlike the pages, UploadForm is a stateful component with its own upload lifecycle. It manages both the form field values and the upload progress state machine.

Form field state

State variableForm fieldNotes
labNumberLab record numberRequired; trimmed before use
sampleNameSpecimen nameOptional; falls back to file.name when empty
caseTypeCase type select"germline" | "somatic"
sequencingDateSequencing dateISO date string; optional
pipelineKeyPipeline selectInitialised to first pipeline option
fileFile inputFile | null; .vcf or .vcf.gz accepted

Note: date of birth is intentionally absent. It was removed from the patients table by migration 004 (UK GDPR data-minimisation). The comment in the source makes this explicit so future developers do not add it back by mistake.

Upload phase state machine

PhaseMeaningUI state
idleNo upload in progressButton reads "Upload VCF"; enabled
uploadingProd: fetching presigned URL or uploading to S3Button shows progress text; disabled
ingestingEither path: triggering backend ingestButton shows progress text; disabled
doneIngest succeededForm replaced by green success banner
errorAny step failedRed error banner shown; form still visible; button re-enabled
Phase reset on retry

The first line of handleSubmit sets setPhase("idle") before the validation checks. This ensures that if a user sees an error and corrects it, the button state machine starts clean. Without this, submitting with an error state already set would leave isUploading incorrectly false even if the phase was stuck at "error" from a previous attempt.

21 handleDevUpload

handleDevUpload async, ~20 lines · dev path only Dev: POST /api/ingest-direct

Purpose: Upload path for local development. Sends the VCF file and form fields directly to POST /api/ingest-direct as a multipart/form-data request. No S3 credentials required. The backend parses the VCF locally, writes all DB rows, and returns a sample_id.

Inputs (closure)

  • file — the selected File object
  • labNumber, sampleName, caseType, pipelineKey, sequencingDate

Side effects

  • Sets phase = "ingesting"
  • On success: sets phase = "done", progress message
  • Throws on HTTP error (caught by handleSubmit)

Key logic — resp.ok before resp.json():

if (!resp.ok) {
  let detail = `HTTP ${resp.status}`;
  try { detail = (await resp.json()).detail ?? detail; } catch { /* ignore */ }
  throw new Error(detail);
}
const body = await resp.json();  // only on success

Checking resp.ok before calling resp.json() is important because error responses (e.g. 413 file too large, 400 bad VCF) may not return valid JSON — or may return a FastAPI error body that should be surfaced as the error message, not silently parsed as success.

22 handleProdUpload

handleProdUpload async, ~40 lines · prod path only Prod: upload-url → S3 ×2 → ingest

Purpose: Production upload path. Executes a strict four-step sequence: (1) request presigned URLs from the backend, (2) PUT the VCF to S3, (3) build and PUT the FHIR manifest JSON to S3, (4) trigger the backend ingest via POST /api/ingest.

Steps

  1. getUploadUrl({vcf_filename})
  2. Direct PUT to urlResp.vcf_url
  3. buildManifest() → PUT to urlResp.manifest_url
  4. ingestSample({vcf_s3_key: urlResp.vcf_key})

Key field names

  • getUploadUrl({vcf_filename}) — not filename
  • VCF PUT: Content-Type: application/octet-stream
  • Manifest PUT: Content-Type: application/json
  • ingestSample({vcf_s3_key}) — uses the vcf_key from step 1, not the presigned URL

Why the manifest is uploaded before triggering ingest: The backend ingest Lambda (triggered by POST /api/ingest) downloads both the VCF and the manifest from S3. If the manifest PUT happens after the ingest call, there is a race condition where the Lambda may try to read a manifest file that has not yet been written.

Field name alignment

The call is getUploadUrl({vcf_filename: file.name}) — the field is named vcf_filename, matching the backend UploadUrlRequest.vcf_filename Pydantic field exactly. An earlier incorrect version used filename, which would have produced a 422 validation error from FastAPI.

23 handleSubmit and the phase state machine

handleSubmit async, ~20 lines · form onSubmit handler Orchestration

Purpose: The entry point for all upload logic. Validates form inputs, determines which upload path to use, delegates to either handleDevUpload or handleProdUpload, and catches any thrown errors into the error state.

Validation

  • e.preventDefault() — stop native form submit
  • Phase reset to "idle" for clean retry
  • Guard: labNumber required
  • Guard: file required

Path selection

  • Evaluated at call time (not module level)
  • import.meta.env.DEV = true in Vite dev server
  • VITE_APP_ENV === "development" for Docker dev builds
  • All other cases → handleProdUpload

Error handling: Both handleDevUpload and handleProdUpload are designed to throw on failure rather than call setError themselves. This keeps the two path functions focused on their happy-path logic, and handleSubmit owns all error state updates. A single try/catch wrapping both calls is all that is needed.
